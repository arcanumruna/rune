# A7 review — park-until-work + epoll-first polling (2026-10-04)

Scope: broker `rune-broker-wt33` perf/a7-idle **60d6bdf**, client `rune-client-cpp-wt9` perf/a7-client-idle **fc509e8**,
against Aeron 1.41.4 (`~/.conan2/p/aeron587c0be5e0d59`, `media/aeron_udp_transport_poller.c`, `aeron_udp_channel_transport.c`,
`aeron_send_channel_endpoint.c`) and rune_gso (`rune-protocol/src/net/rune_gso_bindings.c`). Read-only review: nothing built or run.
The kernel claims below come from Linux UDP and epoll semantics. They are not reproduced on the VM; the test to reproduce
them is given with each finding.

## Verdict

**CHANGES REQUIRED.** One CRITICAL: with epoll-first on, a worker busy-spins whenever a peer's port is unreachable
(crash, restart, startup before peers are up, DR kills). Two MAJOR: latency on paths that were never measured
(ring, io_uring and timer work), and tests that miss both risks. The rest is MEDIUM or LOW.

What is sound:
- Lifecycle: the wake fds are the pollers' epoll instances, which live as long as the driver. Runners are joined before
  `teardownShardRuntimes_`, so there is no fd reuse or POLLNVAL spin at shutdown.
- Polling: transports added or removed at runtime land in the same epoll instance. Aeron registers EPOLLIN level
  triggered, and a nested epoll fd under ppoll stays level triggered. A backlog larger than vlen keeps the socket
  readable, and a pass that drains anything returns work > 0.
- Buffering: rune_gso GRO keeps no userspace stash, so no data hides from epoll.
- Off-switches and macOS: the stock bindings are copied, not patched process-wide. The macOS and non-Linux stubs keep
  the legacy backoff (0 fds → `makeBackoffIdle`, byte-identical).
- Hard rules: no atomics or mutexes added.

## CRITICAL

### C1 — Epoll-first never drains EPOLLERR, so the wake fd stays readable and the worker busy-spins while a peer is down
`libs/node/src/DriverWakeFds.c:81` (client: `src/transport/DriverWakeFds.c:81`): `if (events[i].events & EPOLLIN)`.

Mechanism:
- Consensus and replication publications are plain `aeron:udp?endpoint=host:port` (`NodeConfig.cpp:147/152`, shard
  repl/ingress channels). `AERON_DRIVER_CONNECT_DEFAULT` is true, so `aeron_send_channel_endpoint_create` calls
  `connect()` on every such send-endpoint socket.
- Those sockets sit in the **sender** poller, and a 3-node shard driver has at least 2 of them, so the epoll-first
  branch is taken.
- When the peer process is gone but its host is up (crash, restart, kill in the single-box bench or in Docker DR, node
  not started yet), each Aeron send gets an ICMP port-unreachable. The kernel sets `sk_err` (`__udp4_lib_err`: hard
  error on a connected socket). A host-unreachable after an ARP timeout does the same.
- `datagram_poll` then reports **EPOLLERR without EPOLLIN**. Epoll always adds EPOLLERR to the registered mask, so the
  poller's epoll fd becomes readable.
- In stock Aeron (≤ 5 transports) the next `recvmmsg` returns ECONNREFUSED and clears `sk_err`, which Aeron maps to 0.
  `rune_gro_recvmmsg` does the same.
- `rune_epoll_first_poll` skips any event without EPOLLIN, so `sk_err` is never consumed by the receive path. It is
  only cleared by the next `sendmsg` on that socket, which then fails. The following successful send triggers a new
  ICMP. While the peer is down, the error is pending almost all the time.

Failure scenario:
- A 3-node cluster, node C is killed.
- On A and B, every shard worker's ppoll on `sender.poller.fd` returns at once (`readinessWakes` climbs). The pass
  finds no work (no recvmmsg is issued, so work == 0), the idle parks again, and ppoll returns immediately again.
- Result: 100% CPU per worker, each loop a full ~35 µs syscall pass. This breaks the never-busy-spin rule.
- On the 4-core box this starves the surviving nodes during exactly the failover window that is known to be sensitive
  to CPU starvation (heartbeat churn, rune-idle-churn-cpu-starvation).
- The same applies to the client: InvokerBench, or any owner parking on `Client::wakeFds()`, spins while a broker node
  is down.
- The off arm is also exposed. With `RUNE_AERON_EPOLL_POLL=0`, any poller above 5 transports takes Aeron's own epoll
  branch, which has the same EPOLLIN-only check. Parking on wake fds therefore spins there too. Upstream Aeron gets
  away with this only because nothing parks on the poller fd.

Fix:
- In `rune_epoll_first_poll`, for `events & (EPOLLERR|EPOLLHUP)` without EPOLLIN, consume the error with
  `getsockopt(recv_fd, SOL_SOCKET, SO_ERROR, …)`. That clears `sk_err` without going through Aeron's error path. The
  alternative is to call `recvmmsg_func` for `EPOLLIN|EPOLLERR` (ECONNREFUSED → 0, but EHOSTUNREACH → -1 → aborts the
  loop).
- Do the same for the > 5 case: always route through rune's poller when wake fds are in use, or have
  `makeShardIdle` refuse wake mode when `aeronEpollPoll` is off and a poller can exceed 5 transports.
- Repro test (deterministic, Linux, must be RED today):
  1. Start an invoker driver with 2 exclusive publications to 2 closed loopback ports.
  2. Pump until setup frames go out.
  3. `ParkUntilWorkIdle{0,0,30ms,30ms}` on `wakeFds()` after a pass returning 0 must wait ≥ 20 ms with
     `readinessWakes()==0`.
- Add the same test on the client.

## MAJOR

### M1 — Parking after the first empty pass adds about 50–250 µs to every hop that has no fd, and this was never measured
Code: `NodeConfig.h:290` (derived shape 0/0 when fds exist), `WorkerPool.h:73`, `ParkUntilWorkIdle.h:107`.

Before A7, work that has no fd was picked up within the ~30-pass poll window, about 1 ms of polling after the last
activity. That covers:
- cross-thread rings: runtime → worker (`drainIngress_`), worker → gateway `ret_` (`Worker.h:989`, consumed by
  NodeRuntimeAgent), and session ops
- io_uring CQEs (`reapDurableCompletions_`; `UringFlushBackend::ringFd_` is never in the poll set)
- Aeron timers: NAK delay, SM and heartbeat, the conductor processing a command queued by this thread's own client
  conductor after the driver step of the same pass
- ingress held back by a full `ret_` (`Worker.h` `doWorkShard_`: `pollWorkerIngress_` skipped, data left in the term
  buffer, so no readiness)

Now the worker parks right after the first empty pass. That park lasts at least the 50 µs default timer slack (see M3)
and doubles to 200 µs plus slack.

Failure scenarios:
- **fsync / Strict durability**: every fsync completion waits out the current park. Expect +50–250 µs on the ack, against
  a p99 target of ≤ 100 µs.
- **W > 1 (bigger boxes, already planned)**: every worker → runtime → worker hop on another thread adds the same.
- **Loss recovery**: NAK and retransmit timers fire up to 200 µs late.
- The A/B ran only W=1 fused, with fsync off, at 20k where passes are always busy (> 95% do work). None of this was
  exercised. "p50 unchanged" does not cover it.

Fix:
- Put the io_uring ring fd in the wake set. It is readable when the CQ is non-empty, needs no atomics, and costs
  nothing to add.
- Keep a short spin/yield window, or compute the park as min(next timer deadline, cap), when W > 1 or a durable
  backend is active.
- Measure fsync-on and W > 1 latency (ABAB, n ≥ 15) before calling the default safe.
- Longer term: an eventfd doorbell on the cross-thread rings (the design change the report already names).

### M2 — The tests do not exercise the risky paths of (1) and (2)
- `EmbeddedDriverEpollPollRegression.MultiTransportPollerDeliversEverything` passes on either path. It never proves
  that the epoll branch ran: no counter, no check that the poller length > 1, and the stock fallback delivers the same.
  Expose a test counter (epoll polls taken) and assert it.
- Missing tests:
  - EPOLLERR / ICMP peer-down (C1)
  - a transport add/remove crossing the 1↔2 threshold while running (subscription close, new publication), with
    delivery checked after each step
  - a backlog larger than vlen on one socket plus fairness (one hot socket next to a quiet one, both delivered)
  - an AgentRunner + ShardAgent end-to-end test: a parked runner processes a datagram promptly, and ring-only work is
    processed within the maxPark bound
  - io_uring completion latency while parked
- The client copy of `DriverWakeFds.c` has no multi-transport delivery test at all (only installed/active and a raw
  ppoll wake).
- `ShardIdleRegression.DefaultWithWakeFdsParksUntilWorkAfterFirstEmptyPass` and
  `ParkUntilWorkIdleRegression.WakeShapeParksOnFirstEmptyPass` check a shape constant. They guard no bug, so they
  should not carry the Regression label (it dilutes the suite).

## MEDIUM

### D1 — Timer slack makes the documented "1 µs doubling" park a 50 µs-or-longer park
`ParkUntilWorkIdle.h:107`: shard workers never set `PR_SET_TIMERSLACK`. The default is 50 µs for SCHED_OTHER. The bench
sets it (`BenchIdle.h`, 1 µs); the broker does not.
- Every ppoll timeout of 1, 2, 4, … µs actually ends at about 51, 52, 54, … µs. The shape that is logged (`parkNs=1000-200000`)
  and the comments describe behaviour that does not happen.
- That slack is the real floor of M1.

Fix: `prctl(PR_SET_TIMERSLACK, 1000)` once per shard runner thread, as the bench does, or log the effective slack.

### D2 — The A/B does not prove neutrality, and B is worse on one p99
- Saturation is −2% at n=2, and B's 20k p99 in r1 is 24.0 ms against 17.7 ms.
- The report calls both "noise". That conflicts with the standing rule: interleaved ABAB, n ≥ 15, and cite the code
  path. Treat it as unproven.
- Plausible real cause of the sat dip: when all k transports are ready, epoll-first costs 1 + k syscalls against k
  (an extra `epoll_wait` per duty cycle at saturation).

Fix: run ABAB n ≥ 15 for sat and for 20k p99. If the dip is real, skip the `epoll_wait` when the previous poll found
every transport ready (an adaptive threshold).

### D3 — Env parsing differs between broker and client and between knobs, sometimes silently
- `RUNE_AERON_EPOLL_POLL` (broker, `NodeConfig.cpp`) accepts `0/1/true/false` and rejects anything else.
- `RUNE_CLIENT_AERON_EPOLL_POLL` (client, `TransportConfig.h:210`, `readSize`) accepts only numbers. `=false` logs a
  warning and keeps epoll **on**: someone disabling the A/B off arm with "false" silently measures the on arm.
- `RUNE_IDLE_WAKE` (`NodeConfig.cpp:1203`) treats any unrecognised value as on, with no error.
- `RUNE_IDLE_SPINS/YIELDS` (`:1212`) silently ignore garbage or negative values.

Fix: one strict bool parser on both sides, matching `RUNE_AERON_UDP_GSO`, and reject unparsable spins/yields at startup.

## LOW

- **L1 — One failing transport skips the rest of the poll.** In `rune_epoll_first_poll` (`DriverWakeFds.c:87`) a
  recvmmsg error on one transport returns early and skips the other ready sockets for that duty cycle. This matches
  Aeron, and the ready list rotates, so there is no permanent starvation. With the C1 fix using recvmmsg on EPOLLERR,
  EHOSTUNREACH would hit this path on every ICMP. Prefer SO_ERROR, or `continue` on a per-transport error.
- **L2 — Fragile across Aeron upgrades.** The code depends on Aeron internals: `poller->fd`, `bindings_clientd` holding
  `epoll_event[]` of capacity ≥ length, and receiver/sender poller field names. Add a startup self-check (for example
  `rune_fd_is_epoll(poller.fd)` already exists, so log and fall back to stock when it fails) and pin the Aeron version
  in a comment or static_assert.
- **L3 — Virtual calls on the hot loop.** `AgentRunner` calls the virtual `idle_.idle(w)` and `agent_.doWork(now)` on
  every pass. This was already true before A7, but it breaks the no-virtual-calls-on-hot-path rule. A7 adds a new
  `IdleStrategy` subclass in that slot instead of de-virtualising it (a template or concrete `ParkUntilWorkIdle`
  member in the shard runner).
- **L4 — Duplicated C code.** `DriverWakeFds.c` exists twice, in the broker and the client, so the C1 fix has to land
  twice. Move it next to `rune_gso_bindings.c` in rune-protocol, which both repos already compile.
- **L5 — Production API named as a test seam.** `Client::wakeFds` reaches the transport through
  `agent_.testTransport()`.
- **L6 — Driver error log noise while a peer is down.** In Thread mode (no parking), epoll-first leaves `sk_err` pending
  until the next send, which then fails with ECONNREFUSED. That adds driver error-log entries for a down peer (stock
  had cleared the error in recvmmsg). It goes away with the C1 fix.
- **L7 — `idleMaxParkUs` is unbounded.** A huge value (for example 1 s) bounds ring and timer work by that value with
  no warning. Clamp it or warn.

## Re-review (fix round 1)

Scope: rune-protocol **8636742** (`src/net/rune_driver_wake.c` + header), broker `rune-broker-wt33` perf/a7-idle
**60d6bdf..5dcd4fd**, client `rune-client-cpp-wt9` perf/a7-client-idle **fc509e8..7e98e33**, against Aeron 1.41.4
(`media/aeron_udp_transport_poller.c`, `aeron_udp_channel_transport.c`). Read-only: nothing was built or run. The
RED→GREEN and peer-kill numbers come from the fix report and were not reproduced here.

### Verdict

**APPROVED. No CRITICAL or MAJOR findings, so no further re-review is needed.** C1, D1, D3 and L4 are fixed. M1 is
fixed in code: the spin/yield phase is back and the io_uring fd is in the wake set. Its latency proof is still
outstanding (MEDIUM-2). M2 is fixed: each risky path now has a test, and the C1 and epoll-off tests were RED on the
old code. The fix round adds one MEDIUM regression (MEDIUM-1, timer slack on the fallback arm). The remaining items
are MEDIUM backlog or LOW.

### Fixed: verification notes

- **C1. Fixed for every reachable event path, on both the broker and the client (one shared source).**
  - `rune_driver_wake.c:95-116` reads every event epoll returns.
    - EPOLLERR, with or without EPOLLIN: `getsockopt(SO_ERROR)` clears `sk_err`.
    - EPOLLIN: recvmmsg.
  - `recv_fd` is the right fd. It is the fd Aeron registers (`aeron_udp_transport_poller.c:93-96`), and it equals
    `fd` for unicast (`aeron_udp_channel_transport.c:113`).
  - No error-queue source can keep EPOLLERR set after SO_ERROR:
    - Aeron enables only RX timestamping.
    - Neither Aeron nor rune_gso sets IP_RECVERR or SO_ZEROCOPY.
  - Pollers with 0 or 1 transport (`:71`) go through stock recvmmsg, which consumes `sk_err` itself (ECONNREFUSED →
    0; any other errno → -1, but the error is still cleared).
  - Receive sockets are unconnected, so ICMP never sets `sk_err` on them.
  - The sender polls on every pass with `bytes_sent == 0`, and a pass that sends returns work > 0 and does not park.
    So a readable sender poller is always polled before a park.
  - Off arm: `rune_driver_wake_fds` returns 0 unless the bindings are epoll-first, which covers both
    `RUNE_AERON_EPOLL_POLL=0` and the > 5 stock branch. `ShardAgentWakeRegression.EpollFirstOffExposesNoWakeFdsRegression`
    pins this, and it fails on 60d6bdf.
  - EPOLLHUP-only cannot occur on a UDP socket that is never `shutdown()`. That is accepted.
  - **One gap: the "no ready fd left after a pass" rule does not hold strictly.** A SO_ERROR other than ECONNREFUSED
    (EHOSTUNREACH, ENETUNREACH, EMSGSIZE from PMTU) returns -1 at `:106`. The remaining sockets from that
    `epoll_wait` stay level-triggered ready for the next pass, so an owner that parks right after wakes at once.
    - This is bounded, not a spin: each pass consumes at least the failing socket, and the ready list rotates.
    - Stock Aeron does the same on a recvmmsg error. It is the existing L1, now also reached through SO_ERROR, and
      stays in the backlog.
- **M1. Fixed in code.**
  - `shardIdleShape()` is 10/20 whether or not there are fds (`NodeConfig.h`). This is pinned by the shape test
    `ShardIdle.DefaultWithWakeFdsIsParkUntilWorkAfterTheAeronSpinYieldPhase`.
  - The io_uring ring fd joins the wake set only alongside driver fds (`ShardAgent.h:102-108`).
  - The ring fd is a safe wake source:
    - The ring is created with no setup flags (no DEFER_TASKRUN/SQPOLL), so POLLIN means the CQ holds completions.
    - `reapDurableCompletions_` runs on every shard pass (`Worker.h:1384`) and drains the whole CQ, including the
      internal NOP.
    - In-flight work is capped at submitDepth, below the CQ size, so the CQ cannot overflow and leave POLLIN set
      with nothing to reap.
    - The fd is a Worker member that lives longer than the runner, so there is no POLLNVAL risk.
  - The cap for fd-less work is unchanged (the accepted design).
- **M2. Fixed.**
  - The epoll-path seam asserts > 0 with epoll-first on and == 0 on the stock arm.
  - New tests:
    - 1↔2 transport add and remove
    - a backlog beyond one batch, plus fairness for a quiet socket
    - an AgentRunner that wakes on a datagram
    - fd-less work handled within the cap
    - an io_uring wake
    - the client multi-transport case
  - The two C1 tests were RED on the old code (3/3, per the report). The shape-constant tests lost the Regression
    label.
- **D1. Fixed.** The slack is set to 1 µs on the runner's first pass (`ShardAgent.h:74-76`). See MEDIUM-1 for the
  side effect.
- **D3. Fixed.**
  - Broker: strict 0/1/false/true for `RUNE_IDLE_WAKE`. Non-negative integers for spins and yields; `parseInt32`
    rejects trailing garbage. Anything else refuses startup.
  - Client: `false` now works; any other value warns and keeps the configured value.
  - No script in wt33, wt26 or wt9 used the spellings that are now refused (`off`, `no`).
- **L4. Fixed.**
  - Both repos compile the single rune-protocol source, the same way as rune_gso.
  - No references to `DriverWakeFds`, `rune_client_driver_wake_fds` or `rune_client_driver_epoll*` remain.
  - The non-Linux stub covers every symbol, including the new test seam. The macOS build links aeron only under
    `UNIX AND NOT APPLE`, as before.
- **Hard rules.**
  - No new atomics or mutexes in production code. `std::atomic` appears only in the test `PumpAgent`.
  - No new virtual calls, `std::function` or allocation on the poll path. The only `malloc` is the install-time
    bindings copy, as before.
  - No new busy loop: the spin/yield phase is the bounded Aeron shape that was accepted before A7.

### MEDIUM

**MEDIUM-1 (introduced). The 1 µs timer slack also applies to the legacy-backoff fallback, so that arm no longer
matches pre-A7. It also re-creates the idle churn on the 4-core box.**
- Code: `ShardAgent.h:74-76`. It sets `PR_SET_TIMERSLACK` for every shard runner, whatever idle strategy
  `makeShardIdle` picked.
- Arms that now run the old `makeBackoffIdle` (10 spins, 20 yields, 1 µs→200 µs nanosleep) with 1 µs slack instead
  of 50 µs:
  - `RUNE_IDLE_WAKE=0`
  - `RUNE_AERON_EPOLL_POLL=0`, which C1 deliberately routes to this backoff
  - any Linux runner without driver fds
- Effect:
  - Before, the 1, 2, 4, 8, 16 and 32 µs parks were really about 51–82 µs.
  - Now they really are 1–32 µs. That adds about 6 full passes (~35 µs of syscalls each) per idle episode, and
    heartbeats reset the backoff every few ms.
  - This is the same "1 µs park" churn that rune-idle-churn-cpu-starvation identified as starving workers on the
    4-core box.
- Failure scenario:
  - An A/B that uses `RUNE_IDLE_WAKE=0` or `RUNE_AERON_EPOLL_POLL=0` as the "pre-A7" baseline measures a different,
    more CPU-hungry baseline.
  - `WorkerPool.h:70` ("legacy Aeron backoff — byte-identical to pre-A7") is now false.
- Attribution gap: the same slack makes the park-until-work arm's first 6 parks shorter. Part of the reported 23% →
  31% idle-CPU rise may be the slack and not the restored spin/yield phase, and the report credits all of it to the
  spin/yield phase.
- Fix, either of:
  - Set the slack only when `makeShardIdle` returned a `ParkUntilWorkIdle` with `wakeFdCount() > 0` (for example a
    flag passed into the ShardAgent, or set it in the runner start path).
  - Keep it everywhere, fix the comment, re-baseline the off arm, and split the idle-CPU delta with one
    slack-only run.

**MEDIUM-2 (M1 residual, not a regression). The latency effect of M1 is still unproven.**
- Fd-less work that arrives after the ~30-pass spin/yield window still waits up to `idleMaxParkUs` (200 µs, plus
  1 µs slack). That covers:
  - W > 1 cross-thread hops (runtime ↔ worker rings)
  - Aeron NAK, SM and heartbeat timers
  - ingress held back by a full `ret_`
  - the **portable** backend's completions. Docker's default seccomp profile blocks io_uring, so the DR e2e
    matrix runs portable and gets no completion fd.
- The fsync A/B could not show anything (both arms collapse; see MEDIUM-3), and W > 1 was not run.
- Backlog, together with D2: an ABAB n ≥ 15 with fsync on at a sustainable rate, and W > 1.
- Longer term: an eventfd doorbell on the cross-thread rings.

**MEDIUM-3 (pre-existing; found in the fix report, not caused by A7). The durable tier collapses at 20k rec/s with a
5 ms fsync in both arms.**
- p99 is 9.9–14.9 s in every run.
- Throughput is 8,252–20,003 rec/s, and B r1 delivered less than half of A r1.
- A p99 of seconds means an unbounded backlog: the fsync tier cannot keep up at 20k on that box, or something
  serializes behind it.
- This is unrelated to the A7 diff (A shows it too). It still needs its own ticket and root cause (FR capture of
  fsync submit → reap → ack). Until then no durable-tier latency claim can be validated, including M1's io_uring
  wake.
