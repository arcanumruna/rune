# Rune Materialized Views — Foundation: Typed Topics, rune-codec, and Rune QL

> **STATUS: DESIGN / FOR REVIEW.** First foundation of the broker-local
> materialized-views program. Supersedes the idea-capture draft
> [`2026-09-15-rune-db-face-materialized-views-transactions-DRAFT.md`]. This
> design covers **typed topics + the schema/codec system + the language
> surface**. It does **not** build the view engine, folds, or transactions —
> those are later specs that depend on this foundation.

## 1. Program context & decomposition

End goal: **broker-local materialized views** — derived, always-current tables
the broker maintains by folding a topic's log, queryable directly. The canonical
example folds three co-partitioned logs (`characters`, `attributes`, `position`,
all partitioned by `userId`) into a `characters` view: a local join on
`characterId` with per-source merge rules (character = upsert, attributes =
sum-of-deltas, position = last-write).

Program-wide decisions locked during brainstorming (later specs inherit them):

- **`rune-codec` — our own SBE-style codec generator.** SBE's C++ toolchain has
  **no runtime IR / on-the-fly decoder**, so it cannot give the broker generic
  field access to a runtime-defined schema. `rune-codec` generates a zero-copy
  fixed-layout codec **plus** a **serializable, human-readable descriptor** (the
  full type) **plus** a **fingerprint**. The descriptor is what the broker uses
  at runtime for validation and generic field access; there is no separate
  sidecar. (SBE remains only for internal replication control messages.)
- **The broker is a schema registry.** Schemas are **persisted, replicated, and
  versioned** (via a compacted internal topic). The broker is the source of
  truth for a topic's schema.
- **Rune QL — one client-side language for DDL and queries.** `rune ql
  "create topic …"` and query statements are parsed **client-side** into a
  compact **plan IR**; the broker only ever speaks the typed API (`DefineTopic`,
  later `DefineView`) and executes plan IR — **it never parses text.**
- **Compile-time typed clients.** `openTopic<T>()` returns a handle that only
  accepts `T`; the broker verifies `fingerprint(T)` against the registered
  schema at open. `T` is generated by `rune gen <topic>` (below).
- **Additive-only evolution**, single latest descriptor, lossless (§8).
- **Replicated deterministic fold** (for the later view specs): leader folds
  after append, replicas fold on `applyReplicated`; folds must be deterministic.

**Decomposition — the foundation is three sub-projects, each its own plan, in
order:**

- **0a — `rune-codec`:** the codec + descriptor format + fingerprint + a
  broker-side runtime descriptor reader/validator. No networking. **Implemented
  first; this spec's plan targets 0a.**
- **0b — Registry & typed transport:** `DefineTopic`/`GetTopicSchema` wire API,
  the replicated `__topic_schemas` registry, per-worker validation, client
  `openTopic<T>()` fingerprint-verified open, and `rune gen <topic>` (fetch
  descriptor → codegen).
- **0c — Rune QL:** client-side parser/AST + backends (apply → `DefineTopic`;
  codegen → `rune-codec`; query → plan IR) + the `rune` CLI (`rune query`,
  `rune schema apply|get|generate|list`).

Later foundations (own specs): single-source views → co-partitioned join views →
query execution → sync apply + snapshots → cross-partition transactions.

## 2. Goals / non-goals

**Goals**
- A typed-record system (`rune-codec`) usable at runtime by the broker with **no
  compiled-in knowledge of the schema**.
- A runtime, replicated, versioned **schema registry** in the broker.
- A **compile-time typed client** path (`openTopic<T>()`), generated from the
  registry by `rune gen`.
- The **Rune QL** language surface for `create topic` (and the hooks for queries
  and, later, `create view`).
- **Opt-in, per-worker, fast validation** derived from the descriptor.

**Non-goals (deferred to later specs)**
- The view engine, folds, joins, the query *execution* engine (only the plan-IR
  shape is defined here), transactions, distribution/co-partitioning policy.
- Non-additive schema evolution; multiple historical descriptors coexisting.
- A full SQL implementation (Rune QL is a small purpose-built language).

## 3. Component: `rune-codec` (sub-project 0a)

### 3.1 The descriptor

`rune-codec`'s type model is a flat, ordered field set laid out **SBE-style**:
fixed-width fields form a contiguous **block** at deterministic offsets;
variable-length fields (`string`, `bytes`) follow as length-prefixed **var-data**.

The **descriptor** is the serializable + human-readable representation of the
entire type:

```
schema characters  fp=0xA1B2C3D4  block=20  version=1 {
  id        int64   @0
  userId    int64   @8    key
  strength  int32   @16
  name      string  vardata#0   sinceVersion=1
}
```

- **Serializable form:** a compact binary encoding of the same (field id, name,
  primitive type, offset, sinceVersion, optional enum/range, key/timestamp
  flags). This is what crosses the wire and is stored in the registry.
- **Human-readable form:** the text above, for `rune gen`, tooling, and debugging.
- Both are produced by `rune-codec` from the same in-memory descriptor object.

### 3.2 The fingerprint

`fingerprint = hash(canonical descriptor)` — a deterministic hash over the
canonical (field-order-normalized) descriptor. It is computed **identically**
wherever the descriptor is built (codegen and registry), so a client's
`fingerprint(T)` equals the registered fingerprint iff the types match. Additive
evolution bumps `version` and the fingerprint together; compatibility is checked
by `(schemaId, version, additive-superset)` not raw equality (§8).

### 3.3 Generated codec

From a descriptor, `rune-codec` emits a C++ header: a typed struct with fields,
`encode(buf)→len` / `decode(bytes)→view` (fixed-offset writes + var-data tail),
`encodedSize()`, `kBlockLength`, `kFingerprint`, `kTopicType`, and
`descriptor()`. (See the walked-through `Characters` example in the design notes;
layout = fixed block then var-data.)

### 3.4 Broker-side runtime reader/validator

The same 0a library provides, **without codegen**, given a descriptor + a record's
bytes:
- **Generic field read by name/id** — `readField(desc, bytes, fieldId) → typed
  value/view` (fixed field = read at offset; var-data = follow the tail). This is
  the primitive the view fold and query executor consume.
- **Validator** — `validate(desc, bytes) → ok | fieldError`: length/bounds +
  per-field type/enum/range + var-data consistency, **version-aware** (only
  fields present in the record's version are required). Target implementation is
  a precomputed descriptor→field-table for a tight branch-light loop (the
  OTF-vs-table choice is decided by benchmark; both are correct).

0a is pure library code (no networking, no broker deps) and is independently
unit-tested + benchmarked.

## 4. Component: schema registry & typed transport (sub-project 0b)

### 4.1 Wire API (rune-protocol, templateIds 64–95)

Hand-coded client messages mirroring `MetadataMessages.h`, using the
`putVarBytes32`/`getVarBytes32` var-data helpers for the descriptor blob:

- `DefineTopic` (64, client→broker): `{ topicName, partitionCount, keyField,
  validate, descriptorBlob }`.
- `DefineTopicResponse` (65): `{ topicId, version, errorCode }`.
- `GetTopicSchema` (66) / `TopicSchemaResponse` (67): `{ topicName } →
  { topicId, version, descriptorBlob, errorCode }` — used by `rune gen`.

New `ErrorCode`s: `InvalidSchema`, `IncompatibleSchema`, `SchemaValidationFailed`,
`UnknownTopic`. `Dispatch.h::isKnownTemplate()` extended to accept 64–95.

### 4.2 Registry & persistence

Mirrors the existing `__transaction_state` compacted-topic pattern
(`BrokerNode.cpp`): a compacted internal topic **`__topic_schemas`** keyed by
`topicId`, value = the registered `TopicSchema` `{ topicId, version, keyField,
validate, descriptorBlob }`. Appended via a `PartitionReplica`
(`cleanupPolicy=Compact`, majority-durable), applied on leader + every replica to
an in-memory `SchemaRegistry` (`topicId → { descriptor (parsed), validator?,
fingerprint, keyField, version }`), rebuilt from the compacted topic on restart.
`TopicSpec` (`NodeConfig.h`) gains `keyField`, `validate`, and a `descriptorRef`.

### 4.3 `DefineTopic` handler (gateway)

Added to `ClientGateway::onFragment` dispatch (mirrors `handleProduce`):
parse the descriptor blob (reject `InvalidSchema` if malformed), assign
`topicId` + `partitionCount` + placement (**`DefineTopic` owns topic creation** —
it is the runtime replacement for the env-property path), append the
`TopicSchema` to `__topic_schemas`, respond with `topicId`/`version`.

### 4.4 Per-worker validation

When a topic's `validate` is on, `Worker::executeProduceWire_` runs
`rune-codec`'s validator on the record **before `appendNoSyncRestamp`** — on the
worker's own ingress path so it **scales with worker count** and never serializes
on a shared stage. Off ⇒ one branch; fail ⇒ `SchemaValidationFailed`, no append.

### 4.5 Typed client open + `rune gen`

- `Client::openTopic<T>(name)` (mirrors the `ping()` correlation→promise
  round-trip): sends `{ name, fingerprint(T) }`; broker verifies compatibility
  with the registered schema; returns a `TypedTopic<T>` handle whose `send(T)`
  calls `T::encode`. Mismatch ⇒ error.
- `rune schema generate <topic>`: `GetTopicSchema` → descriptor → `rune-codec`
  generates `<topic>.gen.h` into the publisher's build tree. The publisher's
  build owns the output location; the broker is the source of truth.
  (`rune schema generate --from-file` may also generate from a local descriptor
  for offline builds.)
- `MetadataCache` (client) gains `{ schemaId/version, validate, keyField }` per
  topic; the full descriptor is fetched on demand.

## 5. Component: Rune QL & CLI (sub-project 0c)

- **Language:** small, SQL-flavored, deliberately-tiny grammar (hand-written
  recursive-descent / PEG — single-pass, microsecond parse, no generator dep).
  Boundary = engine capability. DDL now (`create topic <name> { <fields> }
  partitions N key <field>;`), queries and `create view` later.
- **Parser/AST:** one parser, multiple backends:
  - **apply** → emits `DefineTopic` (and later `DefineView`) API calls;
  - **codegen** → builds the descriptor and drives `rune-codec` (`rune gen`);
  - **query** → compiles to the **plan IR**.
- **Plan IR (query wire form):** a compact opcode stream over **field ids from
  the descriptor** + constants (`OPEN_VIEW`, `LOOKUP_KEY`, `FILTER field op
  const`, `PROJECT fieldmask`, `AGGREGATE`). The broker runs a tiny interpreter
  against the view store — no text parsing on the server. (Only the *shape* is
  fixed here; execution is a later spec.)
- **CLI:**
  - `rune schema apply <file|->` — create/alter topics from Rune QL definitions
    (declarative, idempotent).
  - `rune schema get <topic>` — print the human-readable descriptor.
  - `rune schema generate <topic>` — emit the C++ rune-codec header.
  - `rune schema list` — list registered topics.
  - `rune query "<select …>"` — run a read query (read-only verb).

  `schema apply` and `query` share the same Rune QL parser; the verb signals
  intent (and keeps `query` non-mutating). Repeated queries can be prepared once
  → plan IR cached/reused.

## 6. Data flows

- **Create topic:** `rune schema apply` (`create topic …`) → parse → descriptor
  + `DefineTopic` → gateway parses/validates → append `__topic_schemas` →
  replicated → every node's `SchemaRegistry` updated → response.
- **Codegen:** `rune schema generate characters` → `GetTopicSchema` → descriptor
  → `rune-codec` → `characters.gen.h` in the publisher build tree.
- **Produce (validate on):** `topic.send(Characters{…})` → `Characters::encode`
  → produce → per-worker validator (registry lookup O(1)) → append or reject.
- **Restart/failover:** replay `__topic_schemas` → registry rebuilt; a promoted
  leader already has it (applied as a follower).

| `rune` CLI | rune-client-cpp (or rune-ql) | `rune query`, `rune schema apply\|get\|generate\|list` |

## 8. Schema evolution (additive-only, versioned, lossless)

- **Additive-only:** append fields (each `sinceVersion`); never remove/retype.
  Non-additive redefinition ⇒ `IncompatibleSchema`. Redefine bumps `version`.
- **Single latest descriptor — sufficient and lossless.** Every record
  self-describes its version + block length; additive changes preserve existing
  field offsets, so the latest descriptor reads/validates any older record (newer
  fields have `sinceVersion` > the record's version → read as absent/default; the
  decoder never reads past the record's block length). **No record is discarded
  or rewritten** on a schema change.
- **`openTopic<T>` compatibility:** the client sends `{version, fingerprint}`;
  the broker accepts if `T` is an additively-compatible version of the registered
  schema (not raw equality).
- Non-additive evolution + multi-descriptor coexistence: deferred.

## 9. Error handling

| Condition | Result |
|---|---|
| Malformed descriptor blob | `InvalidSchema`, define rejected |
| `keyField` missing/wrong type in descriptor | `InvalidSchema` |
| Redefine, identical schema | idempotent success (same version) |
| Redefine, additive | new `version`, latest descriptor kept |
| Redefine, non-additive | `IncompatibleSchema` |
| Redefine, different partition count | `TopicExists` (partition count immutable in 0b) |
| `openTopic<T>` fingerprint incompatible | `IncompatibleSchema` at open |
| Produce fails validation (validate on) | `SchemaValidationFailed`, no append |
| `GetTopicSchema` / open unknown topic | `UnknownTopic` |

## 10. Testing

- **0a rune-codec:** descriptor serialize↔deserialize round-trip; text form
  matches; fingerprint determinism (same descriptor → same fp; additive change →
  new fp; field reorder normalized); codec encode/decode round-trip incl.
  var-data; generic `readField` for every field kind; validator accepts
  conformant + rejects each violation class, version-aware; **benchmark**
  validation (~tens of ns; zero delta when off).
- **0b registry/transport:** `DefineTopic` round-trip; `__topic_schemas`
  persists + **rebuilds after restart** + **replicates to followers**;
  `openTopic<T>` accepts matching / rejects mismatched fingerprint; per-worker
  validation accept/reject on the produce path; `rune gen` from a mock registry
  produces a compilable header.
- **0c QL:** parse golden statements → expected API calls / plan IR; malformed
  QL errors; parse-speed benchmark; `rune ql`/`rune gen` CLI integration.

## 11. Throughput considerations

- Validation opt-in + per-worker (scales with cores); fixed-offset, no alloc.
- Registry lookup on produce is O(1) in-memory; descriptor/`readField` used
  **off the ack path** (folds/queries), never in the produce fast path except the
  cheap validator.
- Registry maintained via the existing replicated compacted-topic path — no new
  produce-hot-path work.
- The broker executes the **compact plan IR**, never parses QL text.

## 12. Open questions

- Validator implementation — precomputed descriptor table (target) vs. OTF —
  **decided by benchmark** in 0a.
- Home for `rune-codec` and Rune QL: a new `rune-codec` package + a `rune-ql`
  package, vs. folding into rune-protocol / rune-client-cpp. (Leaning: a new
  `rune-codec` package it can be a build-time tool + runtime lib; QL in the
  client/CLI.)
- `rune schema generate` output ergonomics: emit a single header vs.
  header+source; CMake helper for the codegen build step.
- Plan-IR opcode set is sketched here but finalized in the query-execution spec.
