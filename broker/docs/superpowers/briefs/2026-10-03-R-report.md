## 1. Design as built

### 1.1 Real partitionLeaderEpoch on every batch (ruling 1)
- `Log::setLeaderEpochStamp(e)` (owner thread): `appendNoSyncRestamp` (produce hot path, gateway inline produce,
  txn markers, `appendControlBatch`) patches the batch's CRC-excluded partitionLeaderEpoch [12..15] zero-copy —
  `LogSegment::appendNoSyncRestamp` pwritev with 4 iovecs (base 8 | length 4 | epoch 4 | tail); the caller's bytes are
  never mutated.  Set by the replica on `becomeLeader` / leader construction, -1 on `becomeFollower` / self-demote.
- Replica-built batches (`append`, `appendKeyed`, memory-backed `appendControlBatch`) are stamped explicitly
  (`RecordBatchReader::stampLeaderEpoch` on the reused scratch / built batch).  MetadataService records and the
  TCS / GCS keyed stores go through these.
- Followers append the leader's bytes verbatim (stamps kept; no more -1 restamping — the reconcile that did it is
  gone).  The follower epoch cache is built from the stamps: `assignEpochsFromBatches_` = Kafka
  `LeaderEpochFileCache.assign` per appended batch whose epoch is newer than the latest.  The follower no longer
  seeds its cache from the epoch it is told about (initReplica), and a frame from a NEWER epoch than the follower
  follows is dropped (no epoch adoption / truncation off a response — Kafka FENCED/UNKNOWN_LEADER_EPOCH).

### 1.2 lastFetchedEpoch + DivergingEpoch on the fetch path (ruling 2)
- Protocol (rune-protocol `schema/rune-replication.xml`, schema 112 v3, generated codecs regenerated with the
  vendored sbe-all 1.40.2): `FetchRequest.lastFetchedEpoch int32 sinceVersion=3`; `FetchResponse.divergingEpoch
  int32 + divergingEndOffset int64 sinceVersion=3` (block 34→46, before the records var-data).  Internal ring
  (`rune-internal-ring.xml`): `WorkerOp.frLastFetchedEpoch / replDivergingEpoch / replDivergingEndOffset` so the
  fields survive the control→worker ring.
- Broker codecs (`ReplicationMessages.h`): `kSchemaVersion = 3`; `FetchRequestMsg` BLOCK_LENGTH 36 / TOTAL_SIZE 44,
  `MIN_SIZE` 40 (v2) accepted, decode reads the header blockLength — a v2 frame decodes `lastFetchedEpoch = -1`
  (= no validation).  `FetchResponseMsg` decodes the v3 fields only in acting version ≥ 3 (else -1) and computes the
  records offset from the frame's OWN blockLength (v2 frames still decode); `MIN_SIZE` = the v2 empty frame.  All
  transports (Worker, Aeron, per-worker gather) carry the new fields; their length checks use MIN_SIZE.
- Follower: `nextFetch()` carries `lastFetchedEpoch()` = epoch owning LEO-1 (-1 for an empty log).
- Leader `onFetchRequest` validates EVERY fetch with `epochCache_.endOffsetForEpoch(lastFetchedEpoch)`:
  off-lineage iff `ans.epoch < lastFetchedEpoch || ans.endOffset < fetchOffset` (Kafka Partition.fetchRecords).
  Off-lineage → `kErrDivergingEpoch` answer carrying {epoch, endOffset}; nothing credited.  No epoch and ahead of
  the LEO → `kErrOutOfRange` (not credited).  Only a validated fetch sets `FollowerSlot::validated`, ackedLeo,
  ISR liveness (IsrManager), follower LEO (HW), push position.
- Follower on DivergingEpoch (`onDivergingEpoch_`, Kafka getOffsetTruncationState): if it holds divergingEpoch →
  truncate to min(divergingEndOffset, its own end of that epoch); else to its own end of the largest earlier epoch
  (another round); no epoch history at all (legacy unstamped log) → the leader's end offset.  Then re-fetch at once
  (KIP-279 loop).  A truncation below the follower's known HW is logged CRITICAL (only an upstream unclean /
  deficient election leads there — E1b) but performed, as Kafka does.
- Pushes go ONLY to validated slots (a push is applied without its own lineage check); ISR expansion only admits
  validated followers (`IsrManager::maybeExpandIsrIf`, template predicate, no std::function).

### 1.3 Completeness = ISR soundness, not data pulling (rulings 3/4)
- A leader never takes records it did not hold when elected.  `leaderComplete_` (the B1 write gate,
  `acceptsProduce()`) becomes true once a MAJORITY of the ISR assigned at becomeLeader (`completenessIsr_`, self
  counts) has proven, by a validated fetch in this leadership, that its log is a prefix of the leader's.  Every
  committed record is held by a majority of the ISR it was committed under, so such a quorum contains a holder,
  whose log is a prefix of ours ⇒ we hold every committed record.
- Quorum set = assigned ISR minus members that are SILENT in this leadership (no fetch at all) AND were shrunk out
  of the data ISR by the lag check (dead / unreachable replicas — Kafka would not have them in the ISR).  A member
  that talks but is held (diverging / ahead) always stays in the quorum.
- An incomplete leader answers an off-lineage fetch with `kErrLeaderNotComplete` (HOLD: no truncation directive,
  no credit) — a deficient leader must never make a survivor drop records that may be committed.  It never
  completes; its served HW stays at the pre-election floor; it refuses every append (produce, markers, metadata,
  keyed stores).  Liveness then needs the controller to move leadership (E1b).
- A complete leader re-elected at a higher epoch stays complete (nobody else led in between).
- Within a leadership the leader's completeness and log never change because of a follower (no reconcile).
- KIP-966 data plane: the within-leadership regression eviction (follower fetch position falls below the HW ⇒ out
  of the ISR until caught up) stays; ISR re-entry requires a validated fetch at ≥ HW.  The cross-leadership unclean
  signal needs controller-visible state → E1b.

### 1.4 Same-epoch re-assert (ruling 6)
- `becomeLeader(e)` while already Leader at e: only the ISR is applied — removals at once, additions never (they
  re-enter only via the data-plane expansion rule); no slot / completeness / floor / cache reset.
- `becomeFollower(e, L)` while already Follower of L at e: no-op.

### 1.5 METADATA path, TCS / GCS (ruling 5)
- `PartitionReplica::append/appendKeyed` refuse every append on a non-complete leader (acksAll or not).
- MetadataService: the leader edge is `acceptsProduce()` (rebuild + static emit only on a COMPLETE leader); static,
  runtime-topic and dynamic records all go through ONE ordered queue (`pendingDynamicRecords_`) drained only while
  complete; a refused append keeps the record queued (never an ignored result); a refused control tick is re-armed
  with its sequence number reused; losing leadership clears undecided records; a `logGeneration()` change rebuilds
  the MSM.  NodeRuntimeAgent keeps an eligible-set change pending (not consumed into prevElig) while the metadata
  leader is still incomplete (else the one-shot preferred pass of that change was lost — found by
  GatewayReplicationWiring.ThreeNode_FollowersConverge_HWAdvances).
- TCS: `stillLoaded_` also requires completeness + the txn-state replica's logGeneration at load time (unload →
  reload otherwise; `loadable_` already required completeness).
- GCS: the offset index is (re)built only on a COMPLETE offsets leader and re-armed whenever
  (leadershipGeneration, logGeneration) of the __consumer_offsets replica changes.

## 5. Remaining E1b items (controller side; written into docs/superpowers/backlog-2026-10-03.md E1)
(a) never elect / preferred-move to a replica lacking committed records while a clean ISR member exists — the
controller ISR only changes on a leader change; positions carry LEO but no HW (a LEO-only preferred gate would stop
preferred elections under load); a deficient leader stays incomplete (no loss, no writes) with no controller signal
to move it (needs "leader incomplete" / HW in position reports, or AlterPartition-style ISR propagation);
(b) unclean-restart signal (KIP-966 clean-shutdown marker / broker epoch) across a leadership change (M2a);
(c) DISABLED_E1b_MisElectionWithCleanHolderUnreachable_NoAckedLoss and DISABLED_Kip966_DoubleFault_* (both lose 20
acked records today: the elected survivor lacks the range and the validated fetch path truncates it on the others);
(d) RF ≥ 4 even ISR quorum overlap; commits made while the data ISR had shrunk below the assigned set (min-ISR 1).

## 6. Concerns
- Liveness: a deficient leader (controller elected / preferred-moved a replica lacking records a live ISR member
  holds) now stays unwritable until the controller moves leadership, and the controller has no signal for it
  (E1b-a).  FailoverElection picks the max-(epoch, LEO) live ISR member, so failovers mostly avoid it; preferred-
  leader moves to a lagging replicas[0] and stale/missing position reports do not.  Before, the reverse reconcile
  "healed" those cases (unsafely).
- Completeness over the ASSIGNED ISR: when every other assigned member is silent and shrunk (dead), a lone leader
  completes (as before) — safe only if the controller ISR is sound (E1b-c/d).
- A leader re-elected at a higher epoch stays complete (assumes it saw no other leadership in between).
- Pre-existing opt-in rune_transaction_integration_tests: 14 failures identical on f153662 (not fixed here).
- Mixed-version: v3 readers accept v2 frames (tested); an old-version leader receiving v3 frames ignores the new
  fields (no validation) — rolling upgrade is safe but unvalidated until all nodes run v3.
