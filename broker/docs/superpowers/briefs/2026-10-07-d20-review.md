## Durability walk-through (no regressions found)

**Append position**
- Every `.log` fd is still `O_APPEND`, at `LogSegment.cpp:52,82,146`.
- On Linux and XNU, `O_APPEND` makes `pwrite` ignore the offset and write at EOF.
- The old fstream was opened `ios::app`, which also wrote at EOF. So both before and after, bytes land at kernel EOF, and they are only correct while `st_size == logSize_`.
- Every path keeps that invariant:
  - The constructor and staging start at size 0.
  - Preallocation uses `fallocate KEEP_SIZE` or `F_PREALLOCATE`, which leave `st_size` unchanged (`:287-310`).
  - `openTrusted` sets `logSize_` from `fstat` (`:630`).
  - `recover` and `truncateInPlace` call `ftruncate(fd_)` and then set `logSize_` (`:739`, `:670`).
- The `appendNoSync` / `appendNoSyncRestamp` paths (`pwrite` / `pwritev`) now share the same fd and the same EOF. The old rule against mixing the two write paths is gone, correctly.

**Write failure handling**
- `writeAll_` (`:231-243`) retries on EINTR and on short writes.
- A zero-progress write becomes ENOSPC, and any other error keeps its errno.
- Every failure goes to `failWrite_`, which records a sticky `failedErrno` and throws. No failure is silently lost.
- A partial write followed by an error leaves torn bytes past `logSize_`. This does not matter: the log is fail-stopped, and restart `recover()` cuts the torn tail. The fstream path behaved the same way.

**Sync points**
- `sync()` and `syncForRecovery()` keep the same order: fault check, then `fsync(fd_)`, then index `msync`.
- The only code removed is the flush of the libc buffer to the page cache. With unbuffered `pwrite` that flush has nothing to do.
- No durability step ordered work behind the buffered flush:
  - `append()` = write, then `sync()`, and the flush lived inside `sync()`.
  - `truncateInPlace`'s flush only kept the cut from racing buffered bytes. Those bytes no longer exist.
  - `flushBufferedToPageCache` returns 0, which is correct because nothing is buffered.
- Side improvement: a durable append's bytes are now in the file before `logSize_` advances. Before the change, small batches sat in the libc buffer, past what the read mmap or `pread` could see, until the buffer flushed.

**Recover**
- `fstat` and a `pread` loop that handles EINTR and short reads, then `ftruncate(fd_)` on the segment's own inode instead of the path.
- This is strictly safer than the old code:
  - A failed `log_.read` used to leave the buffer zero-filled.
  - Validation then stopped at offset 0, and `resize_file` cut valid data. That was silent data loss.
  - Now the error is thrown. In `truncateTo`, callers turn it into `fatalHalt` (`Log.cpp:1902` try/catch); at startup it fails recovery.
- If the file shrinks during the read (`r==0`), the code validates the prefix it read. This is safe.
- Stale or divergent bytes beyond the valid prefix are cut exactly as before.

**Read mmap**
- It borrowed `fd_` before this change too (`MappedFile.cpp:59-67`, which never closes a borrowed fd). The fd lifetime has not changed.
- An existing mapping survives `close(fd_)`.

**FdBudget = 2**
Each segment holds exactly two long-lived fds:
- the `.log` fd;
- the writable `.index` MappedFile fd, which stays open for grow-on-demand.

Nothing else holds a long-lived fd:
- There is no time index.
- The read map borrows `fd_`.
- Staging segments from `prepareStaging` also cost 2, which `estimateFdNeed`'s `readySegmentsPerPartition * kFdsPerSegment` already counts.
- The `.index.tmp` used during recover and the directory fsync fd are opened briefly and closed again.

**Hot path**
- No new atomics.
- The durable path swaps an fstream write for one `pwrite`, which saves a `seekp` and a buffer copy.
- No new allocations on the worker.

## Findings

### Medium
**M1. No test exercises `writeAll_`'s retry or error branches (`LogSegment.cpp:231-243`).**
- `writeFaultForTest` is checked before `writeAll_` (`:328-329`), so it short-circuits the call.
- As a result, nothing exercises: a short-write resume at `logSize_+done`, the EINTR retry, the `w==0` → ENOSPC branch, or errno preservation from a real `pwrite`.
- Failure scenario: a later edit breaks the resume offset or the errno mapping, and the suite stays green.
- Fix: add a test-only seam that caps the bytes per call (for example, `writeChunkCapForTest`) and a one-shot injected EINTR or error. Then assert:
  - the whole batch is on disk, byte for byte, through `pread`;
  - an injected error ends with `failedErrno == injected` and a throw.
- Mark it `*Regression*`.

**M2. No test covers torn-tail recovery followed by a durable append.**
- `RecoverTruncatesTornTail` (`LogSegmentTest.cpp:332`) only checks the batches it kept.
- Nothing covers recover → `ftruncate(fd_)` → durable `append()` / `appendNoSyncRestamp` → read-back, which is where the new `ftruncate` and the `O_APPEND` EOF write meet.
- The case also needs a preallocated segment (KEEP_SIZE) with a torn tail, to prove the write lands at `validBytes` and not at the allocated extent.
- Failure scenario: a future change makes `ftruncate` and `logSize_` disagree. Appends would then land at EOF while the index points at `logSize_`, and reads would return the wrong batch.
- Fix: add one regression test that runs:
  1. append 2 batches;
  2. preallocate;
  3. add junk to the tail;
  4. reopen and recover;
  5. append (durable) and append (restamp);
  6. assert `st_size == sizeBytes()` and that `read` returns all batches in order.

### Low
- **L1.** `writeAll_` does not check its own invariant: it passes `logSize_` as the offset but depends on `O_APPEND` EOF. A debug-only `assert(lseek(fd_,0,SEEK_END)==logSize_)` is unsuitable for the hot path, so put the assert in the M2 test instead. This invariant existed before the change.
- **L2.** The two write paths handle short writes differently. `appendNoSync` (`:391-393`) still treats a short write as ENOSPC and fail-stops, while the durable path retries. This is conservative and not a bug, but it is worth a comment, or `appendNoSync` could also use `writeAll_`.
- **L3.** `recover()` has two error styles. It now throws `system_error` on `fstat`, `pread` and `ftruncate`, while its rename failure (`:765`) sets `failedErrno` when `storage_` is set. All current callers catch or halt, so behavior is correct.
- **L4.** `flushBufferedToPageCache()` is now a constant `0`. Consider removing it from the seal protocol in a follow-up.
- **L5 (existing before this change, outside this diff).**
  - FdBudget does not count retired segments that `M1` flush pins keep open, or transient recover fds. The margin from `kBaseFds` covers them.
  - A retired read map whose `resize()` runs after its segment is destroyed would remap a reused fd number, because the borrowed fd is already closed. The borrowing predates D20, and D20 does not change it.
