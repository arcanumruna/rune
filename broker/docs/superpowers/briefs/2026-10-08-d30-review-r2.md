# D30 re-review (round 2): sealed read-map cap + RC fail-closed on an unmappable segment

Scope: `2026-10-08-d30-diff-r2.patch`, i.e. `Log::noteSealedMapped_` / `disposeReadMap_` /
`retireSealedReadMap_` (Log.cpp:1103-1154), the `readView` / `segmentBytesAt` hooks
(Log.cpp:1058-1061, 1855-1871), `SegmentBytes::written`, the `RcState::step_` stall (RcState.h:437-447),
and the two regression tests. This was a read-only review: nothing was built or run.

**Counts:** CRITICAL 0 · MAJOR 0 · MEDIUM 3 · LOW 6

---

## 1. Are the round-1 MAJORs closed?

**MAJOR-2 (RC build skipping an unmappable segment): closed on every production path.**
`segmentBytesAt` forces `ownerRemap` on, so `mappedBytes()` returns either the whole written range
(`size == written`) or `data == nullptr`. The only way to get `nullptr` with `logSize_ > 0` is a
failed map (`LogSegment.cpp:602-606`), and that case now stalls the build. Absent segments, empty
segments and retention-deleted segments all return `written == 0` and still take the "walked" branch.
The regression test drives the real worker pass and stays red until the map recovers.
`ReadCommittedView::rebuild` is unchanged and is still exposed. It runs only when `!workerPool_`
(ClientGateway.cpp:680), and `BrokerNode::buildWorkerPool` always builds a pool, so it is reachable
only from unit rigs. That is acceptable for this change (see LOW-1).

**MAJOR-1 (lazy sealed remaps never retired): closed per Log.**
- Every sealed segment that goes from unmapped to mapped through `Log::readView` / `segmentBytesAt`
  is enqueued.
- The other ways a segment gets a map do not create untracked sealed maps:
  - the `ensureReadMap` paths (`truncateInPlace` reactivates the segment, which becomes active);
  - `openReadMap` (eager, for the active or provisioned segment only);
  - the constructor and `reloadSegments` (last segment only);
  - growth answers (active segment only, per the `maybeGrowReadMap_` early return).
  A map taken on the active segment is retired at seal by `retireSealedReadMap_`, because
  `installNextSegment` is reached only from `maybeRoll`.
- So the invariant "mapped sealed segments ⊆ FIFO entries" holds, and the count stays ≤ 8.
- Stale entries cannot break the cap. They come from retention deletes, full truncate,
  `reloadSegments` or a compaction swap that replaces the object at the same base. Such an entry
  either evicts nothing (the segment is gone, active, or has no map) or retires a re-mapped
  duplicate early.
- The ring arithmetic is correct.

What remains is not per-Log. See MEDIUM-1.

**MEDIUM-1 from round 1 (test intercept leaked every disposed map): closed.**
`asyncReadGrowth_` is exactly `channel && channel->servesReadMaps()` (Log.h:864) and is cleared on a
map failure, so intercept channels now delete inline. **MEDIUM-3 from round 1: closed** for the
counters, but they are ForTest accessors only (see LOW-4).

## 2. Is eviction safe? (Any pointer into a read map held across another read of the same Log?)

**Rule now in force:** any `readView` / `segmentBytesAt` on a Log may munmap (or post the munmap of)
a *different* sealed segment's map. That is stricter than before, when only the same segment could be
remapped. I re-audited every holder:

| Holder | Verdict |
|---|---|
| `RcState::step_` `m` | Re-fetched every step. `scanResident_` → `resident_` (mincore) and the sync `MADV_WILLNEED` run synchronously inside the step. The async hint is `submitWillNeed(fd, fileOff)` (Worker.h:4405, IoBackend.h:183), which takes no address. `feedProducerState_` / `RcBuilder` never read the log. Nothing in `Scanning` stores a pointer (only `bytePos` / `segGen` / `readAheadTo`). **Safe.** If the segment is evicted and remapped between steps, the gen is unchanged and `bytePos` stays valid. |
| `ProducerStateManager::rebuildStep` | Each view is consumed before the next `readView`. `segmentEndAt` / `nextBaseAfter` / `fenceEpoch` / `update` do not map. **Safe.** |
| `ReadCommittedView::rebuild` | Consumed per chunk. **Safe.** |
| `Log::prepareTruncationTo` (Log.cpp:1604) | Uses only `v.baseOffset`. Callers hold transport bytes, not log views. **Safe.** |
| Worker push loop (Worker.h:2531) / `readPushChunk_` (2888) | `rcServe_` (which can step the RC build, `segmentBytesAt` → eviction) runs **before** `readNoFault_` for each subscription. `pushRuns_` pointers are consumed by `encodeWorkerReturnGather` in the same call, and `deferPushRead_` stores offsets only. **Safe.** |
| `PartitionReplica::onFetchRequest` | View → ISR/HW bookkeeping (`updateIsr_` may `publishInternalIsr_`, which writes a *different* Log with its own FIFO) → synchronous send. **Safe.** |
| `pushToFollowers` | `resp` is rebuilt on every `readLog_` (only while `builtFrom` matches), so it is never used after a newer read. **Safe.** |
| `retryOwedFetchAnswers_` memo | Compares the pointer and never dereferences it. If a remap lands at the same address with the same len/LEO/installGen, it is the same sealed bytes, so the memoised offsets are still right. **Safe.** |
| `ClientGateway` inline loop (3513) | Consumed in the loop body; nothing in the body reads the log. **Safe.** |
| LogCleaner / SegmentProvisionerAgent | Never touch `readMap_`. The provisioner only deletes posted `MappedFile`s, and `swapReadMap` has already rebound their fd to -1. **Safe.** |

**Result: I found no use-after-unmap.** No caller iterates two segments while holding one segment's
bytes. Every walker (RC, PSM, RCV) is single-segment and re-fetches.

**FIFO vs LRU, and remap churn.** A segment that is still mapped never re-enters the FIFO when it is
read again. A sealed segment the RC build is crossing over many passes is therefore evicted after 8
newer lazy maps, whether or not it is in use. The next step then re-maps it: one mmap, plus one munmap
posted to the provisioner, or done inline if there is none. That costs at most one extra remap per new
lazy map, so there is no unbounded ping-pong. Thrash, where every access remaps, needs more than 8
*concurrent* mapped readers on different sealed segments of one Log. Production has no such readers:
worker push/fetch reads are pread. The mapped readers are the RC build, the PSM rebuild, oversize
fallbacks, and the scratch-less replica entry points (`AdminWorker.cpp:144`,
`AeronPartitionTransport.cpp:847`). See LOW-5.

## 3. Can the stall wedge a healthy build?

No.
- `written == logSize_`, and the stall needs `data == nullptr`, which only a failed map produces.
- **Active segment:** forced whole map, so `size == written`. Async growth cannot leave a prefix
  because `ownerRemap` is forced true.
- **Empty segment:** `written == 0`, so it is walked.
- **Compaction-rewritten segment:** the gen changes, so `bytePos` resets to 0 and `written` is the
  new size. An emptied segment has `written == 0`.
- **Retention:** the I-C clamp moves the cursor past deleted segments, so even a permanently
  unmappable segment is released once retention removes it.
- **Map smaller than written:** unreachable under forced `ownerRemap`, but the "walked" test uses
  `m.size`, not `m.written` (LOW-3).

The stall does have a real cost while it lasts. See MEDIUM-2.

## MEDIUM

### MEDIUM-1: the cap is per Log and never released when idle, so a whole-log walk on every partition leaves 8 maps per partition indefinitely
**Where:** `noteSealedMapped_` (Log.cpp:1131-1154). Entries leave only when a newer lazy map evicts
them.

**Scenario:**
- `rcAdvanceAll_` builds RC state for **every owned user partition** (Worker.h:4613-4626).
- That build also feeds the PSM (F15 S5).
- So after a restart or leadership move, every partition walks its whole log through
  `segmentBytesAt`.
- Each Log then keeps its last ≤8 sealed segments mapped until some later old-data read happens,
  usually never.

The residual is 8 × P maps on top of one `.index` map per segment (MEDIUM-5, deferred). On a
2k-partition broker that is ~16k maps, a quarter of the default `vm.max_map_count`, held for nothing.
The box gate (8p) cannot show this.

**Fix:** release the walker's maps when the walk ends, e.g. a `Log::releaseSealedMaps()` drain of
the FIFO called from `RcState::finish_` and from the PSM `Done` path. Optionally also use a smaller
cap (2-4: the mapped readers are sequential) or a node-wide budget. Test: walk a 50-segment log
through the RC rig and assert 0 sealed maps after Ready.

### MEDIUM-2: a stalled RC build retries a failing mmap, with allocations and an exception, on every pass and on the produce gate, with no backoff
**Where:** `RcState::step_` stall branch (RcState.h:437-447). It is reached from `rcAdvanceAll_`
every pass and from `rcGate_` / `rcServe_` revalidation.

**Scenario:** under the conditions the stall exists for (ENOMEM / `max_map_count`), each attempt
runs:
- `make_unique<MappedFile>`, `fstat` and a failing `mmap`;
- `throw std::runtime_error(string concat)` and the catch in `ensureReadMap`;
- the warn in `LogSegment`, plus `spdlog::error` every 1024 stalls.

That is several µs and two heap allocations per pass per stalled partition on the worker, which
breaks the zero-alloc hot-path rule. At pass rate it also produces about tens of error lines per
second.

The stall also keeps the partition `scanning()`. That defers cleaner swaps
(`cleanerSwapsDeferred_`) and pins the cleaner LSO at 0 for as long as it lasts. This is correct
fail-closed behaviour, but it should be visible.

**Fix:** give the stall the same doubling pass backoff the other waits use (`waitGap` / `oversizeGap`,
capped at 64 passes, or the `PassthroughFailed` 30 s pattern). Rate-limit the log by time, not by
count. Export `unreadableStalls()` as a metric.

### MEDIUM-3 (carried over from round-1 MEDIUM-2 (i)/(ii)): the production dispose path is untested
Both new tests use `Log(dir, 1024)` with no provisioning channel, so eviction and seal-retire only
exercise the inline `delete`. Not tested:
- the posted `kDisposeMsgType` path with a real `SegmentProvisionerAgent`. Assert
  `readMapsDisposedInlineForTest() == 0` and that the provisioner deletes them, which also covers
  LSan;
- the orphaned growth answer arriving after the seal.

The brief does not say whether the HotPathB N1-N3, PartitionReplicaTest:3192, LargeBatchServeTest and
WorkerProducePathTest targets were run with r2.

## LOW

### LOW-1: `ReadCommittedView::rebuild` still skips an unmappable segment
Only the no-WorkerPool rigs reach it (`ClientGateway.cpp:680`; `BrokerNode` always builds a pool), so
leaving it unchanged is acceptable. It is a one-line parity fix with PSM C1: when `v.empty()` and
`log->segmentNextOffsetAt(cursor) > cursor`, stop the rebuild without advancing. Better still, report
it, since `rebuild` returns `void`. That keeps the rigs from encoding the unsafe behaviour.

### LOW-2: the view contract text understates the new rule
`LogReadView.h:9-10` says "a later readView() on the *same segment* may remap". Now any `readView` or
`segmentBytesAt` on the log may unmap a *different* segment's view, and the `SegmentBytes` doc
(Log.h:588-600) does not say this at all. Reword both to "valid until the next readView /
segmentBytesAt / append / truncate on this log". The debug `viewEpoch_` assert from round-1 LOW-1
would make this enforceable.

### LOW-3: the "walked" branch checks `m.size`, not `m.written`
`s.bytePos >= m.size` with `m.size < m.written` would silently skip a tail. That is unreachable today
because `segmentBytesAt` forces a whole map, but it is the same class of bug as MAJOR-2. Make the
branch `s.bytePos >= m.written` (or assert `m.size == m.written` when `data != nullptr`) so the fail
closed property does not rest on the `ownerRemap` detail.

### LOW-4: the counters are ForTest only, and the RC test does not assert the stall path
`sealedLazyRemaps_`, `sealedMapsEvicted_`, `readMapsDisposedInline_` and `unreadableStalls_` are not
exported to metrics, which round-1 MEDIUM-3 asked for. `UnmappableSealedSegmentStallsTheBuildRegression`
asserts only `status != Ready`. Add `EXPECT_GT(rc.unreadableStalls(), 0u)` so the test cannot pass
for another reason, such as too few passes.

### LOW-5: FIFO, not LRU
A sealed segment that is still in use is evicted after 8 newer lazy maps (see §2). That is bounded
(≤1 extra remap per new map) and harmless at production reader counts. Moving a re-read entry to the
tail would need a hook on the mapped-hit path, which is not worth it now. Note it in the comment
instead.

### LOW-6: stale FIFO entries after `reloadSegments` / full truncate / compaction swap
These are harmless: they evict nothing, or retire a re-mapped duplicate early. They do use slots
until they age out. Clearing the FIFO (`mappedSealedCount_ = 0`) in `reloadSegments` and in full
truncate is trivial and keeps the counters meaningful.
