# D2 report — non-worker thread placement + node-driver idle (2026-10-04)

## Status
Implemented, tested, A/B'd. The mechanism is fixed: worker preemption is ~150x lower in thread placement and ~16x
lower in fused. **Thread-placement latency did NOT recover.** The CPU contention moved to core 0, where the three
co-located nodes' control planes now share one core.

## Commits
- rune-broker `fix/d2-thread-placement` (wt35, from integ/perf-defaults 1767c3d): **68c3a62** perf(node): D2 non-worker
  threads off the worker cores + backoff node-driver idle in shard mode
- wt26 `integ/perf-defaults`: **06756fe** docs(findings): §4.13 D2 A/B
- Not pushed. No conan create/export/upload was run.

## What changed
- `NodeConfig::nonWorkerCpus` (override: `RUNE_NONWORKER_CORES`, a cpu list). When workers are pinned, HostDefaults
  derives it as the allowed CPUs minus the worker cores:
  - Conventional layout (derived, or an explicit base equal to the derived one; the bench harness passes
    `RUNE_WORKER_CORE_BASE=1+i*W`): excludes every co-located node's worker cores.
  - Any other layout: excludes only this node's own cores, because the other nodes' cores are unknown.
  - Empty complement: affinity is left unchanged, with one warning in the startup warning line.
  - An explicit override is filtered to the allowed mask, with a warning.
  - Logged as `nonWorker=` in the effective-config line.
- `ThreadAffinity.h` adds `pinThreadToCpus`, `pinCurrentThreadToCpus`, `currentThreadCpus` and an RAII
  `ScopedThreadAffinity`. These are Linux-only (pthread_setaffinity_np); elsewhere they return ENOTSUP and do nothing.
- `BrokerNode::start` pins its own thread to the set for the whole of start(), then restores the caller's mask. Every
  thread start() creates inherits the set: the threaded node driver, the Aeron client conductor (thread placement), the
  runtime, admin, cleaner, startup pump and portable flushers. Workers re-pin to their own core on their first pass.
  `main()` pins the main thread and the signal thread after start(). This follows the A4 io-wq approach: same allowed-mask
  derivation and the same filtering of explicit lists.
- Node driver idle: an unset `RUNE_AERON_DRIVER_IDLE` now gives Aeron `backoff` in shard mode (10 spins, 20 yields, then
  park 1 us..1 ms; never busy-spin) and `sleep-ns` in legacy mode. The override still wins. Per-worker invoker drivers
  keep their previous string. Logged as `drvIdle=`.
- Thread placement was not dropped or deprecated.

## Concerns
1. **Thread latency is not fixed. The diagnosis's causal step ("worker preemption causes the latency") is refuted on
   this box.** With the workers clean, core 0 now carries 3 node drivers (~60%), 3 runtimes (~45%), admin and cleaner,
   plus a share of the unpinned client. That is more than one core. The drivers now take 21-23k involuntary switches
   per 5 s and the runtimes 8-18k (before: 0.6-3k and 2.6-6.7k).
   - Next software lever: find out why a node driver that carries only control-plane traffic still burns ~20% CPU at
     backoff, and the runtime ~15%. An FR waterfall on 68c3a62 in thread placement would localize which hop is on the
     ack path.
2. p50 and p99 come from single runs. Thread p50 went 8.7 to 13.2 ms, fused p99 went 40 to 51 ms. Both are within the
   run-to-run spread seen before (fused p99 was 17-30 ms in §4.12 and 43 ms in the diagnosis). No regression or
   improvement is claimed.
3. io-wq placement was left unchanged. With an explicit core base, A4 still leaves io-wq inheriting the worker's core
   (`ioWq=inherit` in these runs). The new "conventional explicit layout" detection could also feed the io-wq default.
   I didn't apply it, so the A/B would not be confounded.
4. The Linux pin path is proven by the box's `/proc` Cpus_allowed_list readings. The Linux-only ThreadAffinity unit test
   was not run, because the suite runs on the Mac.
5. Planka MCP failed to connect and `rune-live.sh` could not reach live.regressorspath.com, so no tickets or dashboard
   pushes were made.

## Round 2 — the control plane actually idles (2026-10-04)

### Status
Done, tested, A/B'd. Thread-placement p50 recovered: **15.1 ms -> 0.55 ms**, with the bench client pinned to core 0 in
both arms. Review mediums Md-1 and Md-3 and low L4 are fixed.

### Commits
- rune-broker `fix/d2-thread-placement` (wt35): **2013c2e** perf(node): D2 round 2 — control-plane threads park instead
  of yield-spinning (shard mode), plus review Md-1/Md-3/L4. Parent: 68c3a62.
- wt26 `integ/perf-defaults`: findings §4.13.1 and this section.
- Not pushed. No conan package operations were run.

### Diagnosis
Measured on 68c3a62, thread placement, with an idle cluster: `perf trace -s` on one broker for 5 s, plus per-thread
/proc samples.
- **Node driver thread**:
  - 88k recvmmsg calls per 5 s, of which 87k returned empty; 5k sched_yield; 2.2k nanosleep.
  - Aeron's backoff (10 spins, then 20 yields, then a park starting at 1 us that doubles) re-arms on every heartbeat
    or status message.
  - Every spin or yield pass is a whole duty cycle: one recvmmsg per socket, about 60-90 us.
- **Runtime thread**: 15k sched_yield + 17k nanosleep per 5 s.
- **Total**: idle, the control plane used about 76% of core 0, with about 2.8k involuntary switches per second on each
  driver.
- **Driver idle-shape sweep** (same binary, Aeron init args set through the environment), CPU per driver at idle:

  | Aeron backoff args | CPU per driver |
  |---|---|
  | default | 11.6% |
  | 1-0-50us-1ms | 9.5% |
  | 1-0-100us-2ms | 7% |
  | 1-0-250us-4ms | 5.5% |

  With zero yields, involuntary switches drop to about 1 per second.

### What changed (2013c2e)
- **Control-plane idle (shard mode)**: `NodeConfig::controlIdleShape` is 10 spins, 0 yields, then a park that starts at
  100 us and doubles up to `RUNE_CONTROL_IDLE_MAX_PARK_US` (default 2000 us, strict parse in [1, 1e6]).
  - Used by the runtime thread (thread placement; `RUNE_RUNTIME_IDLE=busyspin` still overrides) and the admin thread.
  - The threaded node driver gets the same shape as Aeron backoff init args, with one spin pass:
    `1-0-100000-2000000`. `RUNE_AERON_DRIVER_IDLE_ARGS` overrides it. An explicit `RUNE_AERON_DRIVER_IDLE` keeps
    Aeron's own args.
  - Legacy mode is unchanged. Nothing busy-spins.
  - Worker idle and the worker invoker drivers are untouched (A7 owns them). The cleaner is unchanged: it was already
    parking at 1 ms with no yields, about 1.4% per node.
  - Logged as `drvIdle=backoff{1-0-100000-2000000} ctlIdle=10-0-100us-2000us`. The effective-config buffer grew to
    1536 bytes, so the line is no longer truncated.
- **EmbeddedDriver**:
  - The init args are now set *before* the strategy. Aeron builds the strategy's state from the args present when the
    strategy setter runs.
  - The strategy and its args are validated first on a scratch state (`aeron_idle_strategy_load`).
  - Found while doing this: a failed Aeron idle setter leaves freed pointers behind. Before this fix, an unknown
    `RUNE_AERON_DRIVER_IDLE` aborted the process (exit 134), and the NodeConfig comment wrongly said "safe
    degradation". It is now a clean startup refusal.
- **Md-1**: `RUNE_NONWORKER_CORES` is ignored, with a warning, unless the workers are pinned (shard mode and core
  base >= 0). This node's own worker cores are dropped from the override, also with a warning.
- **Md-3**: a Linux-only test, `ShardModeRegression.NonWorkerThreadsPinnedOffTheWorkerCoresRegression`, starts a real
  shard broker and reads `/proc/self/task/*/{comm,status}`. It asserts that:
  - the worker runs on exactly its own core (read on the worker thread through the owner-thread hook)
  - every other broker thread is on the non-worker set
  - the caller's mask is restored
- **L4**: the ThreadAffinity test skips below 2 CPUs and pins to `before.back()`, which changes the mask.

### Concerns
1. **Thread p99 is still 163 ms**, against 45 ms for fused. p50 is fixed; the tail is not. An FR waterfall on 2013c2e
   would locate it.
2. **The node driver still costs about 7% per node at idle**: about 800 wakeups/s x about 85 us per duty cycle, because
   it does a recvmmsg per socket on every cycle. A7's epoll-first polling also installs on the node driver, so once A7
   merges it should cut the per-cycle cost. The cap could go higher (4 ms measured 5.5%) at the price of control-plane
   latency.
3. **Workers use more CPU at the same 20k after the fix (58% -> 92%)**. The client is no longer starved, so it stops
   sending coalesced bursts; at linger 0 that means one record per batch. This is A8's per-batch work, not a regression
   of this change.
4. **A control-plane message can now wait up to one park (2 ms)** on the runtime, the admin thread or the node driver
   in shard mode. This covers consensus, metadata, gateway Connect, group and txn coordination. Consensus timeouts are
   hundreds of ms. Group and txn round trips get at most +2 ms per hop. This is configurable with
   `RUNE_CONTROL_IDLE_MAX_PARK_US`.
5. **Single runs per arm**, as the user rule allows. The p50 change (27x) is far outside run-to-run spread; p99 is not
   claimed beyond "lower".
6. **Process slip**: an `ssh` launch was issued twice, so two A/B jobs were queued behind the lock. The duplicate was
   killed by pid before it ran. One read-only `pgrep -f` was run over ssh while checking this.
7. **Planka and the live dashboard were not updated**: the Planka MCP failed to connect this session.
