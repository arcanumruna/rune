# A9 review: ring doorbells for the shard worker (2026-10-04)

Scope: `rune-broker-wt38` perf/a9-doorbell, `git diff a3b89e1..0367963` (2b81b03 + 0367963), against the A9
report. Read-only. One scratch experiment was run outside the repo (litmus below).

## Verdict: APPROVE WITH CHANGES. 0 CRITICAL, 0 MAJOR, 4 MEDIUM, 6 LOW

The lost-wakeup protocol is correct. Each side stores its own word, runs a full `seq_cst` fence, then loads
the other side's word, on both the consumer doorbell and the space wait. The code does not rely on
acquire/release where a store-to-load order is needed. Spurious and duplicate wakeups are harmless and bounded
(at most one extra park round per stale fd write). The eventfd/pipe handling is sound: non-blocking, drained
only after a reported fire, EINTR retried, EAGAIN ignored. Every ring the shard worker consumes on a hot path
is attached. The fused runtime's attached rings are drained unconditionally every pass, so no watch can
pin a runner awake. The ADMIN_ACTION retry is correct and bounded (exactly one retry).

The findings are about gaps around the protocol: the kill switch, the missing producer-side space doorbell on
the op and session rings, costs that are always paid, and process items.

### Litmus run (confirms item 1, informs item 6)

The test's ping-pong stress was run with RingDoorbell.h copied to scratch and both fences made macros. Each
lost wakeup is a 200 ms poll timeout.

| fences | arm64 (M-series) | x86-64 TSO (Rosetta) |
|---|---|---|
| `seq_cst` (as shipped) | 0 lost / 2x300k | 0 lost / 5k |
| release (consumer) / acquire (producer) | 0 lost / 2x300k | **32 lost of 86 parks** (N=100) |
| none | 279 and 469 lost / 300k | n/a |

The shipped orderings are required, and they are sufficient. See LOW-5 for what this means for the tests.

## MEDIUM

### M-1: `RUNE_IDLE_DOORBELL=0` does not restore A7, and the doorbell costs are paid in every mode
- **Where:** `libs/node/include/rune/node/Worker.h:536-539`, which attaches the doorbells unconditionally in
  the Worker ctor. Also `Worker.h:1423`, `O2ORingBuffer.h:197/244/275/437` and `RingDoorbell.h:137/144`.
- **What happens:** the consumer doorbell, the producer (space) doorbell and the portable completion doorbell
  attach for every worker, whatever the config. That includes `RUNE_IDLE_DOORBELL=0`, `RUNE_IDLE_WAKE=0`,
  busy-spin, thread placement, and macOS, where there are no wake fds and the runner never parks on the
  doorbell. Only `attachFusedRuntimeDoorbell_` checks `config_.idleDoorbell`. As a result:
  - Every `commit()` on an op, session or completion ring pays a `seq_cst` fence (mfence / dmb ish) plus a
    load on the producer thread. Producers are the runtime and the flusher.
  - Every `ret_` read pays a `seq_cst` fence in `notifySpace_` on the runtime thread. In `controlledRead`
    that is once per COMMIT action.
  - `prepareIdle_` still runs on every empty pass. Whenever `ret_` blocks the worker it arms the space wait,
    and the runtime's next drain makes a real `write()` syscall (`ring()` is unconditional) to an fd that
    nobody polls or drains.
    - On Linux the eventfd counter just grows.
    - On macOS the pipe fills after about 8k writes, and from then on each write fails with EAGAIN.
- **Failure scenario:** someone A/Bs "doorbell off vs on" with the kill switch. Arm "off" still carries the
  fences and the space-wait syscalls under back-pressure, which is the saturation case. The comparison is
  then not A7, and the report says it is ("restores A7 exactly").
- **Fix:** attach (or arm) the doorbells only when the runner will park on them. For example, have
  `makeShardIdle`/`startShardRunners` call a `Worker::enableDoorbell()` before the runners start, and in
  `prepareIdle_` skip the space-wait arm when no doorbell is in use. Add a test that the kill switch leaves
  `hasConsumerDoorbell()==false` and that no fd write happens.

### M-2: no producer-side space doorbell on the op ring or session ring, so in fused placement the runtime waits up to the 1 ms cap after a worker frees space
- **Where:** `Worker.h:536-538`. `ingress_` and `sessionRing_` get a consumer doorbell only. `ret_` is the only
  ring with `attachProducerDoorbell`.
- **What happens:** in fused placement the producer of worker w's (w >= 1) op and session rings is the
  runtime, and the runtime runs on worker 0's thread, which now parks on the doorbell for up to 1 ms. When
  w's op ring is full, the runtime queues the op and retries "every cycle". Examples:
  - `ReplicationMetadataBridge::enqueueRoleOp_` / `flushPendingRoleOps_` (role and ownership ops);
  - `ClientGateway` `pendingSubOps_` (Subscribe);
  - gateway-routed produce;
  - `SessionAnnouncer` announces and closes on the lifecycle path.
  A failed retry does not count as work, so worker 0 parks. When worker w drains its op ring, nothing rings
  worker 0. The retry waits for some other wake source or for the 1 ms timeout. Before A9 that bound was
  200 µs.
- **Failure scenario:** 2 fused workers per node, gateway-routed (endpoint-unaware) produce. Worker 1's op
  ring fills during a burst. Worker 1 drains it in about 20 µs, but the runtime's queued ops sit for up to
  1 ms per episode. Throughput falls under sustained back-pressure, and role-op convergence is delayed by up
  to 1 ms per refusal. The multi-worker arm was not run (the report says so), so this is not covered by any
  measurement.
- **Note:** the report's design text says space wait is "symmetric", but it is implemented only for `ret_`.
- **Fix:** attach worker 0's doorbell (fused only) as the producer doorbell of every other worker's `ingress_`
  and `sessionRing_` in `attachFusedRuntimeDoorbell_`. Arm the space wait on those rings from the runtime
  side when a queue is non-empty after the retry, then re-check by retrying the claim. Or prove the queues
  cold and say so in the report.

### M-3: the flake's failure mode changed in arm B, and the cause was not found
- **Where:** report §Concerns, `ShardModeRegression.SlowEndpointUnawareClientCannotStarveTheShard`.
- **What happens:** A fails with a possible lost ack (`awaitProduceResponse` false). B fails differently: the
  gateway pause did not engage within 40k frames. The report offers a hypothesis, that the ADMIN_ACTION retry
  removed spurious "Held" signals, and marks it "not proven".
- **Why it matters:** B changes how the test fails, and A suggests a real lost ack. Both are open. The
  hard rules (you-find-it-you-fix-it, repro-before-fix) say not to ship a red/flaky test with an unproven
  cause. The changed failure mode could also be M-2 (gateway-routed ops waiting on the cap) rather than the
  ADMIN_ACTION retry.
- **Fix:** root-cause both failure modes with instrumentation: Held/Released signal counts, op-ring-full
  refusals and park wakes per episode. Fix what is found and make the test deterministic.

### M-4: the shipped default (0367963) was measured once per scenario, not interleaved
- **Where:** report A/B table, column B-hyb.
- **What happens:** the default that actually ships has one idle run and one 20k run, both taken through env
  on the 2b81b03 binary and neither interleaved with A. Its headline numbers rest on n=1: 20k p99 of 9.5 ms
  (against A's 19.8-22 ms) and p50 of 356 µs. The p99 "improvement" in particular is a single sample.
- **Fix:** run an interleaved ABAB of A against 0367963 (default config) at idle and at 20k before quoting
  these numbers in findings §4.15. Saturation should be included too, because the spin/yield phase and the
  1 ms park interact differently there.

## LOW

### L-1: the fused worker 0 rings itself through its own `ret_` space wait
- **Where:** `Worker.h:1423` together with `ShardAgent.h` (the runtime runs after `worker_.doWork`).
- **What happens:** worker 0's `prepareIdle_` arms `ret_.armSpaceWait()`. The fused runtime drains worker 0's
  `ret_` later in the same pass, and `notifySpace_` then `write()`s worker 0's own eventfd. The next park
  returns at once and drains it. The cost is one `write`, one wasted `ppoll` and one `read` per back-pressure
  episode on worker 0.
- **Fix:** skip attaching worker 0's `ret_` producer doorbell in fused placement, because its producer and
  consumer are the same thread.

### L-2: false sharing on the space-wait word
- **Where:** `O2ORingBuffer.h:448-449`.
- **What happens:** `alignas(64) m_spaceWanted` is followed on the same cache line by `m_capacity`,
  `m_maxMsgLength`, `m_headPositionIndex` and the other index fields, which both threads read on every
  claim and read. Each arm, disarm or exchange invalidates that line on the other core. This only happens
  during back-pressure episodes, which is exactly when the ring is hot.
- **Fix:** pad `m_spaceWanted` to its own line (`alignas(64)` on the next member, or a trailing pad).

### L-3: the cleaner swap, retention and staging rings and the signal ring are not attached
- **Where:** worker cold tail (`drainCleanerSwaps`, `drainRetentionDeletes`, `drainStagingRenamesDone`);
  runtime `cleanerChannel_` acks; `SignalControl`.
- **What happens:** all are cold and bounded by the 1 ms cap, as the report says. The one wall-time effect
  that should be written down: retirement of replicas (`collectRetired`) and compaction swaps now wait up to
  1 ms for a cleaner ack on an idle node instead of 200 µs. This is acceptable. The report should list the
  worker-side cleaner rings, not only the view-ack and signal rings.

### L-4: cycle-counted backoffs stretch about 5x in wall time
- **Where:** `ClientGateway.cpp:2872/3408` (`pushCycle_` notReady backoff of 1..1024 push cycles). The same
  pattern applies to any "retry every cycle" counter.
- **What happens:** on an idle fused node a cycle can now be 1 ms apart (it was 200 µs). A gateway-pushed
  read_committed subscription that reached the 1024-cycle backoff now re-issues after about 1 s instead of
  about 0.2 s. This is bounded and only applies to a back-pressure fallback.
- **Fix:** note it in the findings, or cap the backoff by wall time.

### L-5: what the tests prove about the fences depends on the platform
- **Where:** `RingDoorbellTest.cpp` (6-interleavings test and stress tests).
- **What happens:** the deterministic interleaving tests run the steps sequentially, so they cannot detect a
  weakened fence. The litmus above shows:
  - The ping-pong stress does catch a fence weakened to release/acquire on x86 (32/86 parks lost), so the
    Linux CI run guards the protocol.
  - On arm64 macOS it does not: clang lowers a release fence to `dmb ish`, and the weakened variant passes
    600k iterations.
  - Removing the fences entirely is caught on both platforms.
- **Fix:** none required. Add a comment that the stress test guards the fences only on x86 Linux, and that
  this is the platform that must run it. The report's "fails on the broken variants" list does not include
  a fence-weakening variant.

### L-6: formally outside the C++ fence rules; correct in practice
- **Where:** `RingDoorbell.h:119-142`, `O2ORingBuffer.h:437-443`.
- **What happens:** the Dekker pairs order a std::atomic (`parking_` / `m_spaceWanted`) against a non-atomic
  volatile ring word (record length via `putInt32Ordered`/`getInt32Volatile`, head via `putInt64Ordered`).
  [atomics.fences] only gives the fence-fence guarantee between atomic objects, so formally this is the same
  data race the whole Aeron ring already relies on. In practice the `seq_cst` fence is a full hardware and
  compiler barrier on x86 and arm64, and the litmus confirms it. No change needed. This is noted because the
  review brief asked about it.
- **Related (opt-in 0/0 shape only):** `ClientGateway::doWork` does not add `drainWorkerReturns_()` (line 417)
  to its work count. With `RUNE_IDLE_SPINS=0`, egress frames claimed in a pass that reports 0 work wait for
  the next driver duty cycle, which is up to the 1 ms park. The default shape (10 spins) hides this. Count
  the drained returns as work before 0/0 is ever recommended. It may explain part of B's +109 µs p50.

## Checked and clean
1. **Protocol.**
   - Consumer: store, `seq_cst` fence, check committed (length > 0). Producer: release-store the length,
     `seq_cst` fence, load. The space wait is the mirror image: store want, fence, re-claim against
     a head store, fence, load.
   - The exchange dedupe stays correct with multiple producers. A second producer that reads 0 from the first
     producer's exchange is ordered before the consumer's next arm fence, so that arm sees its record.
   - Padding written by a refused claim (INSUFFICIENT_CAPACITY with padding) cannot strand a parked consumer.
     That path needs head index < required, so committed records sit at head.
   - `abort()` is used only on halt paths.
2. **Ring coverage.**
   - Attached: op ring (gated, gate equal to `drainIngress_`'s two early returns and refreshed on the pass
     before every park), session ring (drained in full), portable completions (always drained, inFlight_
     decremented), and `ret_` space.
   - Fused worker 0 also watches other workers' `ret_` (gateway `drainAllReturns`, unconditional every
     cycle) and the 3 admin rings (`serviceAdminControl_`, unconditional, limit 16/8/16, work counted).
   - io_uring uses its fd.
   - All are O2O single-producer. The MPSC `IngressRing`s (consensus, `AeronPartitionTransport::outboundRing_`)
     are produced and consumed on the runtime thread in shard mode.
   - Attach happens before `startShardRunners` and the admin runner start. Shutdown joins the admin thread
     before `workerPool_.reset()`, so there is no doorbell use-after-free.
3. **ADMIN_ACTION.** One immediate retry at every worker-path `tryClaim`/`offer`. A second ADMIN_ACTION
   cannot follow for a claim of at most `maxPayloadLength`. `ClientGateway`, `AeronPartitionTransport` and
   the consensus sinks fall back to `offer()`.
4. **Deadlines under 1 ms.** None found.
   - Aeron C defaults in the conan build: NAK unicast delay 60 ms, retransmit delay 0, SM timeout 200 ms,
     timer 1 s. Rune does not override them.
   - Rune timers: fetch 5 ms (node) / 50 ms (replica), ISR 10 ms, follower flush 20 ms, sync 10 ms,
     slow tick 10 ms, hello retry 10 ms, ack timeout 30 s.
5. **Hard rules.**
   - 17 allowlist entries, all RING, all inside ring internals (RingDoorbell.h, O2ORingBuffer.h).
   - Nothing on the hot path allocates, uses `std::function` or makes a virtual call. `describeShardIdle`'s
     `dynamic_cast` and strings are cold.
   - No busy-spin. A doorbell skip happens only when a watched ring holds committed work that the next pass
     consumes.
   - macOS: no wake fds, so production keeps the legacy backoff and the doorbell is used only in tests (pipe);
     see M-1 for the costs that are still paid.
6. **Tests.** The stress tests use 5 s poll timeouts and yields, never sleep. The ParkedRunner test uses a
   2 s park.
