## Design decisions

### 1. Aborted / open txn data never supersedes committed values
* **New `TxnCleanState`** (`libs/storage/include/rune/storage/TxnCleanState.h`), owned by both `OffsetMap` and
  `SkimpyOffsetMap` (next to `ProducerTails`, cleared with them), filled by a **pre-pass** at the start of
  `buildOffsetMapFromBases` (both overloads). The pre-pass walks every batch of every listed segment from log
  start up to `toOffset` (<= HW for the agent path; markers at/after it are untrusted because they can still be
  truncated) and tracks, per producer: the open txn's first offset + batch count, ABORT ranges
  `[firstTxnBatch, abortMarker]`, and markers whose txn has no batch left.
  Marker type comes from the 2-byte LE int16 record key (0 = COMMIT, 1 = ABORT). An unparseable key counts as
  COMMIT, so data is never thrown away because of a marker the cleaner can't read.
* **LSO cap, from the log itself (backstop).** `cleanLimit = min(toOffset, first offset of the earliest
  unresolved txn)`. The map never indexes at or after it. Every rewrite boundary (`rewriteSegmentImpl`,
  `mergeGroupWithMap`, `compact()`) and every `passEnd` (range / file / group paths) is clamped to it, so the
  watermark never crosses an open txn.
* **LSO cap, published by the worker (Kafka parity, agent level).** The owning worker publishes the first
  unstable offset to `PartitionReplica::publishCleanerLso()`. This is a cleaner-visible snapshot,
  release/acquire, the same mechanism as `cleanerHighWatermark()`. The value comes from
  `RcState::cleanerFirstUnstableOffset()`:
  * Ready: `LsoTracker::lso(INT64_MAX)`.
  * Not Ready: 0, so nothing is cleaned while the RC state rebuilds.

  The worker publishes only when the value changes, at three points: the per-pass RC driver
  (`rcAdvanceAll_`), right after `onTxnBatch`, and right after `onMarker`. `LogCleanerAgent` uses
  `firstUncleanable = min(activeBase, hw, cleanerLastStableOffset())`. The default `kNoCleanerLso` (INT64_MAX)
  means not tracked, for example a partition with no RcState; the log-derived cap still applies there.
  * Shared-nothing law: there are 3 new atomic sites, allowlisted as **CLEANER** (the user-law exception for
    the log-cleaner channel) in `scripts/atomics_allowlist.txt`. `check_no_atomics.py` is OK.
* **Aborted batches are discarded:** they are skipped by the map build. In the rewrite they are dropped whole
  (when below the boundary). If one was the producer's last batch, it keeps only its metadata as the C2
  record-less transactional batch (Kafka `RETAIN_EMPTY`) — this is item 1(c).
* **Range-path pass end:** when the map did not fill, `passEnd = limit` (previously last keyed offset + 1).
  The early return when the map is empty now also requires `!txn.hasWork()`, so aborted data and removable
  markers in a range with no keyed records still get processed.
* The pre-pass also took over the producer-tail noting, so prefix segments are no longer read separately for
  tails. Its bytes are reported through `lastPrefixBytesRead()` and throttled the same way as before (M3).

### 2. Marker removal (KIP-534)
* A marker can be removed when two things hold: no batch of its transaction (data or record-less tail) is
  left in the scanned log, and it is **not its producer's last batch**. That second rule is a deliberate Rune
  addition. Rune rebuilds producer state from the log rather than from snapshots, so the producer's last
  marker carries its fenced epoch; it is kept the same way as the C2 data tail.
* The first rewrite pass that finds a removable marker stamps it: it sets `kAttrDeleteHorizon`, writes
  `baseTimestamp = nowMs + deleteRetentionMs`, and re-seals the CRC. The 75-byte layout and CRC coverage stay
  the same, so `ControlMarker::isControlBatch/extract` still accept it. A later pass with `nowMs >= horizon`
  drops it. With `nowMs < 0` (the legacy path) markers are kept.
* `LogCleaner::clean()` and `compact()` gained an optional `nowMs` (default -1) so the sync path can use the
  horizon too.
* Segments that contain only markers are deleted by the existing "emptied segment" path once their markers
  are dropped.

### 3. Marker-key isolation
* Covered by a dedicated test. The control-batch skip in the offset-map build (f9911b9) is what makes it pass.

## Concerns / follow-ups
* **I/O cost:** the pre-pass reads every sealed segment below the limit once more per pass. Clean-prefix
  segments cost the same as before, because the separate producer-tail read is gone. Dirty segments are now
  read 3x instead of 2x. This is background work and throttled; a Kafka-style `.txnindex` would remove the
  extra read.
* **Re-selection churn:** if an open txn is known only from the log (no LSO published, or inside the
  publish/HW-order window), a log with `minCleanableDirtyRatio` of about 0 can be re-selected each cycle
  without progress until the txn resolves. In worker mode the published LSO caps `firstUncleanable`, so this
  does not happen there.
* **Publish ordering:** the worker publishes HW (inside `onLeaderLogAppended`) before it publishes the LSO
  (after `onTxnBatch`). The log-derived cap covers that window.
* **Legacy duty-cycle compaction** (`NodeRuntimeAgent::runBoundedCompaction`, test-only) advances its
  watermark per segment and does not respect the LSO. The data stays safe because the rewrite and the map are
  capped, but a txn that commits late below its watermark is not deduplicated there.
* **Unresolved txn behind a marker above HW:** a txn whose marker sits above HW, or in the active segment
  above `toOffset`, keeps capping the pass until that marker is sealed and below HW. Kafka can clean such
  data earlier because it has the aborted-txn index.
* **Producer's last marker** is kept indefinitely (like the C2 tail, but with no expiry, because markers carry
  `maxTimestamp` 0). At most one marker per producer per partition.

# Fix round 1 (commit **c060eac**, on top of b11e34e; not pushed)

## New finding: production markers were misparsed (HIGH)
Writing the tests with the real marker bytes (`ControlMarker::build`) exposed a bug in b11e34e. That marker's
single record has **no record-length varint**. b11e34e read it through `RecordBatchReader::forEachRecord`,
which takes the attributes byte as the length, so **every production ABORT looked like a COMMIT**. Aborted
data was therefore still indexed and kept, which is the original bug again. The round-0 tests missed it
because they built markers with `RecordBatchBuilder::setControl`, which uses Kafka record framing.

Fix: `isAbortMarker` recognises the fixed 75-byte ControlMarker layout first (record attributes, tsDelta,
offDelta = 0; keyLen = 0x04; valLen = 0x0C) and falls back to the Kafka-framed walk. The storage tests now use
the production bytes by default, and `BothMarkerEncodingsAreParsed` covers both layouts.

## 1. Marker removal gated on every assigned replica (MED)
* `PartitionReplica::replicaFetchPos_` sits next to `configuredReplicas_`. It is updated on every fetch and
  epoch probe, and **reset to 0 on `becomeLeader`**, because a position learned in an earlier term may
  predate a truncation.
* `publishCleanerState()` publishes `cleanerMarkerRemovalBound()`:
  * leader: min(fetch position) over all assigned replicas other than self; a replica that never fetched
    counts as 0;
  * single-replica partition: `kNoCleanerLso`;
  * follower: 0.

  The new snapshot is CLEANER-category in the allowlist.
* The agent calls `LogCleaner::setMarkerRemovalBound(...)`. The default is **0, so no marker is ever removed**
  unless a caller proves every replica holds it. `TxnCleanState::finish(toOffset, bound)` makes a marker
  removable only when `offset < bound`. Stamping is gated as well, so the delete horizon starts only once
  every replica has the marker.
* A permanently dead assigned replica keeps every marker. This is intended: correctness over growth.

## 2. Rebuild invariant (LOW-MED)
* `publishedLsoForCleaner_` starts at **0 for topicId >= 0**, which are exactly the partitions a Worker builds
  an RcState for. It starts at `kNoCleanerLso` for internal topics. The invariant is documented at
  `publishCleanerLso`.
* `Worker::rcAdvance_` revalidates and publishes 0 **before** any rebuild step, then publishes the real value
  after the step. This covers the inline produce gate `rcGate_`. `rcServe_` publishes on a serve-time reset.
* `Worker::cleanerSwapsDeferred_`: while the RC state is **Scanning**, cleaner swaps are not drained, on both
  drain sites (legacy and shard). The scan walks the mapped pre-swap segments and sees one consistent log
  version; the swaps are applied once the state is Ready. A cleaner pass already in flight therefore cannot
  land mid-rebuild, and the LSO stays 0 during the rebuild, so no new pass starts.
* Worker-less test rigs (CompactionCleanerAgentTest, CompactionStressTest) now publish `kNoCleanerLso`
  explicitly. They have no RcState, so without this they would correctly clean nothing.

## 3. hasWork / bounded paths (LOW)
* `hasWork(nowMs)` counts only aborted batches that **still hold records**, plus removable markers the pass
  would stamp (no horizon yet) or drop (horizon reached).
* `produceCleanedFileBounded` and `produceCleanedGroupBounded` no longer early-return on an empty map when
  there is txn work. Their `passEnd` follows the range path (the limit unless the map filled).
* `LogCleaner::lastRewriteSegmentsRead()` exposes the rewrite-phase segment reads for the test.

## Concerns (fix round 1)
* **Unreproduced failure:** the PerWorkerReplication Failed + SegFault from the first full run did not
  reproduce in 1 full rerun and 8 targeted repeats, and I have no stack trace. The code this round touches
  does run in that path: the Worker swap deferral, the rcAdvance_/rcServe_ publishes, and
  `replicaFetchPos_`. I reviewed those for out-of-bounds or null access and found nothing. Add it to the D8
  watch list and capture output on the next occurrence.
* **Bound learned from fetches, not lineage:** the marker-removal bound trusts fetch offsets. A divergent
  follower reporting a fetch offset above a marker it doesn't hold on the leader's lineage could let a marker
  go before its reconcile truncates it. Kafka has no such gate at all; this matches the existing HW trust
  model.
* **Rebuild-length stall:** swap deferral and LSO 0 pause compaction for the length of an RC rebuild on that
  partition. That is cold: once per leadership or truncation.
* **Worker-less rigs:** they must now publish `kNoCleanerLso` to compact user topics. In production every user
  partition has a Worker RcState, so this only affects test rigs.
