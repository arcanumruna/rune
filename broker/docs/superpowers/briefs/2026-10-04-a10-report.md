# A10 group commit — report (2026-10-04)

**Status:** group commit is implemented and tested on `perf/a10-group-commit` (worktree rune-broker-wt41).
It does NOT fix the 20k periodic-fsync collapse. The A/B shows the collapse is bimodal and does not follow disk
load, so the §4.16 root cause ("disk IOPS saturated") is wrong. Details: findings §4.16.1 (wt26 134d04e).

## Commits
- wt41 `0e0c5ce` perf(node): A10 group commit — one durability round per worker
- wt41 `d049b21` fix(node): A10 — submit Strict roll seals before the round batch opens
- wt26 `134d04e` docs(perf): findings §4.16.1

## Design
- `Worker::submitRound_` runs at the end of every pass, in both placements. The worker's single `SyncRound` state
  is Idle or InFlight{outstanding, startNs}. Strict waiters (Durable members), follower flush requests, re-requests
  and the periodic sync (`LogFlushSlot::roundWanted`) are queued with `IoBackend::queueFlush` and submitted with ONE
  `submitQueued()`. On io_uring that is one `io_uring_enter`; on portable it is one batch to the flusher thread.
  The next round starts only after every member of the previous one has completed.
- When the periodic sync is on, a round that starts after half its interval covers every dirty log and restarts
  the interval. Leader and follower timers therefore merge into one round.
- Semantics are unchanged: each member is a real fdatasync of its log's active segment. On success it marks the log
  durable up to the LEO sampled at round start (durableLeo/bgLeo → lastSyncedLeo). A Strict ack fires only after the
  round that covers it; a Strict append that arrives during a round joins the next one. An error is fail-stop
  (failLog_). A refused Strict member gets an Internal answer; a refused background member stays wanted for the
  next round. Nothing syncs on the worker loop and nothing allocates (roundMembers_ is reserved).
- Compatible with E1d: R can advance only on a member's durable completion covering the segment (per-log
  completions, as before). Seals stay separate and are submitted before the batch opens.
- (a) syncfs and (c) two-phase (sync_file_range + fdatasync) were measured and rejected. syncfs needs about 2x the
  write IOs and, on a shared filesystem, flushes every other node's files. The two-phase round adds IOs.
- Portable/macOS: the flusher thread runs the round's fdatasyncs one after another.

## A/B headline (20k, 3-node acks=all 1 KiB, MTU 1408 + GSO; A = integ, B = A10)
- 5 ms: A r1 = 19,999 rps, p50 1.75 s / p99 10.1 s, 27% busy / 1,851 IOPS. A r2 = 20,004 rps, p50 1.9 ms /
  p99 43 ms, 99% busy / 6,816 IOPS. B r1 = 20,000 rps, p50 1.74 s / p99 10.0 s, 23% busy / 1,624 IOPS.
  B r2 invalid (harness raced the previous broker's exit). Extra B diag run: p50 2.06 s / p99 10.0 s.
- 50 ms: A r1 = 7,406 rps, p50 11.6 s / p99 20 s, 33% / 519 IOPS. B r1 = 17,472 rps, p50 2.6 ms / p99 9.9 s,
  35% / 549 IOPS. B r2 = 20,003 rps, p50 1.55 s / p99 10 s, 25% / 506 IOPS. A r2 invalid (harness).
  Extra B diag run: 20,002 rps, p50 3.6 ms / p99 120 ms.
- fsync off: unchanged. A p50 354/406 µs, p99 37/36 ms; B p50 416/383 µs, p99 42/45 ms; all 20,000 rps.
- Collapsed runs had low disk load, and the only healthy 5 ms run had 99% busy. In the collapsed diag run, node 1
  marked its peers out of the ISR at age 10,003 ms and the client sessions expired. The shard loop sat in jbd2
  journal waits (pwrite) in about 3-5% of samples.

## Tests
- New RED-first `*Regression*` tests. GroupCommitRegression ×5: the round covers every dirty log (shard and
  thread placement), the Strict ack waits for its covering round, a failed round is fail-stop, and a round is one
  backend batch with no inline sync. UringDurabilityTest ×3: one enter per queued round, the cap is respected, a
  single submit during an open batch is refused. PortableFlushBackendRegression ×1: syncs run on the flusher only.
- ShardNonBlocking: 3 tests were adapted because a re-request is now served by the next round.
- Mac full suite (build-fast): 3,519/3,519 passed before the seal fix; the 133 durability/Strict/seal tests passed
  after it.
- Linux k3s-node-01 (Release, io_uring): uring 10, group-commit rounds 5 (default and RUNE_IO_BACKEND=uring),
  shard non-blocking 97, async durability 8, node 327, all green.
- check_no_atomics OK (the allowlist gained the new SQ-tail sites, RING category).

## Concerns
- A10 does not solve the collapse. The real cause is a roughly 10 s stall/lease path when periodic fsync is on;
  the ISR-out and the session expiry point at it. Instrument it next.
- The A/B is weak: n = 1–2 per arm, a bimodal outcome and 2 invalid runs. tp.sh's "ABORT: rune_broker running"
  needs a wait-for-exit.
- Behaviour change: a Strict append now waits for the in-flight round (on any log) before its own fsync. That adds
  up to one round of latency at low load in exchange for batching.
- Merge with E1d (wt32) needs a check of R-advance against round members (a design-compatible, per-log completion).
- VM time: probes ~8 min + A/B ~16 min + diag ~3 min (builds excluded). /root/a10ab and /root/a10p deleted;
  13 GB free.
