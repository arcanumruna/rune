# D30 review — retire the sealed segment's read mapping at roll

Scope: uncommitted `libs/storage` diff (`2026-10-08-d30-diff.patch`): `Log::retireSealedReadMap_`
(Log.cpp:1100-1117), its call in `Log::maybeRoll` (Log.cpp:331), counter in Log.h, regression test
`SegmentLifecycleHotpathRegression.SealedSegmentsKeepNoReadMapRegression`
(SegmentLifecycleHotpathTest.cpp:1149). Read-only review; nothing was built or run.

**Counts:** CRITICAL 0 · MAJOR 2 · MEDIUM 5 · LOW 5

---

## Question 1: use-after-unmap audit (result: none found)

Pre-D30, a disk view was invalidated in practice only by a later `readView` on the same log. That
call can swap a grown map in `pollReadMaps_` or `resize` the map in `ensureReadMap`. The
"valid until the next append" clause of `LogReadView.h:7-10` did nothing for disk logs, because
sealed maps lived until the segment was deleted. **D30 now relies on that clause**: an append
that rolls munmaps the old active map, asynchronously and possibly at once. I checked every
holder of a disk view or raw map pointer:

| Path | Thread | Held across an append to the same log? |
|---|---|---|
| `Worker::readNoFault_` fallback (Worker.h:3010), in-worker push loop (2531) and `readPushChunk_` (2888) | owner | No. Consumed into the return ring inside the loop; ingress appends run elsewhere in the pass |
| `PartitionReplica::onFetchRequest` view (PR.cpp:909 → 1027) | owner | No. Between read and send only ISR/HW bookkeeping (`updateIsr_`) runs, and nothing appends. `sendFetchResponse` copies synchronously (WorkerReplicationTransport tryClaim/encode) |
| `pushToFollowers` (PR.cpp:3313+) | owner | No. The view is shared across the follower loop, with sends only |
| `retryOwedFetchAnswers_` memo (`builtView` pointer, PR.cpp:1078-1101) | owner | The view is re-taken each attempt. The memo compares pointers only, never dereferences a stale one, and a roll always changes the LEO, so `builtLeo` forces a rebuild even if the remap reuses the address |
| `ClientGateway` inline path (ClientGateway.cpp:3513) | gateway (non-shard). The same thread appends (inline produce) | No. Consumed in the sub loop. Appends to other logs (offsets/txn) do not touch this log's maps |
| `ReadCommittedView::rebuild` (RCV.cpp:355), `ProducerStateManager::rebuildStep` (PSM.cpp:589), `Log::prepareTruncationTo` (Log.cpp:1566) | owner | No. Each view is consumed before the next read; nothing appends |
| `RcState::step_` → `segmentBytesAt` (RcState.h:434) | owner | No. Re-fetched every step. The async hint goes by `fd`+offset (`submitWillNeed`, Worker.h:4407), not by address; the sync `MADV_WILLNEED` is synchronous |
| Cleaner / compaction (LogCleaner.cpp) | cleaner | Never touches `readMap_` (no `readView`/`mappedBytes`/`readMap` use) |
| NodeRuntimeAgent / BrokerNode | control | No `readView` callers |

`swapReadMap` rebinds the retired map's borrowed fd to -1 (LogSegment.cpp:199-201), so the
asynchronous `delete` never closes a reused fd number. The new path uses the same off-owner
dispose as the grown-map retire in `pollReadMaps_` and relies on the same kind of invariant,
except that the trigger is an append instead of a `readView`. → LOW-1 asks for this to be made
explicit or guarded.

## MAJOR

### MAJOR-1: lazy remaps of sealed segments are never retired, so mapped walks bring back 2 maps per segment
**Where:** `LogSegment::ensureReadMap` (LogSegment.cpp:560-599) keeps every lazy map for the life
of the segment. D30 retires a map only once, at seal (Log.cpp:331).

**Scenario:** Any path that walks old data through the mapping maps each sealed segment it
touches, and that map stays until retention deletes the segment:
- RC build: `RcState::step_` → `Log::segmentBytesAt` → `mappedBytes()`, with ownerRemap forced
  on (Log.cpp:1817-1830)
- `ReadCommittedView::rebuild` and `ProducerStateManager::rebuildStep`, which are full-log walks
  through `readView`
- follower catch-up through `PartitionReplica::readLog_` whenever no `ReplReadScope` is set
  (`readScratch_ == nullptr` → `readView`, PR.cpp:3310)
- every non-shard gateway consumer (ClientGateway.cpp:3513), including a tailing consumer just
  behind a roll: one owner mmap per roll, then kept
- `readNoFault_` / `readLog_` oversize fallbacks

On the box scenario (~32k segments), one RC build or PSM rebuild after a restart, or one catch-up
follower without scratch, raises the map count back to about 2 per segment and hits the same
`vm.max_map_count` wall: `bad_alloc` on the next roll's `.index` mmap. D30 fixes only the
"runtime-sealed and never re-read" case. Before D30, sealed segments after a restart were already
lazy (F3); D30 brings runtime-sealed segments to that state, but nothing bounds the re-growth.

**Fix (pick one):**
- (a) Keep a small per-Log cap of lazily mapped sealed segments (an intrusive LRU, e.g. K=4-8).
  When a sealed segment has to be mapped and the cap is full, retire the oldest through the same
  dispose post. The `LogReadView` contract ("never hold a view across another readView") already
  allows this, provided the eviction happens inside `Log::readView`/`segmentBytesAt` before the
  new view is returned.
- (b) Convert the remaining mapped walkers to `readInto`/pread (RC scan via `segmentBytesAt` and
  the RCView/PSM rebuilds; give non-worker replica callers a scratch) and retire after use.

Either way, add a regression test: walk 200 sealed segments via `readView` and assert at most K
are mapped.

### MAJOR-2: a failed sealed-segment map makes the RC build silently skip the segment
**Where:** `RcState::step_` (RcState.h:436, `if (m.data == nullptr || ...)` → "walked, next
segment") and `ReadCommittedView::rebuild` (ReadCommittedView.cpp:356, `v.empty()` → treated as
a compaction gap, skip to the next base).

**Scenario:** Before D30, runtime-sealed segments kept their maps, so an RC scan of them never
needed an mmap that could fail. After D30, every RC build over runtime-sealed segments must mmap
each one. With MAJOR-1 that can exhaust `max_map_count`; ENOMEM can also come from address-space
or cgroup limits. `ensureReadMap` then returns empty. The builder skips the whole segment:
abort markers and transactional batches in it are never classified, the aborted index misses
those aborts, and read_committed consumers receive **aborted records**. This is a correctness
failure, and the only sign is a rate-limited `readMapFailures` warning.
`ProducerStateManager::rebuildStep` already guards this exact case: "Re-review C1: an empty view
BELOW the segment's written end ... fail the proof" (PSM.cpp:591-593).

**Fix:** In `step_`, treat `m.data == nullptr && segment size > 0` as "retry next pass", counted
and stalling at the LSO, never as "walked". Fail-closed after N tries the same way as
`haltInvariant_`/C1. Better still, read the RC scan through pread so it needs no map at all
(see MAJOR-1 b). Give `ReadCommittedView::rebuild` the same check as PSM C1
(`segmentEndAt > cursor` → fail). This is pre-existing, but D30 makes it reachable on every
runtime-sealed segment, so it belongs with this change. Add a regression test that injects a
map fault (`setReadMapFaultForTest`) into a sealed segment holding an abort marker and asserts
the build stalls instead of completing.

## MEDIUM

### MEDIUM-1: test intercept channels leak every retired map
`retireSealedReadMap_` (Log.cpp:1112-1116) posts whenever `provisionChannel_ != nullptr`. With
`DemandChannelForTest` (testing/DemandChannelForTest.h:19-21), `tramp_` returns **true** for any
non-demand type, so `m.release()` runs and the `MappedFile` (heap object + mapping) leaks on every
roll. Affected: LargeBatchServeTest, WorkerProducePathTest, and SegmentLifecycleHotpathTest users
of it. LSan fails under ASan, and long tests rebuild the map-count problem in-process. The header
itself says "Growth / dispose posts are not used (servesReadMaps() is false while intercepted)",
and the growth path honours that through `asyncReadGrowth_`.
**Fix:** post only when `provisionChannel_->servesReadMaps()` (or `asyncReadGrowth_`); otherwise
`delete` inline.

### MEDIUM-2: the regression test covers only the legacy inline-munmap branch
`SealedSegmentsKeepNoReadMapRegression` uses `Log(d, 1024)` with no provisioning channel, so it
exercises only the `provisionChannel_ == nullptr` inline delete. Not covered:
- (i) the posted dispose with a real `SegmentProvisionerAgent` (worker-driven, deferred seal)
- (ii) the orphaning branch: a growth request outstanding for the segment that seals, whose
  answer arrives after the seal and must not be installed into the sealed segment (`find(growBase_)`
  must fail)
- (iii) that a lazily remapped sealed segment stays mapped. A second `readView` must not remap;
  assert the segment's `readMapRemaps()` stays at 1.

Also, the brief only states that the storage suite passes. Run the affected node and replication
targets: HotPathBRegression N1-N3 (HotPathBRegressionTest.cpp:1068-1120), PartitionReplicaTest:3192
(asserts sealed is unmapped), LargeBatchServeTest, and WorkerProducePathTest (MEDIUM-1).

### MEDIUM-3: owner-side sealed remaps and the inline munmap fallback are uncounted
A lazy remap of a sealed segment is an mmap syscall on a worker that takes mmap_lock for write,
the exact #65 stall class. It appears in no Log-level counter:
- `ownerFallbackRemaps_` is not bumped, because `beyond` requires `readMapBytes() != 0`
  (Log.cpp:1056).
- `activeReadMapRemapsForTest` covers the active segment only (Log.h:249-251).
- The ring-full inline `delete` in `retireSealedReadMap_` (a worker munmap inside the append
  path) is also uncounted.

**Fix:** add `sealedLazyRemaps_` (bumped in `Log::readView`/`segmentBytesAt` when the target is
sealed and `readMapBytes()==0`) and `sealRetireInline_`, and export both. Without them, MAJOR-1
regressions and hot-path cost are invisible. This follows the rule that hot-path briefs state a
µs budget and require a measured before/after.

### MEDIUM-4: the provisioner still builds an eager whole-segment read map per segment, which is now mmap+munmap churn per roll
`LogSegment::create` → `openReadMap(readMapBytes)` (LogSegment.cpp:97) maps every provisioned
segment, and D30 unmaps it at seal. Worker reads are pread (#65/D26), so the map is usually
never touched. Each roll now adds an mmap_lock-write munmap on the provisioner; before D30,
munmap happened only at retention delete. Under #65 that lock was shown to queue worker faults
(index pages, fallbacks) for about 1 ms.
**Fix:** for worker-driven logs, skip the eager read map (`readMapBytes = 0`, lazy, as for
recovered sealed segments). The few fallback/RC readers map on demand within the MAJOR-1 cap.
Measure SegmentRoll/8p p99 before and after (D30 alone and with this change).

### MEDIUM-5: the .index mapping stays at 1 map per sealed segment; a lazy sealed index is recommended
After D30 the ceiling only moves from about 32k to about 65k segments per broker (minus other
maps). Each sealed segment also still holds a `.log` fd (and an index fd if `MappedFile` keeps
one), which counts against RLIMIT_NOFILE. A small `segment.bytes` or many partitions reach it
again: 8p × 8k segments. Kafka solved this with `LazyIndex` (KAFKA-7283): indices are mmapped
only on first lookup and closed again for inactive segments.
**Recommendation (backlog, worth doing):** at seal, `msync`/trim the index and unmap it.
`readInto`'s `index_->lookup` on a sealed segment then does a pread-based binary search over
the index file (≤ `indexMaxBytes`, about 2-3 preads of 4 KiB each), or maps lazily under the
same bounded LRU as MAJOR-1(a). That brings sealed segments to 0 maps, bounded by K. Pair it
with an fd LRU if the fd count also matters.

## LOW

### LOW-1: the append clause of the view contract is now load-bearing for disk views
`LogReadView.h:7-10` already says "valid until the next append/truncate", but nothing enforces
it, and the audit above relies on reading the code.
**Fix:** expand the comment to say a roll munmaps the old active map asynchronously. Consider a
debug-only per-Log `viewEpoch_`, bumped on retire, swap or truncate, that callers stamp and
`assert` in debug/TSan builds.

### LOW-2: an orphaned growth answer lingers and blocks growth
Log.cpp:1108 keeps `growOutstanding_ = true`. `pollReadMaps_` runs only inside `Log::readView`,
so on a pread-only log the orphaned answer (a full-segment mapping) stays in `mapRing_` until
some `readView` happens, and the half-full growth check in `maybeRoll` (`!growOutstanding_`) is
blocked for the new active segment. The orphan is disposed without being counted in
`readMapsDiscarded_`. A `kMapFailedMsg` for the orphan still disables async growth for the whole
log (Log.cpp:1121-1126).
**Fix:** on orphan, set `growOutstanding_ = false` instead of moving `growBase_`. The seq rule
then discards the answer as superseded and counts it, and a failure with a stale seq is ignored.
Optionally poll `mapRing_` once per roll. (Rarely hit in practice: provisioned segments already
carry a whole-segment map, so `maybeGrowReadMap_` seldom posts.)

### LOW-3: the ring-full inline munmap runs on the worker's append path
Log.cpp:1112-1116. It happens only when the 64 KiB M2O ring is full, i.e. a stuck provisioner,
which coincides with forced rolls. It is acceptable but should be counted (MEDIUM-3).

### LOW-4: disposes are dropped at shutdown
Retire posts still queued in the provisioner ring when it stops are not deleted. That leaks the
mappings, harmless at process exit. The volume is now one per roll instead of one per growth.
Check that the provisioner drains `kDisposeMsgType` on stop, as `Log::~Log` drains `mapRing_`.

### LOW-5: the lazy remap size is rounded to a power of two
`ensureReadMap` doubles from 1 MiB, so a 64 MiB+ε sealed segment maps 128 MiB of virtual space
(one VMA, so the map count is unaffected). Use `readMapBytesFor(logSize)`-style page rounding for
sealed segments.

## Answers to the brief's questions
1. **Use-after-unmap:** none found (see table). Every holder consumes its view before the next
   append or readView on the same log, cross-thread readers of read maps do not exist, and
   read-ahead hints use fd+offset.
2. **Lazy remap:** a remapped sealed map is kept (`ensureReadMap` steady state, no repeated
   syscall). `ownerRemap_ == false` with `readMap_ == null` is correct: both early returns need
   `readMap_` non-null, so the segment maps whole on the owner. But the maps are never retired
   (MAJOR-1), the remaps are uncounted (MEDIUM-3), and non-shard tailing consumers pay one owner
   mmap per roll.
3. **Orphaning:** correct. `find(INT64_MIN)` fails, so the answer is never installed into the
   sealed segment. A later legitimate request gets a new seq, so the orphan is never mistaken for
   it. Not leaked: it is disposed on arrival, only late (LOW-2) and uncounted.
4. **Other seal/roll paths:** forced and legacy rolls both go through `maybeRoll` (legacy:
   inline munmap, acceptable). In-place truncation remaps the reactivated sealed segment on the
   owner (cold), which keeps a whole-segment map; a map failure falls back to a rebuild. Full
   truncate, rebuild truncate, `reloadSegments` and the constructor map only the last segment;
   compaction prebuilt segments have no read map. No assertion or test expects a sealed map;
   PartitionReplicaTest:3192 asserts the opposite.
5. **Index:** still 1 map per sealed segment. A lazy or closed sealed index is worth doing
   (MEDIUM-5).
