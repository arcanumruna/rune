## Correctness analysis (no findings, recorded for the record)

### 1. Triple-buffer protocol (Log.h:627-633, Log.cpp:402-407)

- **Index invariant.** `{snapBack_, snapFront_, snapMiddle_ & 3}` starts as `{0, 2, 1}`, a permutation of {0,1,2}. The owner's exchange swaps back and middle. The cleaner's exchange swaps front and middle. Each exchange is one atomic RMW, so no index is lost or duplicated and the permutation holds forever. The owner only writes `snapSlot_[snapBack_]` and the cleaner only reads `snapSlot_[snapFront_]`, so they never touch the same slot concurrently.
- **Fresh-bit encoding.** Indices 0..2 fit in the mask `kSnapIndex=3`, and `kSnapFresh=4` is a separate bit. The cleaner deposits `snapFront_` with no fresh bit, which correctly marks the middle as "already seen". The owner always deposits `back|4`. No ABA problem is possible: there is no CAS, only unconditional exchanges, and the fresh bit is set only by the owner and cleared only by the cleaner.
- **Owner to cleaner ordering.**
  1. The owner writes the header and chunk entries in `publishSnapshotView_`, then the slot assignment, then a release exchange.
  2. The cleaner's acq_rel exchange reads that value, or a later one. Every modification of `snapMiddle_` is an RMW, so the release sequence extends through it and the cleaner synchronizes with every earlier owner publish.
- **Cleaner to owner ordering (slot reuse).** The cleaner copies `snapSlot_[snapFront_]` in call N. That is sequenced before its release exchange in call N+1, which hands the slot back. The owner gets the slot with an acquire exchange before it overwrites it. So the overwrite (and the refcount decrement) happens after the cleaner's copy.
- **The relaxed pre-check is safe.**
  - A stale "not fresh" read just returns the previously acquired front.
  - A "fresh" read is followed by the acq_rel exchange, which does the synchronizing.
  - Staleness relative to other channels is bounded by read-coherence. If the cleaner learns, through another ring, of anything the owner did after a publish, that publish's exchange happens-before the relaxed load. The load must then see that value, or a later one in modification order. A later value can only be the owner's own fresh write or a cleaner take that already consumed it.
- **Initial state.** All three slots alias the same empty `make_shared<SealedSegmentSnapshot>()`. Middle is 1 and not fresh, so before any publish the cleaner gets a non-null empty snapshot, as with the old code. `recover()` then publishes with the fresh bit set. The cleaner thread is started, or receives the replica over its view ring, after that, so it is synchronized.
- **Destructor thread.**
  - Control-block refcounts are atomic, so dropping a slot value on either thread is safe.
  - The aliased `SealedSnapshotDir` destructor is pure memory: it frees `unique_ptr<shared_ptr<Chunk>[]>`, `unique_ptr<SealedSegmentSnapshot[]>` and the chunk refcount decrements. It touches no owner state, no fds and no rings, so it is safe on the cleaner thread (when the cleaner's local copy is the last ref) and on the owner thread (slot overwrite or `ownerSnap_` reassignment).
  - This is the same exposure as the old `atomic_store`, which also dropped the old value on the owner. Nothing reads `use_count()`, so the extra slot refs change no behavior.
- **Persistent-chunk invariant** ("published snapshots never cover slots ≥ snapEnd_"). This is unaffected. The slots only hold already-published snapshots, the same kind of thing a cleaner-held copy always was.

### 3. Liveness

The fresh bit is sticky until the cleaner takes it. If the owner publishes once and stops, the cleaner gets that snapshot on its next `cleanerSnapshot()`, and read-coherence ensures the relaxed load eventually sees the bit. Every take returns the latest publish made before the exchange. The cleaner can never lag by more than "publishes since its last call", so it cannot miss the latest snapshot forever. The test's final `fin == owner` assertion covers this.

### 4. Remaining shared_ptr atomic free functions

I swept the whole repo (libs, src, tests, bench, benchmark, dr-e2e) for `atomic_{load,store,exchange,compare_exchange}*`, in qualified and unqualified forms, and for `atomic<shared_ptr>`. The only remaining instance is `RoutingImageHolder` (libs/metadata/include/rune/metadata/RoutingImage.h:228 `atomic_store_explicit` and :240 `atomic_load_explicit`). It is already allowlisted as UNSCOPED ("convert to a ring-delivered image") and has the same hidden libstdc++ mutex-pool problem on every `current()` call. The ClientGateway comments (ClientGateway.h:1633, .cpp:2023/2036) show its readers capture the image once per cycle, which limits the damage but does not remove the lock. Nothing else was found.

## MEDIUM

### M1. The owner-only and single-consumer contracts are now load-bearing but unenforced, and the accessor name gives no hint
- **Where:** Log.h:619 (`sealedSegmentSnapshot()`) and Log.h:627 (`cleanerSnapshot()`).
- **Failure scenario:**
  - Before D22, `sealedSegmentSnapshot()` was safe from any thread. It keeps its name, signature and `const noexcept`, but now returns a plain copy of `ownerSnap_`. Any future off-owner caller (a metrics/admin/describe-log path on the gateway or control thread, or a test that reads it while a Worker runner thread appends) is a silent data race on a shared_ptr, which can tear the control-block pointer and corrupt the refcount, causing a use-after-free.
  - Likewise, a second concurrent `cleanerSnapshot()` consumer (for example a future second cleaner, a per-shard cleaner, or a diagnostic call from the control thread) would race on the plain `snapFront_` and could take a slot the other consumer is still copying.
  - Nothing catches either mistake. TSan only does so if a test happens to exercise it.
- **Fix (cheap):**
  - Rename to `ownerSealedSnapshot()`, so the old name disappears and every off-owner use must be reconsidered. About 60 test call sites would change, mechanically.
  - Or keep the name and add a debug-only (`#ifndef NDEBUG`) thread-identity check. Record the first caller's `std::this_thread::get_id()` in plain members (owner side: set in `publishSnapshotView_`; consumer side: set on first `cleanerSnapshot()`), and assert later calls match. Provide a `rebindCleanerConsumerForTest()` for join-then-reuse tests such as RetentionCleanerAgentTest.cpp:858 and the new test's line 1139.

## LOW

### L1. Stale comments still describe the atomic_store/atomic_load design
- Log.h:1129-1138: "via std::atomic_store / std::atomic_load … libc++ spinlock … per-pointer-address". This block now sits directly above `ownerSnap_` and the triple buffer, and contradicts them.
- LogCleanerAgent.h:11 ("atomic shared_ptr published by the append thread"), :184 ("atomic shared_ptr"), :336 ("atomic acquire").
- Log.cpp:1258 says "returns nullptr" (pre-existing, also wrong: it is an empty snapshot).
- **Fix:** replace them with one sentence pointing at the D22 triple buffer.

### L2. False sharing in the triple-buffer layout
- **Where:** Log.h:1145-1148.
- `alignas(64)` puts `snapMiddle_` at the start of a line. `snapBack_` (owner-written on every publish) and `snapFront_` (cleaner-written on every take) then pack into that same line, followed by the owner's `snapDir_` and `snapBegin_/snapEnd_/snapHeadersUsed_`. `snapSlot_[3]` (read by the cleaner on every call) shares the preceding line with `ownerSnap_` (owner-written on every publish).
- The cost is per roll, not per append, so the impact is negligible today. It is still the opposite of the intent of `alignas`.
- **Fix:** put `snapFront_` on its own cache line next to `snapMiddle_`, or after it with padding, and keep the owner fields (`snapBack_`, `ownerSnap_`, `snapDir_`…) on a different line from what the cleaner reads.

### L3. Bounded extra retention of stale snapshot directories
- The two non-front slots hold the latest and the previous publish. The front slot pins the cleaner's last take until its next fresh take, indefinitely if the cleaner is idle or detached from this Log.
- So up to two stale `SealedSnapshotDir`s are kept alive, along with any chunks they alone reference. Such chunks are copy-on-write leftovers from truncation, compaction or reload. Each pinned directory costs about 4 KiB plus O(chunks) pointers.
- The amount is bounded and the slots are released at `~Log`. No fix is needed; a one-line comment noting the bound would help.

### L4. Owner-side cost of `ownerSnap_`
- **Where:** Log.cpp:402-404.
- Every publish now does about 3 refcount RMWs on the directory's control block (aliasing ctor, `ownerSnap_` assignment, slot assignment) plus the exchange. That is still cheaper than the old mutex-pool `atomic_store`.
- `ownerSnap_` exists only for `sealedSegmentSnapshot()`, which has no production caller. An alternative is to keep a raw `const SealedSegmentSnapshot*` (header pointer) on the owner and build the aliasing shared_ptr lazily in the owner accessor. That is optional and per roll only.

### L5. The regression test's mid-run check can pass vacuously
- **Where:** SegmentLifecycleHotpathTest.cpp:1116-1142.
- `seen > 0` is satisfied by the initial empty snapshot alone. The mid-run monotonic check (`size() < last`) is the only cross-thread property checked, and it does not prove that the cleaner received any intermediate publish.
- **Fix:** also count distinct `s.get()` values the cleaner observed and `EXPECT_GT(distinct, 1u)`. Optionally yield in the owner loop so the cleaner gets airtime.
- The final `fin == owner` assertion and TSan cover the essentials.

### L6. RoutingImageHolder still uses the mutex-backed shared_ptr atomics
- **Where:** RoutingImage.h:228/240.
- This is outside the D22 scope and already allowlisted as UNSCOPED, so it is listed only for completeness, as the one remaining instance of the same hidden-lock pattern.
- **Fix:** convert it the same way: per-reader latest-value triple buffer or ring-delivered image, as its allowlist note says.
