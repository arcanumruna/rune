## Measurements before tuning (A = base 770a9ba / ff60185)
- 20k rec/s: workers 74-86% each, client 75-82%, system idle 0-1%, sys ~47%. Per worker only 24-160 sched_yield/s and
  6-24 clock_nanosleep/s, but ~175k recvmmsg/s + ~28k epoll_wait/s.
- A7DIAG (instrumented pass, 20k): >95% of passes do work. That is ~8-10k passes/s, each with ~4 driver duty cycles,
  costing driver ~70-80 us + worker ~25 us + runtime ~3 us per pass. Idle cluster: ~4.5k passes/s, ~15% of them with
  work, driver ~35 us per pass with nothing to do.
- perf (system-wide, 20k): the top entries are syscall_enter_from_user_mode + __recvmmsg, then copies, pwrite and ext4.
  The cost is spread thinly over many functions.
- Idle cluster: 39% per worker. The yields (4.3k/s) and nanosleeps (2.8k/s) are re-armed by heartbeats.

## Root cause
- **20k:** the CPU is NOT idle spinning or yielding. Passes always find work. With linger 0 every record is its own
  batch, and each batch costs ~30 us of CPU per node. At saturation the same work costs ~6 us per record because it
  is batched. On top of that, Aeron recvmmsg-s every transport on every duty cycle while a poller holds 5 transports
  or fewer, so most of those syscalls come back empty. The idle strategy has almost no idle time to save here.
- **Idle cluster:** this one is real idle-strategy waste. The Aeron backoff counts passes, and each "spin" is a full
  syscall-heavy pass costing ~35 us.

## Changes
1. **Park-until-work (from the WIP, kept).** A shard worker that finds no work parks in ppoll() on its invoker
   driver's receiver/sender poller epoll fds. The derived shape is 0 spins and 0 yields, with a park that doubles from
   1 us up to idleMaxParkUs. That cap stays because work arriving on rings or timers does not wake an fd.
   - Config: `RUNE_IDLE_WAKE=0` restores the legacy backoff.
   - `RUNE_IDLE_SPINS` / `RUNE_IDLE_YIELDS` override the shape.
   - The resolved idle is logged per worker.
2. **Epoll-first transport polling (new).** A poller with more than one transport now does one epoll_wait(0), then
   recvmmsg only on the ready sockets. This is Aeron's own path above the threshold, installed through the bindings
   `poller_poll_func` hook.
   - It patches rune_gso's own bindings in place. Without GSO it patches a private copy of the stock bindings, never
     Aeron's process-wide struct.
   - Config: `RUNE_AERON_EPOLL_POLL=0` (broker) or `RUNE_CLIENT_AERON_EPOLL_POLL=0` (client) restores the stock
     poller. The driver startup line logs `poll=epoll-first|stock`.
   - Effect: per-worker recvmmsg went from ~175k/s to ~30k/s.
3. **Client invoker bench (from the WIP, kept).** An idle pass parks on the wake fds until the next scheduled send, a
   datagram, or 200 us, whichever comes first. `RUNE_BENCH_IDLE=spin` restores the old loop.
4. Tried and dropped: a 20 us batch-window sleep after each pass that did work. Worker CPU went from 75% to 65%, but
   p50 went from 510 us to 1,057 us. Removed.
5. Tests: removed the sleeps from the WIP tests (tests never sleep). Added a config parse test, an installed/active
   test, and a real-driver multi-transport delivery test (gso on and off).

## Concerns
- The 20k goal ("large CPU drop") is not met, and cannot be met through idle tuning. What would move it: less
  per-batch work at linger 0 (batching, fewer syscalls per replicated batch, the pass composition in §4.6).
- 20k p99/p999 is very noisy on the full box in both arms (17-30 ms). B's r1 p99 is worse; r2 is equal.
- Saturation is -2% on the mean, which is inside A's own 4% spread between rounds. Not proven neutral at n=2.
- The remaining idle CPU (~23% per worker) comes from the 200 us park cap, which is kept because ring and timer work
  has no fd. Going lower needs a wakeup fd (eventfd) on cross-thread rings, which is a design change.
- Epoll-first reaches into Aeron's internal poller struct, the same way rune_gso already does. It needs a re-check on
  any Aeron upgrade.
- DriverWakeFds.c is duplicated in the broker and the client, just as the WIP already duplicated the wake-fd code.
- The WIP's WorkerPool uses `dynamic_cast` and a virtual idle. That is startup/per-pass only, the same pattern as
  before.
