## Changes per item

### B1: CRC only after Aeron accepts the frame (no `canOffer`)
- New `producer/ProduceFrameBuilder.h` replaces `rune::protocol::RecordBatchBuilder` as the Tier-1 partition accumulator.
  - It builds the Produce **wire frame in place**: each record is written once, at append.
  - `seal()` writes only the Produce header and the RecordBatch header (~110 B) and leaves the CRC at 0.
  - Its output is byte-identical to `Produce::encode` + `RecordBatchBuilder::build`. A randomized conformance test covers this.
- New `transport/FrameCrc.h` with `FrameCrc{crcAt, from}`. `AeronTransport::offer/offerOn/offer(stream)` take an optional `FrameCrc`. The CRC is computed only after Aeron accepts the frame:
  - **Frame of one MTU payload or less:** after a successful `tryClaim`. The CRC is computed over the source and written into the source, then the frame is copied into the claim and committed.
  - **Multi-MTU frame:** inside the `offer()` reserved-value supplier. Aeron calls it after its `position < limit` check and after copying the first fragment, before that fragment commits. The supplier computes the CRC over the full source frame and patches both the term buffer and the source buffer. The CRC field is always in the first fragment, since the header is about 110 B. A defensive fallback is there anyway.
  - A refused offer computes nothing.
- The supplier is a `std::function`, because Aeron's C++ API (`on_reserved_value_supplier_t`) requires one. It is built **once** in the `AeronTransport` constructor; the transport is immovable. Aeron's default `offer()` already goes through a `std::function` (`DEFAULT_RESERVED_VALUE_SUPPLIER`), so this adds no new kind of cost.
- Plumbing: `ClientAgent::offerToPartition`/`offerProduceToLeader_` and `AgentProduceSink` gained a `FrameCrc` overload. `CountingSink` gained a `FrameCrc` overload that seals only on accept, so benches model the transport. Generic sinks (the `std::function` SendFn test/cold seams) get a frame that is sealed before the offer, as before.
- Under back-pressure, a refused offer costs one header re-seal, with no record copy and no CRC. Records keep joining the held batch.

### B2: incremental CRC patch
- New `detail/Crc32cPatch.h`. It uses CRC32C linearity: the new CRC is the old CRC XOR `raw(delta)·x^(8·trailing) mod P`. This is the zlib `multmodp`/`x2nmodp` operator, O(log n), with no rescan.
- `restampBatchIdentity()` re-stamps producerId, epoch and baseSequence (14 contiguous bytes) and patches the CRC. It is used by:
  - the Tier-2 stamp, including every back-pressured retry (a zero delta leaves the CRC unchanged);
  - `resequence_`, the retransmit re-sequencing.

### B3: 3-way interleaved CRC32C (implemented, because CRC was still hot)
- After B1+B2, CRC was still the largest single cost of the duty thread's per-batch produce work. Per 64 KiB batch:

  | Value size | CRC time | Total per batch | CRC share |
  |---|---|---|---|
  | 256 B | 6.0 µs | 23.4 µs | 26% |
  | 1 KiB | 6.0 µs | 12.4 µs | 48% |
  | 4 KiB | 6.0 µs | 9.9 µs | 61% |

- New `detail/Crc32cFast.h`:
  - Three independent hardware chains per 3·B block (B = 8 KiB, then 512 B), combined using raw-CRC linearity.
  - The fixed x^(8B) and x^(16B) shifts are 4-lookup tables built once at static init. No PCLMUL is needed, and the same code runs on x86 SSE4.2 and ARMv8.
  - Bit-exact with `rune::protocol::crc32c`. Also verified natively on arm64 with a standalone build.
- `FrameCrc` sealing uses it.
- **Follow-up outside this repo:** move it into rune-protocol so the broker's batch validation benefits too. I left rune-protocol untouched because of the worktree-only rule.

### B4: no extra full-frame copy
- **Tier-1:** an accepted acked frame becomes the retained retransmit frame through an O(1) `vector::swap` (`swapFrameInto`). The builder takes the slot's old buffer.
- **Tier-2 acked:** encoded straight into the in-flight slot it will claim (new `InFlightRing::peekNext()`; `canFlight_` guarantees the slot is free).
- `keepFrame` is gone. The old path copied the records three times (builder, encode scratch, retained frame); now they are copied once.
- The steady-state no-allocation test (`ProducerAllocRegressionTest`) still passes.

### B5: client default MTU 1408
- The library defaults were already 1408 and are regression-guarded by `ClientConfigMapping.MtuAndSocketBuffersMapToTransportRegression` and `TransportConfig.DefaultsAreValidAndMtuIsAeronDefaultRegression`.
- The bench tools still defaulted to jumbo 8192. These now default to 1408, with 8192 opt-in:
  - `rune_produce_throughput` (`RUNE_BENCH_MTU`)
  - InvokerBench `--mtu`
- The ShardConfig guidance comment is updated.
- The `BenchArgs` test was changed first and went RED (8192 != 1408) before the fix.

### B6: 16 KiB maximum record size
- `Producer::kMaxRecordBytes = 16 KiB`, measured as key bytes + value bytes. Records over the limit are rejected:

  | Path | Result |
  |---|---|
  | Ring `trySend` | `SendResult::MessageTooLarge` (non-retriable) |
  | Direct (Invoker) append | `SendResult::MessageTooLarge` / `RejectReason::MessageTooLarge` |
  | void `send()` | throws `std::length_error` |
  | Tier-2 `BatchBuilder::add` | throws `std::length_error` |
  | `TransactionalProducer::send` | throws `std::length_error` |

- The check is one O(1) compare at append; no per-record scan was added anywhere else.
- `kMaxSendValueBytes` was 8154, based on a stale "8 KiB stack scratch" rationale. It is now the largest value allowed with any key: `kMaxRecordBytes - Key::kMaxInline` = 16368.
- `ValueTooLarge` now only means "can never fit this (tiny) producer ring".
- The Direct deferral arena is sized for a 16 KiB record.
- **API change:** callers that expected `ValueTooLarge` for oversized values now get `MessageTooLarge`. Three existing tests were updated for this.

## Concerns
1. Aeron's `offer()` supplier is a `std::function`, which Aeron's C++ API requires. It is constructed once rather than per call, and is invoked once per fragment of a multi-MTU frame. This is the same mechanism Aeron's own default `offer()` already uses.
2. B6 changes the API: `MessageTooLarge` is a new `SendResult` value, and `kMaxSendValueBytes` grew from 8154 to 16368. Downstream code that switches on `SendResult` or relies on `ValueTooLarge` for size errors needs a look.
3. The B3 numbers come from x86 under Rosetta and from native arm64. Real x86 hardware (single chain ~2.7 B/cycle) should show a similar or larger gain; the VM ABAB will confirm.
