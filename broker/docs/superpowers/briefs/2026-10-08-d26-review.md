# D26 review: replication reads use pread into a worker scratch

Scope: uncommitted diff on `integ/perf-defaults` (wt26), `docs/superpowers/briefs/2026-10-08-d26-diff.patch`.
Read-only review. Nothing was built or run.

**Verdict: no CRITICAL or MAJOR findings.** The change is correct for every caller that gets a scratch. The remaining findings are about test fidelity and coverage, one fault source that is still there, and a few hardening items.

Counts: CRITICAL 0 · MAJOR 0 · MEDIUM 3 · LOW 7

---

## What was verified (no finding)

1. **Lifetime and aliasing.**
   - `onFetchRequest` (PartitionReplica.cpp:911 to 1035): one `readLog_` call, then only ISR, HW and DUR-1 bookkeeping, then `sendFetchAnswer_`. `updateIsr_`/`changeIsr_` never read the log, so nothing can overwrite the scratch between the read and the send.
   - `retryOwedFetchAnswers_` (:1068): each slot re-reads, walks and sends before moving to the next slot.
   - `pushToFollowers` (:3312): the `builtFrom` memo holds only the most recent read. When a follower has a different cursor the code re-reads and rebuilds `pre` and `resp` together. A follower whose cursor matches the memo again (A, B, A) also re-reads, because `from != builtFrom`. A stale `resp` is never sent.
   - Every transport copies synchronously during `sendFetchResponse`:
     - `WorkerReplicationTransportImpl::sendFetchResponseImpl_` encodes into a claim.
     - `AeronPartitionTransport::enqueueFetchResponse` encodes into the outbound-ring slot before `commit`.
   - No span into the scratch outlives the call.
   - `pushScratch_` (client push reads, `serveHeldPushReads_`) and `replScratch_` are separate buffers that are never used together. No replica call re-enters the Worker, so scopes never nest.
2. **Ownership and threads.**
   - Every scoped site runs on the owning worker. `executeFetchRequestWire_` gets its op through `tryEnqueueOp(topic, partition)`, which routes to the router worker.
   - `pollReplTransportDispatch_` uses `findOwnedReplica_`.
   - The doWork loops iterate `owned_`.
   - `executeAppendControlRecordWire_` already touches the replica (`epoch()` and other calls) before the scope.
   - WorkerPool's F7 invariant says no production path moves a replica between workers.
   - Internal partitions (`topicId < 0`) stay on the control thread and are never routed to a worker (AeronPartitionTransport.cpp:819).
   - Exceptions are handled: the scope is constructed outside the `try`, so the destructor clears the scratch on every path.
3. **Owed memo** (FollowerSlots.h:72-79, PartitionReplica.cpp:1096). The memo is still sound with a constant pointer:
   - `fetchOffset` and `maxBytes` are fixed for one owed entry, and a new entry resets the memo through the aggregate defaults (`builtLeo = -1`).
   - Every segment install bumps `segInstallGen_`: roll and `install_` (Log.cpp:1706), reload (:2083) and compaction swap (:2307).
   - A leader's log is append-only within a leadership. Truncation happens only on a follower, and every role change, including the self-demotion in `onFetchRequest`, runs `followerSlots_.resetLeadership()`, which clears `owed`.
   - Retention can only remove the segment that holds `fetchOffset`. Both `readView` and `readInto` then return empty, which leads to `continue`.
   - With the same LEO, `installGen`, offset and len, `readInto` is deterministic: `remaining`, `want` and `got` all match. So the bytes and the prefix match.
   - Switching between the mapped fallback and the scratch, or moving between workers, changes the pointer and forces a rebuild, which is harmless.
4. **`readInto` against `readView`** (LogSegment.cpp:614 and :690).
   - Whole-batch semantics hold, including "first batch always whole, even above maxBytes".
   - The KIP-74/F18 check `view.len > maxBytes` is preserved:
     - A first batch that is larger than maxBytes but fits the buffer is returned whole (`fill(end)`).
     - A first batch larger than the buffer gives `firstTooLarge`, then `readView`, then the same check.
   - For a read at or after LEO, callers guard with `< LEO`.
   - Below `logStart`, `upper_bound` returns `begin()` and the result is empty in both functions.
   - Neither function crosses a segment boundary (no change).
   - A torn tail gives an empty view in both: `total <= 0`, or `end > remaining` with `firstTooLarge = false`.
   - `fd_` is always open for the segment's lifetime (it throws on open failure and is closed only in the destructor), so `fd_ < 0` cannot produce a silent empty view.
   - After a compaction rename-over, reads still come from the old inode through `fd_` until the reload. That matches the mapping.
5. **Concurrent append.** Confirmed: nothing appends while a read is in progress.
   - Appends run on the same owning thread, and `pwrite`/`pwritev` complete before `logSize_ +=` (LogSegment.cpp:358, :431, :512).
   - `pread` is bounded by `logSize_`.
   - The cleaner writes only staging files, and the provisioner only builds the next segments and maps.
6. **Hot-path rules.**
   - No allocation: the scratch is allocated once, at Worker construction.
   - No virtual calls: `readLog_` takes one branch on `memoryBacked_` and the scratch, and calls the concrete `Log::readInto`.
   - No atomics. The scope costs two stores per call.
7. **The RED-first test does exercise the worker fetch serve.**
   - `Rig(withFollower)` sets ISR {1,2}.
   - The fetch at 0 travels `tryEnqueueOp`, then `executeFetchRequestWire_`, then `onFetchRequest` with `serve = Data` (slot 2 is new, `lastFetchedEpoch = -1` so no lineage validation, offset < LEO).
   - Without the fix, `readView` raises `readViewCallsForTest`, so the test fails. With the fix the count is unchanged and `fetchDataServes` increases by 1.

## MEDIUM

### M1. `readInto` still faults through the `.index` mmap (the "never faulting" claim is too strong)
- **Where:** LogSegment.cpp:622 (`index_->lookup(startOffset)`), OffsetIndex.cpp:8 and :58. The `.index` is a `MappedFile`, prefaulted only when the provisioner builds the segment (`prefaultIndex`). These are created with `prefaultIndex=false`:
  - segments recovered at startup (Log.cpp:169)
  - segments loaded by `reloadSegments` (:2077)
  - cleaner-installed groups
- **Failure scenario:** after a broker restart, or after compaction installs a group, a follower catches up from old sealed segments. Each first fetch into a cold segment binary-searches pages of an untouched index mapping. That is a first-touch fault, which takes `mmap_lock` (read) and queues behind the provisioner or cleaner's `mmap`/`munmap`. This is the same D-state stall D26 fixes, now on catch-up after restart or compaction. The new gate scenario does not catch it, because its segments are all provisioner-built and therefore prefaulted. #65 has the same gap.
- **Fix (pick one):**
  - Prefault the index off the owner when a segment is installed or reloaded. The provisioner already has the `prefaultIndex` machinery; post the installed segment to it.
  - Keep the sparse index in an owner-private heap array; it is a few KiB per segment.
  - At minimum, narrow the comments and the D26 claim to "log bytes never fault", and add a gate variant that fetches from a recovered or compacted segment.

### M2. Gate scenario `Fetch+Retention/2p`: mixed clocks, and nothing proves the fetches served data
- **Where:** DutyPassLatencyGateTest.cpp, in `fetch()` (`op.fetchRequestPayload.nowNs = nowNs`, called with `static_cast<int64_t>(i)`, the pass index) and in `fetchDataServesForTest` (no assertion).
- **Failure scenario:**
  - The worker passes run on `clock_.nowNs()`, a monotonic clock in nanoseconds since boot. The fetches stamp `lastFetchTimeNs = i`, a few thousand.
  - At the first ISR check after `resetLagClock`, `now - i` exceeds `replicaLagMaxMs` (10 s), so follower 2 is shrunk out of the ISR within about 10 ms.
  - From then on: no pushes; the DUR-1 `unclean` path fires; the follower never re-expands.
  - Before the shrink, `decideFetchServe` answers about half the LEO-32 fetches AckOnly. `nowNs - askSinceNs` uses the same tiny clock and is below `kFetchResendNs`, so those fetches read nothing.
  - The one ISR-shrink pass (`updateIsr_`/`changeIsr_`, cold) is tagged `kFetch` and can inflate the "fetch" solo maximum.
  - The scenario asserts only the retention preconditions. If fetches were refused (NotLeader, stale epoch, a refactor), the gate would pass without serving anything.
- **Fix:**
  - Pass the rig clock: `rig.fetch(p, from, rig.nowNs())`, or have `fetch()` read `clock_.nowNs()`.
  - Add `EXPECT_GT(sum of p.rep->fetchDataServesForTest(), 0u)` with the message "precondition: fetches served data". `Reads+Retention` checks `readBytes > 0` the same way.
  - Optionally assert `readMapFallbacksForTest() == 0` and that the ISR is still {1,2} at the end.

### M3. Test coverage misses three of the five scoped paths
- **Where:** HotPathBRegressionTest.cpp `FollowerFetchNeverFaultsThroughTheReadMapRegression`.
- **Gaps:**
  - It covers only the ring-op path, `executeFetchRequestWire_`. The production path when `workerReplTransport_` is set, `pollReplTransportDispatch_` (Worker.h:3600), is not covered.
  - **Push:** after the fetch at 0, `dataServedThrough` equals LEO (about 256 KB, below the 512 KiB maxBytes), so `pushToFollowers` never reads.
  - **Owed re-serve:** NullPartitionTransport accepts every send.
  - **`appendControlBatch`:** not covered.
  - **Memo with a constant pointer across a compaction swap at the same LEO:** this is the only invariant whose argument changed. F27OwedMemoSwapTest runs with no scratch, so it still keys on mapping pointers.
- **Failure scenario:** a refactor drops one of the scopes (for example the inline-dispatch one, or the doWork loop that covers push and owed). The perf fix then silently regresses on that path, and every test stays green. For the memo, a future change to the swap or gen bookkeeping could serve a torn batch only when a scratch is set, and no test runs that configuration.
- **Fix:**
  - Extend the regression test:
    - push: produce more after the first fetch, then pass, and assert the `readView` count is unchanged.
    - owed: use a refusing transport or the F27 `notConnected` seam, then pass.
    - marker: append one marker.
  - Add a `setReadScratch` variant of `F27OwedMemoSwapTest` (and of `OwedAnswerToDeadFollowerIsNotRebuiltEveryPassRegression`) that asserts a rebuild after a swap at the same LEO and no rebuild while nothing changes.

## LOW

### L1. Scratch size is a hard-coded literal, not tied to the fetch cap
- **Where:** Worker.h:4072 (`(1u << 20) + 64 * 1024`).
- **Detail:** `readInto` needs `maxBytes + 2*indexInterval + overhead`, about 1 MiB + 8.3 KiB. `userTopicMaxFetchBytes` caps the replica's pushCap at `kDefaultMaxFetchBytes`. However, `req.maxBytes` is capped only by the transport ceiling (AeronPartitionTransport.cpp:805-814), which can be above 1 MiB.
  - A larger request gets a silently shorter response. The behaviour is correct, but no counter records it.
  - A first batch between `bufCap` and `maxBytes` falls back to the mapped read.
- **Fix:** size the scratch from `rune::replication::kDefaultMaxFetchBytes + 64 KiB`, add a `static_assert` that the slack is at least `2*kDefaultIndexIntervalBytes + kRecordBatchOverhead`, and clamp or count when `maxBytes > cap - slack`.

### L2. Paths without a scratch still use `readView` (performance gap, not a bug)
- **Paths:**
  - The control thread drives internal partitions: `NodeRuntimeAgent.h:613/622` doWork, then push and owed reads; `AeronPartitionTransport.cpp:847`, the inline `onFetchRequest` for `topicId < 0` and the no-pool mode.
  - Control-thread services call `append`/`appendKeyed` (with `pushOnAppend=true`, the default): MetadataService, ReplicatedOffsetStore, ReplicatedTxnStateStore.
- **Impact:** these are low volume, but a first-touch fault on the control thread queues behind the same `mmap_lock`.
- **Fix (if wanted):** give the control thread its own scratch and wrap those loops the same way.

### L3. A pread error becomes a silent permanent stall
- **Where:** LogSegment.cpp:632-640 (`fill` returns false on EIO), PartitionReplica.cpp:3301.
- **Detail:** `readLog_` returns an empty view with `tooLarge=false`, so there is no fallback and no counter. `onFetchRequest` then returns without answering (the "transient read-map failure" branch), owed retry hits `continue`, and push hits `pre.bytes==0`. This is still better than `readView`, which would SIGBUS. But a persistent EIO now leaves the follower stalled with nothing logged, and the storage-failed halt is never triggered.
- **Fix:** have `readInto` report an errno (or a `readErrors_` counter on the segment). On a non-EINTR error, call `markStorageFailed` so the owner halt path (exit 74) runs, as the fsync and write failures do.

### L4. `readMapFallbacks_` is visible only to tests
- **Where:** PartitionReplica.h `readMapFallbacksForTest`.
- **Detail:** on the box a mapped fallback, the exact event that brings the faults back, cannot be observed.
- **Fix:** expose it through the existing replica metrics or the FR site, as `pushReadMapFallbacks_` would also need.

### L5. Replication reads no longer drain grown-map replies
- **Where:** Log.cpp:1036-1054.
- **Detail:** `readInto` skips `pollReadMaps_`/`maybeGrowReadMap_`. On a partition whose only readers are now pread-based, an outstanding grow reply (a `MappedFile*` in `mapRing_`) waits for the next `readView` or for Log destruction. It is bounded at one outstanding request, `Log::~Log` handles it, and no new grow requests are made. There is no leak, but the retired mapping stays mapped longer.
- **Fix:** none required; optionally poll `pollReadMaps_` once per owner pass.

### L6. The memo comment cites the wrong invariant
- **Where:** PartitionReplica.cpp:1089-1092.
- **Detail:** "same offset/LEO/len/install gen = the same bytes" holds only because a leader's log never truncates within a leadership; every role change runs `resetLeadership()` and clears `owed`. If a future leader-side truncation (for example a storage-repair path) bypassed `resetLeadership`, the constant pointer would no longer catch truncate-then-re-append to the same LEO. The old mmap key might have caught it through a remap.
- **Fix:** state that invariant in the comment, or add `diskLog_->logGeneration()` (or the truncation count) to the memo key at the cost of one load.

### L7. Possible pre-existing bug, unchanged by this diff and not verified: an empty read inside a compacted gap
- **Where:** both `readView` and `readInto` return empty when `startOffset` lies after the last surviving batch of a sealed segment but below the next segment's base (a compaction removed the segment's tail). They do not continue to the next segment.
- **Detail:** `onFetchRequest` then treats this as a transient read failure and never answers. A follower whose fetch offset falls in that gap would re-fetch forever. Kafka moves on to the next segment.
- **Next step:** check whether the cleaner always keeps each segment's last batch. If it does not, have `Log::readView`/`readInto` move to the next segment when the offset is missing.

### Note: NUMA placement of the scratch (informational)
`replScratch_` (like `pushScratch_`) is zero-filled on the thread that constructs the Worker, so its pages are first-touched on that thread's NUMA node, not the pinned worker's. This does not matter on the 4-core box. On the planned bigger boxes, first-touch the buffer from the worker thread at start.
