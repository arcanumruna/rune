## M2: fixed. m3: fixed, with a new major

### N2 (MAJOR, new)

**The balancer filter blocks failover for a held unit's live siblings indefinitely.**

- **Where:** `runDynamicRebalanceOnTick`, `MetadataService.h:~1450`.
- **What it does:** it erases every balancer record with `leaderNode != NO_LEADER` for any key in a unit that still has an `emptyMemoryLeader_` entry.
- **Why the entry lasts forever:** a held unit keeps that entry forever. Survivor election is off by default (`survivorLeaderElection=false`), so a held unit is the default result whenever a member has no clean candidate.
- **Scenario:**
  1. A-0 is held because its sole-ISR memory leader restarted empty.
  2. B-0, in the same unit, is led by live node 2.
  3. Node 2 dies.
  4. The balancer's failover record (leader=3) is erased.
  5. `decideLeaderless_` ignores B-0, because its `leaderNode` is the dead node 2, not `NO_LEADER`.
  6. B-0 stays led by a dead node until an operator steps in. ISR-change and move records for the unit's live siblings are suppressed the same way.
- **Fix:** filter only records that would elect a leader for an EML member itself, or a non-marked `NO_LEADER` sibling that is still awaiting the unit decision. Never filter records for a sibling that currently has a leader. Add a test where a held unit's live sibling leader dies.

## m5: not OK

The migration and crash-safety parts are correct:

- The legacy value is folded in with max.
- The legacy file is unlinked only once `fencePersisted_ >= fence`, followed by a directory fsync.
- Corrupt state means the fence is unknown and the first leadership is refused. This is safe, because the controller's bump always grants an epoch above any epoch the node led before.
- A crash between submit and completion is safe: the leadership is never taken before the completion, and the image is either durable (so a restart refuses) or was never acted on.
- No worker-thread I/O is left on this path, because `setMemoryEpochStateDir` runs at replica build.

### N1 (CRITICAL, new)

**In a multi-node cluster, a memory-backed user partition never becomes leader.**

- **Why the leadership is deferred:** `BrokerNode` calls `applyWorkerDrivenDurability`, which sets `externalFollowerFlush_ = true` for every user replica. `setMemoryEpochStateDir` now sets `es_.enabled` and `fenceFile_`. `setIsrChannel` is set in multi-node. As a result, `becomeLeader` always takes `deferLeadership_`.
- **Why it never completes:** `Worker::submitEpochStateWrite_` (`Worker.h:~4885`) begins with `if (!r.isDiskBacked()) return 0;`. It also needs a `LogFlushSlot`, and completion routing goes through `gate->replica` of a log slot. Neither exists for a memory replica.
- **Result:**
  - The prepared write is never submitted, so `epochStateWriteCompleted` never fires and the leadership stays pending forever.
  - The node keeps the follower role while the controller has committed it as leader. The partition is unavailable.
  - Followers can wedge as well: `completeDivergenceTruncation_` sets `awaitEsFetch_` while `!epochStateDurable()`.
- **Why the tests are green:** `MemoryFenceWrittenByTheAsyncEpochStateWriterRegression` performs the io backend's job by hand (prepare, pwrite, fsync, completed), so the worker gap is invisible. No `BrokerNode` or `Worker` test covers a multi-node memory topic.
- **Fix:** give the worker an epoch-state submit and completion route for memory replicas. That means a slot or route keyed by the replica, not `r.log()`. Add a RED test that runs a real `Worker` and `WorkerPool` with a memory replica, `setMemoryEpochStateDir`, `setIsrChannel`, and `becomeLeader`, and asserts it reaches Leader.
