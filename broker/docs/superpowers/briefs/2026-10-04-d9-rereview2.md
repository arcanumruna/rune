## NEW MEDIUM

### MEDIUM-1: a deposed coordinator's stale copy closes the next transaction when the new load's marker was taken but not yet applied

**Where:**
- `ClientGateway.cpp:3848-3864`. The index only acts when `sameLoad` holds (same origin, coordinator epoch and token incarnation). Any other copy falls through, is recorded as the new entry, and goes to the worker.
- `Worker.h:3204` with `ProducerStateManager.cpp:262`. The worker fence compares against the PSM's `coordinatorEpoch`, which rises only after a *successful* append (`Worker.h:3240-3242`).

**Scenario:**
1. Coordinator C (txn-state leader epoch 5) sends COMMIT(T1), token k, to L. L appends it and answers R1. A re-sent copy A2 of k is still held: in C's HeldFifo to L, or in L's image behind a back-pressured controlled poll. This is the same back-pressure state as in round 1.
2. R1 lands, T1 completes, and T2 starts writing to the partition on L.
3. The DynamicBalancer moves the `__transaction_state` partition to C′ (epoch 6). C's process stays alive, so its HeldFifo and L's image still hold A2.
4. C′ ends T2 (say ABORT) and sends token k2 with epoch 6. L records the entry (C′, 6, k2). The worker then refuses k2 for a transient reason: the owed-cap reservation (LOW-5 of round 1), or the min-ISR gate during a brief ISR shrink. So the PSM `coordinatorEpoch` stays 5.
5. The transient condition clears, and A2 arrives before the TCS retry of k2 (backoff of 10 ms to 1 s).
   - `sameLoad` is false (the origin and epoch differ), so A2 goes to the worker.
   - The fence checks `5 < 5`, which is false, so A2 is appended as COMMIT.
   - `rc->onMarker` closes **T2 as committed**.
6. The retry of k2 (ABORT) finds no open transaction. T2's aborted data stays visible to read_committed readers: an atomicity violation.

**Why it was missed:** the round-2 index treats a cross-load copy as "not my business" and leaves it to the worker fence. But the fence only knows about epochs that were *applied*, while the index already knows that epoch 6 was *taken*.

**Fix (one comparison, cold):** in `appendRemoteControlRecord`, when an entry exists and `w.coordinatorEpoch < e.coordinatorEpoch`, answer `kMarkerCoordinatorFencedError` and do not record or append. Coordinator epochs per producer are monotone (one `__transaction_state` partition per producer), so a lower epoch seen after a higher one always comes from a deposed coordinator.

Regression test: take k2 (epoch 6) with min-ISR forcing a refusal, restore min-ISR, then deliver the epoch-5 copy. Expect no append, T2 still open, and a FENCED answer.

### MEDIUM-2: `lastRemoteMarker_` grows without bound under transactional-id churn

**Where:** `ClientGateway.h:1694`. The map is never erased from (report concern 3).

**Is it bounded in practice?** Not for every client.
- Producer ids are stable per `transactional.id`, so a fixed fleet gives a bounded set: transactional ids × partitions each one touches.
- Flink's KafkaSink, and other exactly-once frameworks, derive transactional ids from the checkpoint or task attempt, and every new id gets a new producer id.
- Example: parallelism 10, 10 output partitions and a checkpoint every 10 s give about 100 new keys every 10 s, roughly 860k per day. At about 80 to 100 B per `unordered_map` node, that is close to 80 MB per day per broker, never reclaimed. The broker also rehashes this map on the runtime thread as it grows.

**Fix:** pruning is safe at two points that need no timer:
- **On demotion or removal of the partition on this node.** A copy that arrives after this node regains leadership was routed under an older leader epoch, so the MEDIUM-3 check refuses it. A copy for a partition no longer here is answered NotLeader. The entry is therefore never needed again.
- **On PSM producer expiry** (`transactional.id` expiration). An expired producer cannot have an open transaction for a copy to close.

Either bound alone is enough for a long-running broker. Add a test counter for the map size, and a test that demotes and checks the size falls to 0.

## NEW LOW

1. **Image→peer attribution by host is ineffective, or occasionally wrong, outside flat-IP deployments** (`AeronPartitionTransport.cpp:97-104`, `:441-468`).
   - **Ineffective with hostnames.** `Image::sourceIdentity()` is always a numeric `ip:port`. The peer host comes from the configured egress endpoint. Docker-compose service names and k8s DNS names therefore never match, and every new image falls back to -1 (all peers). That is the round-1 behaviour, and it is safe now because the leader is idempotent; it only costs cold re-sends.
   - **Occasionally wrong under NAT.** With docker published ports or SNAT, the source IP can equal *another* peer's configured host. The image is then attributed only to that peer, and the real sender's markers are not re-sent. Note also that `find("endpoint=")` would first match a `control-endpoint=` key if one ever precedes it.
   - **The impact is limited.** A peer restart or a C→L outage is also caught by the per-peer publication edge (ruling 2). Only an L→C answer-direction image loss with C→L still connected depends on the image path.
   - **Suggestion:** with leader idempotence in place, either always report -1 on a new image (simplest and exact enough), or learn session→peer from the first frame of each image, as the report proposes.
   - **Two minor points:**
     - Detection keys on an *image count* change (`:445`), so a remove plus an add between two polls is missed. In practice that cannot happen at poll granularity.
     - An up edge is reported twice: once by the publication edge, and again by the `noteLink` generation bump. Harmless.
2. **A leader restart at the same leader epoch loses the index.**
   - **This is realistic.** If L restarts faster than failure detection, the DynamicBalancer does not move leadership, and L resumes at the same epoch from the committed map. The MEDIUM-3 check then cannot help.
   - **Hazard:** a copy of an *answered* token held in C's HeldFifo while L was down is flushed on the up edge. If the client has already begun T2 on the restarted L, that copy is appended again (the index is empty, the epoch is equal and the fence is equal) and closes T2.
   - **Why it stays LOW:** the flush happens at link-up, normally before a client can reconnect, refresh metadata and produce.
   - **Cheap fix:** on a peer down edge, drop held `WriteTxnMarker` frames for that peer. The up-edge re-send already re-issues every marker still in flight, so the held copies add nothing but risk.
3. **The token incarnation is random, so cross-incarnation copies at an equal coordinator epoch reach the worker fence, which passes equal epochs** (`ClientGateway.cpp:3669-3675`, `:3850-3851`).
   - This is safe only if a coordinator restart always bumps the `__transaction_state` leader epoch. A quick restart that keeps leadership keeps the epoch (see LOW-2).
   - The hazard needs an old-incarnation copy to sit in L's image while the restarted coordinator completes T2 and T3 begins, so it is very narrow.
   - Making the incarnation monotone (for example boot wall-clock seconds in bits 32..62) would let `sameLoad` order incarnations, so an older-incarnation copy could be refused like an older token.
4. **During the startup window, leader-epoch skew in the routing image produces NotLeader refusals and can trip the stuck gauge** (report concern 6).
   - A coordinator image that lags the replica epoch is refused and re-routed with TCS backoff until the committed map arrives. This is bounded, and correct, since only *older* epochs are refused.
   - If the bootstrap window is longer than 5 s, the gauge reports these markers as stuck, a false alarm at startup.
   - Consider counting from the first *committed* routing image, or logging the refusal reason as "stale target epoch" so operators can tell the cases apart. The worker logs it at info (`Worker.h:3216`); the gateway's remote answer path does not.

**Not counted:**
- The block-length change 40→44 makes round-2 nodes reject round-1 frames (`ReplicationMessages.h:682`). D9 has not shipped, so this is fine.
- The gauge ages a re-dispatched retry from the original dispatch. That is acceptable for observability.

## Cross-failover analysis (fence + leader epoch + idempotence)

| Case | Caught by | Result |
|---|---|---|
| Same coordinator load, copy trails its answer | index: same token, answered → re-answer | safe |
| Same load, copy of an older token after a newer one was taken | index: older token → NotLeader (ignored by the coordinator) | safe |
| Copy held across a leader change and delivered to a node that leads again | target leader epoch < replica epoch → NotLeader | safe |
| Copy delivered to a new leader that never saw the token | the copy was routed to the old leader under the old epoch, so the new leader never receives it | safe |
| Deposed coordinator copy after the new load's marker was **applied** | worker fence (PSM coordinatorEpoch) | safe |
| Deposed coordinator copy after the new load's marker was **taken but refused or not yet applied** | nothing | **MEDIUM-1** |
| Same epoch, coordinator restarted (new incarnation) | worker fence passes equal epochs | LOW-3 |
| Leader restarted at the same leader epoch | index lost, epoch equal | LOW-2 |

**Can a transaction get stuck forever?** I found no permanent stall:
- The pending-skip branch only holds while the original is genuinely owed. Every leader-side exit answers: the worker return (`ClientGateway.cpp:3592-3596`), the not-registered refusal (`:3663-3667`) and the halt-on-invariant reroute bound.
- An older-token NotLeader answer goes to a coordinator that has already forgotten that token.
- A target-epoch refusal is retriable and converges once the image catches up.
- A re-answer of an error outcome makes the coordinator re-dispatch with a new token.

**Can a transaction be closed by a stale decision?** Only in the narrow windows listed above (MEDIUM-1, LOW-2, LOW-3).

Not D9: a coordinator that acknowledges EndTxn before CompleteCommit is replicated can have C′ re-drive T1's marker after T2 began. That affects local markers equally and belongs to the coordinator-durability work.
