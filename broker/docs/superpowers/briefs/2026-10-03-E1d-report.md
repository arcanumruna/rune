## Design as built

### 1. Recovery point R (Log)
- Each `LogSegment` now tracks `durableNext()`: the highest offset known to be on disk.
  - It is raised by an inline `sync()`, by `Log::noteFlushCompleted(seg, upTo)` (the worker's io completion), and by recovery.
  - A seal completion passes `INT64_MAX`, meaning the whole segment.
  - An active-segment flush passes the LEO at submit, which is stored in the route as `TokenRoute::aux`. The uring backend reports `flushBoundary = 0`, so the value from the completion can't be used.
- `Log::advanceRecoveryPoint_()` moves R **in order**. It passes a sealed segment only once that segment is fully durable, then moves into the first partially durable one. A completed seal on a later segment never skips an earlier pending seal. The cost is O(log segments) on completions only. There is no allocation and no virtual call.
- R is persisted to `<dir>/recovery-point-offset-checkpoint` (text `1\n<R>\n`) with tmp + fsync + rename + dir fsync. Writes happen only in these cases:
  - **R crosses a segment boundary** since the last persist. This is the `rpDue_` flag, set about once per roll and never per append.
  - **Truncation below the on-disk value**, or below an in-progress checkpoint's value. This is persisted inline on the accepted role-change path, and the in-progress checkpoint is abandoned (its completion never renames).
  - **After recovery.**
  - **Clean shutdown**, in the destructor. This is skipped on a failed log or when the dir is gone. The `crashForTest()` seam makes a simulated crash skip it.
- **Worker-driven logs** (`deferSealSync`) checkpoint through the io backend: `Worker::submitRecoveryCheckpoint_` drives a rich-state machine on the Log, `Idle → TmpWritten → TmpSyncing → Renamed → DirSyncing → Idle`.
  - It uses a new `RouteKind::RecoveryPoint`, and the sequence number in the route rejects stale completions.
  - There is no inline fsync on the loop; `syncCallsForTest` stays 0. When idle the per-pass cost is two loads.
- **Legacy inline-seal logs** checkpoint inline at the roll, which already fsyncs inline.
- **Errors are fail-stop (fsyncgate):** sticky `failedErrno`, and the worker's existing error path calls `failLog_` and signals the halt.
- A Log that was never `recover()`ed never writes R, and its cleaner gate reflects the on-disk value or none (unchanged behaviour).

### 2. Recovery (`Log::recover` / `validateFromRecoveryPoint_`)
- The file is read with `readRecoveryPointFile`. If it is missing, R is set to the last sealed segment's end and a WARN is logged (only if segments existed at open, so a fresh log stays quiet).
- **Segments ending at or below R** are CRC-recovered but not chain-checked, so compaction gaps there are accepted.
- **From the segment holding R onward:** each segment is CRC-recovered and must end exactly at the next segment's base.
  - At the first mismatch or torn tail, the log is cut there and **every later segment is deleted** (files and map entries).
  - The validated region is fsynced (`LogSegment::syncForRecovery`, counted as roleChangeSyncs). The checkpoint's dir fsync makes the cuts and deletions durable.
  - Then R = LEO is persisted.
- That LEO is what flows through `isRecovered()`, the epoch-cache clamp and the HW clamp.

### 3. Cleaner invariant
- `SegInfo::belowRecoveryPoint` is true when the segment ends at or below the **persisted** R, or when no R was ever persisted. The snapshot is republished when a persist moves R.
- `LogCleanerAgent` bounds `firstUncleanable` by the first segment that is not below R.
- `LogCleaner::cleanSegment` and `compact` (the append-thread paths) refuse or stop at such segments.

### 4. Truncation and reload
- The rebuilt segment keeps `min(old durable, cut)`.
- `reloadSegment(s)` carries durability over. A cleaner-rewritten segment was fsynced before its rename.

### 5. Follower acked LEO vs synced LEO / R (KIP-966 / E1b tie-in): **it can exceed both — follow-up, not changed here**
- `PartitionReplica::nextFetch` reports `fetchOffset = logEndOffset_()`, which is the page-cache LEO.
- The follower flush (`followerFlushIntervalNs`) is **off by default** (durability comes from replication, the Kafka model).
- So the leader gives HW / acks=all credit for follower offsets that are not on that follower's disk and are above its R.
- After E1d, a power-lost follower recovers to its durable gap-free prefix (lower than what it reported) and re-fetches. This is correct, but an acked record's copy count can temporarily drop. If the leader is lost at the same time, acked data can be lost.
- Follow-up for E1b / KIP-966: either report `min(LEO, synced LEO)` for acks=all credit when a durability tier needs it, or add unclean-recovery / ELR semantics.

## Concerns / follow-ups
1. **Pre-existing test-infra flake, not fixed (outside the storage scope):**
   - Aeron node tests pick free UDP ports by bind(:0) → close → reuse, which races when many test processes run at once under `-j10`.
   - I stress-tested 12 concurrent instances per binary over 2 rounds. Baseline: 12/24 runs failed, 5 with `EADDRINUSE`. New: 16/24 failed, 4 with `EADDRINUSE`. The port-collision rate is the same, so this is not caused by the change.
   - Fix idea: per-process disjoint port ranges, or bind-and-hand-over.
2. **Per-roll syscalls on the worker loop:**
   - The async checkpoint does an `open(O_CREAT|O_TRUNC)` + `pwrite` (tmp file) and a `rename` on the loop, about once per roll (the fsyncs go through the io backend).
   - Possible follow-up: pre-create the tmp file on the pre-provisioning thread.
3. **Directory fsync goes through `IORING_FSYNC_DATASYNC` / `fdatasync` on the dir fd.**
   - This commits renames on ext4/xfs (journaled dir metadata).
   - If strict `fsync` semantics are wanted for the dir, add a full-fsync op kind to the io backend.
4. **Trusted-region file loss:** a segment file whose directory entry never became durable would look like a compaction gap below R.
   - This is mitigated by ordering: the checkpoint's dir fsync runs after the segment file is created or renamed and its data fsynced. Recovery of staging files also handles un-renamed staging segments.
   - A gapped follower's staging segment that was never renamed before a crash is renamed to its first batch's base, which can be above the true segment base. Recovery would then see a chain mismatch and truncate there (the follower re-fetches the data).
5. **Follower acked LEO above synced LEO / R:** see design item 5 (KIP-966 / E1b follow-up).
6. **The DR harness `crash()` now calls `Log::crashForTest()`.** Before this, a simulated crash ran Log destruction, which would now perform a clean-shutdown checkpoint.

### Changes
- **F1: no open/pwrite/rename/dir-open syscalls on the shard loop.**
  - **The file:** `<dir>/recovery-point-offset-checkpoint` is created **once**, at first recovery: tmp + fsync + rename + full directory `::fsync`. It is pre-allocated to 8 KiB with two slots 4 KiB apart. Each slot is 32 bytes: `{magic "RRP1", version, seq, R, crc32c}`.
  - **A checkpoint** is one io-backend request, `IoBackend::submitWriteSync(fd, data, len, off)`:
    - io_uring: a linked `IORING_OP_WRITE` (with `IOSQE_IO_LINK`) followed by `IORING_OP_FSYNC(DATASYNC)`, both submitted in one `io_uring_enter` (`pushSqes_`, which is now the single SQ submit path; the atomics allowlist was updated to match).
      - The bytes are copied into backend-owned blocks pre-allocated in the constructor.
      - The write's CQE is internal and never handed out. A failed write cancels the fsync (`-ECANCELED`). A short write turns the fsync's completion into `ENOSPC`.
    - Portable: a new `WriteSyncRequest` ring message carrying the block inline (pwrite then fdatasync on the flusher thread). The submit ring is sized for the larger message.
  - **The worker** prepares the slot image in memory (`Log::prepareRecoveryCheckpoint`), submits it, and completes it. The loop makes no syscall and no allocation for this.
  - **Inline paths** (legacy seal, truncation, recovery, clean shutdown) write the slot that is **not** in flight, with a higher seq, so a superseded in-flight write can never win.
  - **Recovery** takes the valid slot with the highest seq. A torn slot falls back to the older, lower R, which is safe.
- **F2: persisted R and the cleaner gate move only on durable completion.** `persistedRp_` and `SegInfo::belowRecoveryPoint` change only when the write+fdatasync completes, never at submit.
  - New test of the production gate: `CompactionCleanerAgentRegression.NeverCompactsAboveRecoveryPoint` (LogCleanerAgent's `firstUncleanable` bound).
  - New test of the compact gate: `RecoveryPointRegression.CompactNeverRewritesAboveRecoveryPoint` (`LogCleaner::compact`, via `clean`).
  - Worker test: the checkpoint is in flight and neither persisted R nor the gate has moved, then the completion arrives and both move.
- **F3: the one-time directory sync at file creation is a full `::fsync`, inline.** No directory sync happens per roll.
- **F4: the legacy duty-cycle compaction advances `lastCleanOffset` only when `cleanSegment` returned true.**
  - Deviation from the ruling: an *empty* sealed segment with the gate open is also passed over. `cleanSegment` returns false for an empty file, so without this the watermark would be stuck on that segment forever.
- **F5: a checkpoint file with both slots invalid (or present but unreadable) is fail-stop.**
  - The log is marked failed, and recovery only CRC-recovers: it never truncates at a chain gap and never deletes a segment.
  - If the file is missing, behaviour is unchanged: R = the last sealed segment's end, plus a WARN.
  - A persisted R above the recovered LEO now logs an ERROR.
- **F6: `truncateTo` persists `min(R, truncateOffset)` before touching any file.**
  - If that persist fails, the log is failed and no file is touched.
  - It persists again if a mid-batch cut rounds the LEO down below `truncateOffset`.
- **F7: a new owner replays completions the previous owner never saw.** When `rebuildFlushSlots_` creates a fresh slot for a log with no route in flight on that worker:
  - A RecoveryPoint completion that went to a previous owner: `Log::resetRecoveryCheckpointForNewOwner()` treats the outcome as unknown, rewrites that slot with a higher seq, and never moves persisted R on it.
  - A Seal completion that went to a previous owner: `Log::requeueUndurableSeals()` re-queues (pinned) every sealed segment that is not yet durable.
- **F8: checkpoint submission is event-driven.**
  - A completion that makes the log's checkpoint due queues the log once (`rpQueue_`, a per-slot `rpQueued` flag, capacity reserved at slot rebuild).
  - The pass touches only queued logs. A refused submit stays queued.

### Changes

**MAJOR-1: possibly-durable checkpoint values.**
- `Log::rpUnconfirmedMax_` holds the highest R carried by a checkpoint write that may have landed.
  - It is raised when the write is submitted (`recoveryCheckpointSubmitted`).
  - `resetRecoveryCheckpointForNewOwner` keeps it and never drops it.
  - Only a confirmed durable write with a higher seq clears it: an observed async completion, or any inline write.
- `onDiskRecoveryPointUpperBound() = max(persistedRp_, rpUnconfirmedMax_)` is the bound that `persistAtMost_` (and so `truncateTo`) now compares against.
  - A truncation below that bound persists the lower R inline before any file is touched.
- After a fresh-owner reset, the inline write targets the alternate slot, which is the slot that may hold the landed value, so it overwrites it.
- The clean-shutdown checkpoint also runs when `rpUnconfirmedMax_ > R`.

**MEDIUM-1: seal replay always runs.**
- `rebuildFlushSlots_` always calls `requeueUndurableSeals(inFlight, n)`.
- It skips only segments whose Seal route is still in flight on this worker; their completion still arrives here.

**MEDIUM-2: directory durability (Kafka `flushParentDir` parity).**
- **Generations.** Every directory mutation bumps a per-log generation:
  - a segment install at a roll (adopted staging file, or the fallback create);
  - a truncation's deletions or its recreate.

  `LogSegment::dirEntryGen()` records the generation of its entry, and `install_` / reload carry it over a rebuild of the same file name.
- **The gate.** `advanceRecoveryPoint_` never moves R past the base of a segment whose entry is not covered by a completed directory fsync (`dirSyncedGen_`).
  - So R never trusts a segment, and never re-enters a truncated range, before the directory state is durable.
  - A segment that loses its entry therefore always lands in the chain-validated region, never in the trusted one.
- **Worker-driven logs:** `Log::{directorySyncDue, prepareDirectorySync, directorySyncCompleted, directorySyncNotSubmitted, resetDirectorySyncForNewOwner}`.
  - When R is blocked, the worker submits one batched **full** fsync of the directory fd through the io backend:
    - `IoBackend::submitFsync` → `IORING_OP_FSYNC` without the DATASYNC flag;
    - portable: `::fsync` on the flusher, using the FlushRequest body under a ring record type of its own (no schema change).
  - New `RouteKind::DirSync`. A fresh owner replays an unobserved one (F7 parity). It is event-driven through the existing `rpQueue_`.
  - No syscall on the loop.
- **Legacy inline-seal logs** fsync the directory inline at the roll.
- **Recovery** opens the directory fd once and fsyncs it before persisting R = LEO, so entries from earlier incarnations and staging reconciliation become durable.
- **Staging renames:** after adoption, the staging file's own entry is what the directory fsync makes durable. If the deferred rename is lost, construction reconciles the staging name, so R does not wait on the background rename. That avoids a wedge when no cleaner thread runs.
- **Correction to round-0 concern 4:** "the checkpoint's dir fsync" no longer exists. The guarantee is now the R gate above.

**LOW-4: io_uring linked pair.**
- (a) `writeSupported()` probes `IORING_OP_WRITE`. If it is missing, `IoBackend` falls back to the portable backend up front, for both explicit and auto selection, with a logged `fallbackReason`. It never halts.
- (b) `pushSqes_` treats a partial `io_uring_enter` as an error.
  - The unconsumed SQEs are rolled back, so they never run later unlinked.
  - If only the write reached the kernel, its token is still handed out and completes with an error (a synthetic EIO from `reap`). It never counts as success, and the possibly-landed write is never forgotten.
- (c) A failed or short linked write records its own errno (short = ENOSPC). The fsync's completion reports that errno instead of ECANCELED.

### Backlog (LOWs not fixed this round)
- **LOW-1:** two inline writes during one in-flight checkpoint target the same slot. A torn second write falls back to the superseded, higher in-flight slot. The round-1 concern 2 wording ("fail-stop") is wrong: the result is a stale higher R.
  - After the abandoned completion arrives, the next inline write targets the possibly-landed slot (so the window closes). The remaining window is a non-atomic sector write plus two truncations inside one checkpoint latency.
  - A fix needs a third slot or deferring the second inline write until the in-flight write completes.
- **LOW-2:** a mid-batch truncation persists `min(R, truncateOffset)` before the batch floor is known, so a crash in between logs a spurious "durable data vanished" ERROR. Data is not affected.
- **LOW-3:** R advanced on an inline path of a `deferSealSync` log sets `rpDue_` without queueing it on the worker, so the checkpoint waits for the next flush completion.
  - The new directory gate does not change this. R advances only on completions, and those queue the log.

### Concerns (round 2)
1. **Fd budget:** each recovered Log now holds 2 extra fds (`rpFd_` + `dirFd_`).
   - The broker never raises `RLIMIT_NOFILE` itself. Linux's default soft limit of 1024 is reached at about 300 partitions, even before counting segment fds; that segment-fd exhaustion is pre-existing.
   - Production needs `LimitNOFILE` / ulimit set (Kafka's guidance is 100k+), or the broker should raise soft to hard at startup. Not changed here.
2. **Directory fsync cost:** about one extra directory fsync per roll.
   - Worker logs: one io-backend request, serialized before the checkpoint (two async round trips per roll).
   - Legacy logs: one inline fsync at the roll.
3. **Unchanged:** the cross-repo dependency on rune-protocol `6d14dc8`; the follower acked LEO vs synced LEO / R gap (KIP-966 / E1b); the Aeron startup/port test flakes.
