# D2 review — non-worker thread placement + node-driver idle (68c3a62, wt35 `fix/d2-thread-placement`)

Reviewer: Opus, read-only. Scope: `git show 68c3a62`, plus the surrounding code in BrokerNode::start, Worker self-pin,
WorkerPool, EmbeddedDriver, HostDefaults, and main.cpp. Report: `2026-10-04-d2-report.md`.

## Verdict: APPROVE WITH CHANGES (no CRITICAL; 1 MAJOR, which is about process and goal, not code; 3 MEDIUM; 5 LOW)

The mechanism is correct.
- The complement is computed correctly for the derived layout, an explicit conventional base, an explicit
  unconventional base, and the override path.
- start() pins inside an RAII scope placed after every validation. Every non-worker thread is created inside that
  scope: the threaded node driver, the Aeron client conductor (thread placement), the startup pump, the runtime, admin
  and cleaner runners, and the portable flushers. The caller's mask is restored on return and when start() throws.
- Workers re-pin to their own core on their first doWork. The Worker::doWork prologue runs before any real work.
- The idle-default change reaches only the node driver in non-fused shard mode:
  - Legacy mode keeps sleep-ns.
  - The override wins.
  - Invoker drivers never call an idle setter (EmbeddedDriver.cpp:108-112), so the per-worker and fused-runtime
    drivers are unaffected whatever string they carry.
- Aeron's `backoff` (10 spins, 20 yields, then a 1 us..1 ms park) is a bounded backoff, not a busy-spin.
- No atomics or mutexes were added.
- The Linux-only test is correct and should pass (see L4 for one weakness).

## MAJOR

### M-1 The goal is not met, and thread p50 may have regressed; the A/B does not meet the perf-evidence rule
`HostDefaults.cpp:372-392` (derived set); report §A/B.
- **What happens:** on the 4-core box (3 nodes, W=1) the derived set is `{0}`. All three nodes' control planes now
  share core 0: 3 node drivers, 3 runtimes, admin, cleaner, flushers, main and signal. The report measures more than
  one core of demand there. Thread placement p50 went 8.6 -> 13.2 ms, and fused p99 went 40 -> 51 ms.
- **The evidence is not enough to clear it:**
  - Each arm ran once.
  - The two changes (affinity, and the driver idle default) were A/B'd together, so neither effect can be
    attributed on its own.
  - The perf-AB rule needs interleaved ABAB with n >= 15 before a dip is called noise.
- **Failure scenario:** merged as "D2 fixed", thread placement could be slower than before. In thread placement the
  runtime sits on the produce/ack path, and it now queues behind 3 drivers and 2 other runtimes on one core.
- **Fix:**
  - Before merging, run ABAB n >= 15 with four arms: baseline, affinity only (`RUNE_AERON_DRIVER_IDLE=sleep-ns`), idle
    only (`RUNE_NONWORKER_CORES` = the full mask), and both.
  - If affinity-only regresses p50, place by role instead of putting everything in one set:
    - drivers, admin, cleaner and flushers go to the complement
    - the runtime keeps a soft placement: the complement plus its own node's worker core, which is the one core the
      runtime shares with only its own worker
  - Either way, the real lever stays concern 1 (the control-plane CPU cost). M-2 is part of it.
- The fix is still worth keeping for the worker-preemption win: about 150x fewer involuntary switches. It just
  cannot be recorded as "D2 done" yet.

## MEDIUM

### Md-1 An explicit `RUNE_NONWORKER_CORES` with unpinned workers (or in legacy mode) confines the workers too
`HostDefaults.cpp:365-371` (the override branch has no `workerCoreBase >= 0` / `shardMode()` gate); `BrokerNode.cpp`
ScopedThreadAffinity.
- **Why:** the override is honored in every mode. Workers re-pin only when `coreId_ >= 0` (Worker.h:1184). With an
  unpinned layout, a worker created inside the scope keeps the non-worker mask for good. Unpinned layouts include:
  - multi-host, where `deriveWorkerCoreBase` returns -1 for non-loopback peers
  - `RUNE_WORKER_CORE_BASE=-1`
  - legacy mode
- **Failure scenario:** a production multi-host node sets `RUNE_NONWORKER_CORES=0` to keep the control plane on core 0.
  Every worker then also runs on core 0 and throughput collapses, with no warning.
- **Fix:** ignore the override unless workers are pinned (shard mode and `workerCoreBase >= 0`), and warn when it is
  ignored. Alternatively, pass the inverse set to the workers. Add a Regression case to
  `NonWorkerThreadsStayOffWorkerCoresRegression`.
- Related (LOW): an override that overlaps the worker cores is accepted silently. Warn on overlap.

### Md-2 The node driver's backoff default reproduces the yield/1 us-park churn profile that A7 proved starves a small box
`NodeConfig.h:595-599` (`effectiveDriverIdleStrategy` returns `"backoff"`).
- **Why:** Aeron C's backoff defaults are 10 spins, 20 yields, then a park starting at 1 us that doubles up to 1 ms.
  The memory note `rune-idle-churn-cpu-starvation` names exactly "20 yields / 1 us park" as the churn behind the
  4-core starvation. The workers' own backoff was retuned for that reason (`idleMaxParkUs`).
- **Evidence it is happening:** 3 such drivers now share core 0, and the report measures 21-23k involuntary switches
  per 5 s each, at about 20% CPU each on a control-plane-only driver. Concern 1 asks why a mostly idle driver burns
  20%; this churn is a likely part of the answer.
- **Fix:**
  - Use the same tuned backoff the workers use: fewer or no yields, a larger minimum park, and `idleMaxParkUs` as the
    cap.
  - Check whether this Aeron version takes backoff parameters through `aeron_driver_context_set_*_idle_strategy_init_args`
    or through the `backoff` init-args string. If it does not, use `sleep-ns` with an explicit, larger
    `AERON_..._SLEEP_NS`-style period. Aeron's default sleep is what made sleep-ns poll in the first place.
  - Measure it in its own arm (see M-1).

### Md-3 No test covers the wiring; the only proof is a manual `/proc` reading on the box
Tests: `HostDefaultsTest.cpp` (derivation only) and `ThreadAffinityTest.cpp` (the RAII mechanism only).
- **What is untested:**
  - BrokerNode::start applies `config_.nonWorkerCpus` after derivation
  - the scope covers the thread-creating calls
  - workers end up on their own core rather than the non-worker set
- **Failure scenario:** a refactor of start() creates a thread outside the scope, or adds a worker path that skips
  `setCoreId`, and nothing turns red. This happened before: A4 io-wq had to retry on EBUSY because of where its work
  ran. The never-hand-over-untested-code rule is not met for the Linux path.
- **Fix:** add a Linux-only `BrokerNodeTest ... NonWorkerThreadsPinnedRegression`:
  - start a 1-node shard broker with explicit `workerCoreBase` and `nonWorkerCpus` taken from the test process's
    allowed mask (GTEST_SKIP below 2 CPUs)
  - read `/proc/self/task/*/{comm,status}` and assert:
    - the driver, runtime, admin and cleaner threads have `Cpus_allowed_list == nonWorker`
    - each worker has exactly its own core
    - the test thread's mask is restored after start()
  - run it on k3s-node-01, where the Linux tier has not run yet

## LOW

- **L1 The conventional-layout check can give a false positive** (`HostDefaults.cpp:376-378`). Node 0's derived base
  is always `allowed[1]`, so an operator who sets base 1 on node 0 is treated as conventional even when the other nodes
  use other cores.
  - Example: 12 CPUs, W=2, bases 1/5/9. Node 0 excludes indices 1-6 and leaves node 2's cores 9 and 10 in its
    non-worker set.
  - This is no worse than before D2, but the log claims every co-located node is excluded. The check also assumes
    every peer has W workers and the same allowed mask (`p.workerCount` is ignored).
  - Fix: use the conventional layout only when every peer's `workerCount` equals W. Document the limit, or take the
    other nodes' bases from an explicit list.
- **L2 A worker whose pin fails now stays on the non-worker set instead of the full mask** (Worker.h:1184-1193 combined
  with the scope).
  - Example: an explicit base whose `base+w` falls partly outside the cgroup cpuset (allowed 4-7, base 3, W 2). Worker
    0's pin to core 3 fails, and it shares {5,6,7} with the control plane. There is no validation that `base+w` is in
    the allowed mask, and `CPU_SET(core)` is not bounds-checked (this part predates D2).
  - Fix: in HostDefaults, warn and treat the base as unpinned when any `base+w` is outside `allowedCpus`.
- **L3 io-wq is inconsistent with the explicit conventional base** (report concern 3). With
  `RUNE_WORKER_CORE_BASE=1+i*W`, `nonWorker=0` is derived but `ioWq=inherit`, so io-wq kernel workers stay on the
  worker cores. It was deferred on purpose, and that is reasonable. Fold it in once M-1's arms are measured, by using
  the same conventional predicate for `ioWorkerCpus`.
- **L4 The Linux ThreadAffinity test is vacuous on a 1-CPU mask** (`ThreadAffinityTest.cpp:19-32`). It sets
  `target = {before.front()}`. When `before.size()==1`, neither the restore check nor the inherit check can fail.
  Otherwise it is correct: the restore happens in the destructor before the post-scope assert, the child is joined
  inside the scope, and `ScopedThreadAffinity none({})` resolves unambiguously on GCC and Clang. Fix: GTEST_SKIP when
  `before.size() < 2`, and pick `before.back()` so the mask actually changes.
- **L5 Cosmetics and robustness:**
  - (a) `drvIdle=backoff` is logged in fused placement, where the node driver is an invoker and has no idle loop. Log
    `drvIdle=invoker` instead.
  - (b) The `dcfg.idleStrategy` override at `BrokerNode.cpp:3014` is dead, because invoker drivers never apply the
    string. Its comment suggests the override matters. Either drop it or say it is inert.
  - (c) `char line[1024]` plus two full CPU lists will truncate the tail of the effective-config line on large boxes,
    including `derived={...}`, which is the proof of config. Compress the lists to ranges or build a `std::string`.
  - (d) If `pthread_getaffinity_np` fails (more than 1024 CPUs, or a cpu_set_t size mismatch), `saved_` is empty, the
    pin still succeeds, and the mask is never restored. Return without pinning when the save fails.
  - (e) The comment in `BrokerNodeTest.cpp:1056` still says the default is "sleep-ns".

## Checked and fine
- The `complementCpus` filter is correct, including dedup, sort, a non-contiguous mask, and excluded CPUs outside the
  mask. The override filtering computes the intersection correctly. Running the derivation twice gives the same result.
- An empty complement leaves the affinity unchanged and emits exactly one warning. `pinThreadToCpus` refuses an empty
  set or a set with every CPU at or above CPU_SETSIZE.
- macOS: `allowedCpus` is empty and the derived base is -1, so `nonWorker=inherit`; every pin call returns ENOTSUP and
  start() does not warn about it.
- A cgroup cpuset is respected: `allowedCpus` comes from `sched_getaffinity`, and the complement is always a subset of
  it.
- Fused placement: worker 0 hosts the runtime, node driver and conductor, and re-pins to its worker core. The interim
  startup pump runs on the non-worker set, which is correct.
- The main and signal threads are pinned after start(), and `nonWorkerCpus()` reads config that is immutable after
  start().
- The env parse is correct: it rejects bad lists, and an empty value counts as unset.

# Review (round 2) — control-plane idle + Md-1/Md-3/L4 (2013c2e on 68c3a62)

Reviewer: Opus, read-only. Scope: `git show 2013c2e`, plus NodeRuntimeAgent::doWorkImpl_, Election liveness timing,
Worker shard-mode ack/return paths, HostDefaults ordering, and the Aeron 1.41.4 sources for `aeron_idle_strategy_load`,
the backoff init-args parser and the driver-context idle setters/initialisation.

## Verdict: APPROVE WITH CHANGES (0 CRITICAL, 0 MAJOR, 2 MEDIUM, 6 LOW)

Round-1 status: M-1 resolved in substance (thread p50 15.1 ms -> 0.55 ms, also well under the pre-D2 8.6 ms; fused no
regression); its per-lever attribution arms were never run (see R2-L6). Md-1, Md-2 (driver now on the tuned
1-0-100us-2ms shape), Md-3 and L4 are fixed. L1, L2, L3 and L5 are still open.

### Checked and fine
- **Liveness vs a 2 ms park.** Leader NLT/commit heartbeat every `electionStatusIntervalMs` (20 ms). Follower timeout is
  `max(electionTimeout 150 ms, 3 x status)` (Election.cpp:77). The failover eligible set uses 3x that. Worst-case added
  delay per heartbeat is about 8 ms: sender runtime park, sender driver park, receiver driver park, receiver runtime
  park. That leaves more than 18x margin on the timeout and about 2.5x on the status interval. Every other control timer
  is seconds-scale and checked against `nowNs`, never against cycle counts:
  - gateway session 10 s, Connect resolve 5 s
  - group session timeouts of 500 ms or more (tests) and 5-10 s (default)
  - txn 45-60 s, pending-ack 30 s
  - replica lag 10 s
  - internal-partition fetch backstop 5 ms
  - Aeron client liveness 10 s and its status/NAK timers
  No time-bounded handshake depends on the old fast polling. The only cadence that changes is the thread-placement
  "every cycle" failover scan, which is idempotent and time-independent, so a lower rate is fine.
- **Wake/work detection.** These are pure polling backoffs with no wake signal to lose. A non-zero work count resets
  them, and every park is bounded by the cap: `std::min(park*2, max)` in Agrona C++ and the same clamp in Aeron C. With
  `maxYields=0`, both implementations go straight from YIELDING to PARKING without calling `sched_yield`. Rings that the
  runtime drains while parked have far more than 2 ms of headroom: the return ring is 32 MiB, and worker-side acks in
  shard mode mean the produce answer never waits on the runtime. When the ring is full, the worker applies a controlled
  intake throttle, so nothing is lost.
- **Legacy mode is unchanged.**
  - The runtime's `{10,20,1us,idleMaxParkUs}` matches `makeBackoffIdle` exactly.
  - Admin `BackoffShape{}` matches the default-constructed `BackoffIdleStrategy` (10, 20, 1 us, 1 ms).
  - Driver args are empty, so only the strategy setter runs, as before.
  - The worker idles (`WorkerPool` `makeBackoffIdle`) and the startup pump are untouched.
  - Invoker drivers skip validation and both setters.
  - Member destruction order is safe: `adminWorkerIdleStrategy_` is declared before `adminWorkerRunner_`.
- **Aeron args format.** `"1-0-100000-2000000"` matches `%16[,.0-9]-%16[,.0-9]-%16[,.0-9mus]-%16[,.0-9mus]`, and
  undecorated durations are read as ns. Args are set before the strategy, which is correct because the setter loads from
  `context->*_init_args`. `env_var` is unused by every built-in init function, so passing "RUNE_AERON_DRIVER_IDLE" is
  harmless. The `extern "C"` redeclarations match the 1.41.4 signatures.
- **Hard rules.** Nothing busy-spins by default; only the opt-in `RUNE_RUNTIME_IDLE=busyspin` does. No atomics,
  mutexes, std::function, virtual dispatch or allocation were added on a hot path. All new code runs at startup or in
  the idle path, and `dynamic_cast` is used only in a test.
- **Md-1.** Ordering is correct: the gate runs after `workerCoreBase` is derived. Own-core dropping and its warnings are
  correct, and the regression test covers unpinned, legacy, overlap and the honoured path.
- **Md-3 test.** It excludes pre-existing tids and `iou-*`, checks the worker from the worker thread, and names the
  runtime, admin and worker threads. This is a real guard for the wiring.

## MEDIUM

### R2-Md-1 `RUNE_CONTROL_IDLE_MAX_PARK_US` accepts values that break consensus liveness
`NodeConfig.cpp:1179-1186` (range [1, 1e6] us); `NodeConfig.h:293` (`controlIdleShape`).
- **What happens:**
  - The cap applies to the runtime, which sends heartbeats, and to the node driver, which carries them.
  - A leader runtime that is otherwise idle sends its NLT/commit heartbeat only when it wakes.
  - With the cap at or above `electionStatusIntervalMs` (20 ms), heartbeats go out at the park period instead of the
    status interval.
  - Once 2 x cap plus driver parks approaches `leaderHeartbeatTimeoutNs` (150 ms by default, and lower in tight test or
    LAN configs), followers time out the leader.
  - The validation accepts 1 s.
- **Failure scenario:** an operator raises the cap to cut idle CPU, following report concern 2 ("the cap could go
  higher"). At 100 ms or more the cluster churns leadership forever while idle; the first produce after a quiet period
  also triggers it. Nothing warns, and the effective-config line shows the value as accepted.
- **Fix:** validate the cap against the election timing (both are known in `parseNodeConfig`). Refuse, or clamp with a
  warning, when `cap > electionStatusIntervalMs*1000/4` (5 ms by default). Document the bound next to concern 2. Add a
  `*Regression*` parse case.

### R2-Md-2 The control-plane latency cost was not measured on the paths that now pay it
Report concern 4; `NodeConfig.h:293-304`.
- **What changed per hop:**
  - Runtime park cap: 200 us -> 2 ms. In shard thread placement it was `RUNE_IDLE_MAX_PARK_US`.
  - Driver park: about 1 ms with yields -> 2 ms, with the first park after 3 empty cycles.
- **Paths affected:** a round trip that crosses both on each node can now add up to about 8 ms on a cluster that was
  quiet just before. These paths are sequential and latency-bound:
  - offset commit: `__consumer_offsets`, acks=all over internal replication on the node driver and runtime
  - group join/sync
  - EOS: AddPartitions, then EndTxn, then `__transaction_state` write, then markers through the runtime to worker rings
  - metadata propagation
  - any gateway-routed produce in shard mode: redirect or fallback clients, and Strict or acks=all gateway-routed
    frames (Worker.h:5133)
- **What was measured:** the A/B covered only open-loop plain produce at 20k/s, where the runtime rarely parks.
- **Failure scenario:** a transactional or consumer-group workload regresses several-fold in latency or throughput, with
  per-transaction or per-commit latency moving from sub-ms to several ms. This would ship unnoticed under "D2 done",
  against the benchmark-everything rule.
- **Fix:** before merge, run one before/after arm for each of these on k3s-node-01 (thread placement, same config as
  §4.13):
  - a txn produce loop (commit latency p50/p99)
  - an offset-commit loop
  - a low-rate closed-loop produce (1 in flight)
  If any regresses materially, give the runtime a lower cap than the node driver. The runtime is the hop the report
  measured as cheap: about 0 involuntary switches.

## LOW

- **R2-L1 The scratch validation does not use the args the setter will use**
  - **Where:** `EmbeddedDriver.cpp:134-140`.
  - **Mismatch:** with `idleArgs == nullptr`, validation loads the strategy with NULL args, but the Aeron setter loads it
    with `context->*_init_args`, which the context initialised from `AERON_{SHARED,CONDUCTOR,SENDER,RECEIVER}_IDLE_STRATEGY_INIT_ARGS`.
  - **Scenario:** the report's own sweep exported backoff-shaped `AERON_SHARED_IDLE_STRATEGY_INIT_ARGS` (for example
    `1-0-100us-2ms`), and the driver then runs legacy `sleep-ns` or an explicit `RUNE_AERON_DRIVER_IDLE=sleep-ns`.
    - Context init accepts the env args, because they are valid for the default backoff.
    - Scratch validation passes.
    - `aeron_driver_context_set_shared_idle_strategy` then fails, after it has freed `*_state` and `*_name`.
    - `aeron_driver_context_close` frees them again: a double free, which is UB and not the clean refusal the commit
      describes.
  - **Fix:** when `idleArgs` is null, validate with `aeron_driver_context_get_<role>_idle_strategy_init_args(ctx_)` for
    each role being set. In dedicated mode that is three validations.
- **R2-L2 `RUNE_IDLE_MAX_PARK_US` silently stops governing the shard thread-placement runtime** (`NodeConfig.h:298-300`).
  An operator who tuned it gets no warning. Warn when it is set explicitly in shard mode, or mention it in the
  `RUNE_IDLE_MAX_PARK_US` doc comment.
- **R2-L3 `RUNE_AERON_DRIVER_IDLE_ARGS` is silently ignored for `yield`, `spin` and `noop`**, because Aeron's
  `init_null` ignores args. Warn in `parseNodeConfig` or HostDefaults when args are set with a strategy that has no args.
- **R2-L4 The effective-config line misstates idle in two cases** (`HostDefaults.cpp:421-425`), carrying round-1 L5a
  forward:
  - Fused placement prints `drvIdle=backoff{...}` and `ctlIdle=...`, but the node driver is an invoker with no idle
    loop, and the runtime runs on worker 0.
  - `RUNE_RUNTIME_IDLE=busyspin` still prints the backoff `ctlIdle`.
  These are the proof-of-path fields, so print `invoker` or `busyspin` when they apply.
- **R2-L5 The "spins once" comment is inaccurate** (`NodeConfig.h:270-279`). In Aeron's state machine, `1-0` takes 3
  non-sleeping empty duty cycles before the first park: NOT_IDLE->SPINNING, one `proc_yield` pass, then YIELDING->PARKING.
  Each of those cycles is a recvmmsg per socket. `0-0` would take 2. Fix the comment, or measure `0-0-100us-2ms` as one
  more point toward concern 2.
- **R2-L6 Carry-overs and test gaps:**
  - Round-1 L1, L2, L3, L5(b-e) are still open.
  - The M-1 attribution arms (affinity only vs idle only) were never run. Without them it is unknown whether the
    affinity half alone costs thread placement anything.
  - Thread placement p99 is still 163 ms against 45 ms fused, and is unexplained (concern 1).
  - Md-1 drops only this node's own cores. An override that overlaps *another* co-located node's workers is still
    accepted silently (the round-1 overlap note).
  - No test covers R2-L1 (an AERON_* env args mismatch).
  - No BrokerNode-level test shows that legacy keeps its shapes end to end. NodeConfig-level only, which is acceptable.
  - The RED-first claims are credible: the shard wiring test fails on the 10/20/1 us shape, and the EmbeddedDriver
    malformed test aborted with 134 before. The Md-3 test is a guard for round-1 wiring and could not be RED on
    68c3a62. That is fine, but it should not be counted as RED-first.
