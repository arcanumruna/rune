# Latency-gate A/B: broker main 5cc6b16 (tonight's batches) vs 6ee164d (2026-10-09)

**Method.** k3s-node-01 box (4 cores). Same builder image for both binaries. Every DutyPassLatencyGate scenario ran
serially with `RUNE_LATENCY_GATE_BENCH=1` on a fresh 8G ext4 loop fs or a 6G tmpfs, with caches dropped before each
run. The old/new order was interleaved, n=3 each, 216 runs in total.

**Verdict: no regression.**
- Every scenario passes 3/3 on both builds.
- Medians are at parity.
- One clear improvement: FollowerFetchDuringRetention on tmpfs, p99.9 802 → 115 µs. This is the D26 read path (reads
  bounded by HW, no read-map provisioning for unread logs).
- FollowerTruncationDuringCleanerPass on ext4 looked worse at n=3 (704 → 2216 µs). A dedicated ABAB with n=10 shows
  parity: median 614 µs old vs 647 µs new. Both builds have the same bimodal ext4 journal distribution, and
  worker-work spikes occur in both (old run 4 had 19.2 ms). This is the known D27 behaviour.
