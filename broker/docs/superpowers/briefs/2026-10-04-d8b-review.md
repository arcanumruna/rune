# D8b review — held session's aborted produce frame refreshes its lease

Commit `982b50e` (rune-broker-wt37, branch `fix/d8b-held-session-lease`). Read-only review, 2026-10-04.

## Verdict: REQUEST CHANGES (1 CRITICAL, 1 MAJOR, 1 MEDIUM, 2 LOW)

The diagnosis is right: a paused session that has not read any acks yet gets no lease refresh, so it is reaped and its acks are dropped. The fix's safety argument is not right. It says "the aborted frame proves the client's publication is connected (Aeron drops a dead publisher's image after its liveness timeout)". The Aeron driver in use does not do that while the subscriber is stuck behind unconsumed data. Because the gateway ABORTs the frame, the gateway is that stuck subscriber. So the fix turns "a dead client is reaped after 10 s" into "a dead client is held forever".

---

## CRITICAL-1 — A dead or departed client's held session is never reaped. Session, acks and image leak forever, and the shard's intake capacity shrinks

`libs/gateway/src/ClientGateway.cpp:989` (`s->lastSeenNs = nowNs_;` in `produceFrameHeld_`), together with the ABORT at `:476`.

Aeron C driver source (conan `aeron587c0be5e0d59`, `aeron-driver/src/main/c/aeron_publication_image.c:893-935`):

- ACTIVE → DRAINING happens on the liveness timeout (no packets). That part works when the client dies.
- DRAINING → LINGER needs `aeron_publication_image_is_drained(image)`, which means every subscriber position must be `>= rcv_pos` (`aeron_publication_image.h:255-270`). **No timeout escapes DRAINING.**
- The subscriber-side `onUnavailableImage` is only sent from `aeron_driver_conductor_image_transition_to_linger` (`aeron_driver_conductor.c` ~1446). LINGER is never reached, so the gateway's `Image` stays in the subscription and remains pollable. `controlledImageWatch_.afterPoll` never sees it go.

The gateway's position for that image is pinned at the start of the aborted Produce frame, which is below `rcv_pos`. So the image stays in DRAINING forever. Every `doWork` re-delivers the same aborted frame, and `produceFrameHeld_` refreshes the lease each time. `reapExpired` (`:749-761`) never fires.

The other exits are closed too:
- **Release:** the worker's claim on the dead client's egress returns NOT_CONNECTED. `SessionAckSink` treats that as "keep queued" (`SessionAckSink.h:501`, `:186-191` → `blockedPass`). The acks never drain, so Held never clears.
- **SessionFailed:** this fires only on CLOSED or MAX_POSITION_EXCEEDED. NOT_CONNECTED is not fatal.
- **Disconnect:** it is queued behind the aborted Produce on the same image (`:457-459`), so it is never processed.

Before this commit the 10 s reap was the only way out. Now nothing gets out.

Failure scenarios:
1. **Crash.** A client is paused (acks held), then is SIGKILLed or its host dies. The session lives forever.
2. **Graceful close while paused.** The client sends Disconnect, then closes its publication. Disconnect never reaches `onFragment`. On the client driver the network publication stays in DRAINING (`aeron_network_publication.c:976-1001`: producer > sender, `has_receivers` true while the gateway image still exists). Same result.
3. **Restart churn.** Every crash or restart of a slow client leaks one session-table slot, one held image (its term buffers) and up to that session's owed acks in a worker's `SessionAckSink`. Those owed acks count against `kAckCapacity` (16384), and intake gates on that (`Worker.h:3346-3362`: `ackRoom_() = kAckCapacity − A − O`). Leaked owed acks therefore permanently cut the intake of **every** session on that worker. A few dead slow clients can starve the shard, which is the exact property `SlowEndpointUnawareClientCannotStarveTheShard` protects.

Proposed fix (state-driven, time-independent). Ground the extra lease on a real liveness signal, not on replayable buffered data:
- **Worker side (preferred):** for a session in `PubReady` that has been connected at least once, a claim of NOT_CONNECTED is Aeron's own connection-loss verdict. The worker's publication has lost its receiver's status messages. A live but stuck client process still sends SMs, because its driver does that whatever the app does. Treat it as `fail_(st)` → `reportFailures` → `SessionFailed` → `closeSession_`. A record-once `everConnected` bit in `PubReady` keeps the startup case ("client image not yet connected") queued as today. The publication's `isConnected()` could be used instead of the claim result.
- With that in place, the D8b refresh is safe to keep: a dead client is closed by the worker, independent of the image.
- Alternative without the worker change: refresh only while the worker reports the held session's publication connected (a Held signal carrying `connected`). Never refresh from the aborted frame alone.

Required test (per never-hand-over-untested-code): real-driver, default config.
1. Pause a client: hold acks with pending produce frames queued.
2. SIGKILL it, or close it without reading.
3. Assert the gateway session is closed and the worker's owed acks for it are freed within a bounded time.
4. Assert another session's intake on the same worker is not reduced.

Mark it `*Regression*`. As shown above, it fails against `982b50e`.

## MAJOR-1 — A live client that never reads egress holds its session and acks with no bound. Kafka bounds this case

`ClientGateway.cpp:989`, and the "never-drop, no timer" design in `SessionAckSink.h:24-28`.

Even after CRITICAL-1 is fixed, a stuck application (its driver alive and sending SMs, the app never polling egress) now keeps its session, its image and up to `kAckCapacity − O` owed acks on each worker indefinitely. Before this commit the 10 s reap capped that.

Kafka mutes the channel. `connections.max.idle.ms` (broker default 600000 ms) then closes a connection with no I/O activity, and a client that never reads a pending response counts as idle. Holding while the client drains slowly is correct, matching Kafka's muted channel. Holding forever with zero progress is not.

Proposed bound: progress-based, not a convergence timeout. While held, refresh the lease only on evidence of ack drain:
- the existing post-ack (deferAck) touch at `:3499`;
- or a Released edge;
- or a per-held-session "acks drained since last report" counter the worker already has at hand.

Then add a Kafka-parity `maxHeldIdleNs`, default 10 min and configurable: no ack drained for that long → close the session. This is an idle-resource policy like Kafka's, not a failover or convergence timer. It keeps the slow-but-progressing reader alive, so the D8b e2e still passes, and evicts the zero-progress one.

## MEDIUM-1 — The comment and commit message state a false Aeron guarantee

`ClientGateway.cpp:461-465` and `:985-988` say "a client that is gone leaves through the lease reap once Aeron drops its image". As shown in CRITICAL-1, Aeron never drops an image whose subscriber is stuck behind unconsumed data, so that never happens here. The same claim is in the test comment at `ShardNotifyTest.cpp:239-243`. Correct all three when CRITICAL-1 is fixed, or the invariant will be relied on again.

## LOW-1 — The regression test covers the unit mechanics only, not the scenario that matters

`libs/gateway/tests/gateway/ShardNotifyTest.cpp:244-260`.
- **RED without the fix:** confirmed. `injectTestSession(0)` gives `lastSeen = 0`. Without the store, `reapExpiredForTest(T+0.5s)` reaps `a`, so `EXPECT_GE(... a ..., 0)` fails. With the fix `lastSeen = T−1ms` and `a` survives.

- **Gaps:**

  - Nothing covers the client going away while held (CRITICAL-1) or a held client with zero progress (MAJOR-1). Add the real-driver test described in CRITICAL-1.
  - Optionally add a test that uses `doWork(now)` itself, so the `nowNs_` ordering is proven by the test rather than by inspection.

## LOW-2 — Lease refresh rate depends on poll cadence (informational)

The refresh happens only when `controlledPoll` reaches the held image. Round-robin over images with `fragmentLimit_` (default 256) means the head frame is re-polled every cycle in practice. A gateway saturated by many images could still go a cycle or more without visiting it, which matters only if a cycle ever approaches the 10 s lease. Accept as is. Note it if the refresh becomes the sole liveness source.

## Checked and OK

- **(2) `nowNs_` freshness.** `doWork` sets `nowNs_ = nowNs` first (`:395`), before `drainWorkerReturns_`, the controlled poll (`:466`) and `reapExpired(nowNs)` (`:505`). They all use the same cycle timestamp. A frame refreshed in this cycle has `nowNs - lastSeenNs == 0` at the reap. There is no staleness or ordering hazard.
- **(3) Other close paths.**
  - Disconnect, reap and SessionFailed all go through `closeSession_` (`:942-972`), which decrements `heldSessions_` and announces the close to the workers.
  - On a SessionFailed for a held session, the next poll finds no session, so the frame CONTINUEs to `handleProduce`'s unknown-session path and the image drains. That is correct.
  - The only paths that lose acks are the ones in CRITICAL-1 and MAJOR-1: Disconnect stuck behind the ABORT, and NOT_CONNECTED treated as non-fatal.
  - Worker-side close is runtime-driven only.
- **(5) Hot path.**
  - The cost is one plain store into the `Session` already found by `sessions_.find`, on an `[[unlikely]]` branch gated by `heldSessions_ != 0` and `heldByWorkers != 0`.
  - No atomics, no allocation, no virtual calls, and no new cache line touched (`lastSeenNs` is in the looked-up `Session`).
  - The const-to-mutable `Session*` change is harmless.

Read-only, 2026-10-04. Scope: the fix round over `982b50e`.

## Verdict: REQUEST CHANGES (0 CRITICAL, 1 MAJOR, 3 MEDIUM, 3 LOW)

Status of the earlier findings:
- **CRITICAL-1: resolved.** The abort-frame refresh is reverted (`ClientGateway.cpp:985-988`). A held dead client is now released in two ways:
  - The worker fails it. About 5 s after its SMs stop, Aeron reports NOT_CONNECTED (`aeron_network_publication.c:518` `has_receivers=false` → `:956-960` `is_connected=false`). The sink then runs `fail_` → `reportFailures` → `SessionFailed` → `closeSession_`. On the next poll the stuck frame finds no session, CONTINUEs, and the image drains to LINGER.
  - Or the 10-min held bound fires.
- **MAJOR-1: resolved in substance.** There is now a 10-min bound, `reapExpired` `:756`. It is measured from the last ack *enqueue*, though, not from the last ack *read*. See MEDIUM-A.
- **MEDIUM-1: partly resolved.** The false Aeron image claim is gone. Two new false claims replace it (MEDIUM-B).

## MAJOR-A — "NOT_CONNECTED after delivered = dead" also kills live clients whose Aeron driver stops sending status messages for 5 s

`libs/node/include/rune/node/SessionAckSink.h:189` (plus the comment at `:91-93`).

NOT_CONNECTED on a network publication means exactly one thing: no status message for `publication_connection_timeout` (Aeron default **5 s**, `aeron_driver_context.c:299`; the broker does not override it).

- SMs come from the *client's driver receiver*, whatever the client application is doing. So a Thread-mode client whose app thread is merely busy is safe. Its receiver keeps sending SMs with a closed window, the claim returns BACK_PRESSURED, and the session is held as intended.
- The receiver only runs when something pumps it, and rune-client-cpp has exactly that mode (`TransportConfig.h:23-27`, `Client.cpp:103-106`):
  - **`RunnerMode::Invoker`:** the app thread pumps the embedded driver *and* the conductor through `dutyCycle()`.
  - **`driverOnDutyThread`**, which shard clients force on: the runner thread pumps them.
- In those modes, "the client stops reading its acks" means it stops calling `doWork()`. That stops the receiver, so no SMs go out, and 5 s later the claim returns NOT_CONNECTED.

Failure scenarios:
1. **Paused Invoker client.** A RunnerMode::Invoker bench pauses pumping while it has acks pending, which is exactly the D8b slow/paused reader. After 5 s:
   - the session is failed and its owed acks are dropped;
   - SessionExpired is sent, and the client reconnects (`reconnectForeverAfterLive`).

   Data was appended but never acked. A non-idempotent producer retries and creates duplicates. This is the D8b symptom ("paused client lost every queued ack") moved from the gateway lease to the worker, and the timeout is now 5 s instead of 10 s.
2. **Stalled runner thread.** A shard client whose runner thread blocks for more than 5 s (a user callback on the runner, or a host stall) gets the same result.
3. **Network blip.** A Thread-mode client hit by a network partition or blip of more than 5 s between broker and client: a transient becomes session death, which is harsher than the 10 s lease. Kafka tolerates this up to `request.timeout.ms`.

The test that motivated D8b (`ShardModeTest.cpp:1296`) uses `ShardTestClient` with `DriverMode::Threaded` (`ShardTestClient.h:~88`). It keeps sending SMs and never hits this path, so the green run says nothing about Invoker clients.

Context. A non-held client that stops pumping is reaped on the 10 s lease anyway, because it sends no keepalives. So for a client that is not pumping, the change shortens tolerance from 10 s to 5 s rather than creating a new class of failure. But the commit's stated contract ("a live slow reader stays connected and back-pressures") is false for Invoker clients. The hole is also wider than the lease's, because it fires on any NOT_CONNECTED edge, including transient ones.

Proposed guard. Treat NOT_CONNECTED as suspicion, not a verdict.
- Replace the immediate `fail_` with a `PubLost` sub-state, or a `lostSincePass`/`lostSinceNs` field in `PubReady`. Acks stay queued. A later successful claim moves it back to Ready.
- Fail only if NOT_CONNECTED persists for a bound. For consistency, use the normal session lease, `sessionTimeoutNs` (10 s). The worker could instead report a `Lost` edge, like Held, and the gateway would reap a held-but-Lost session on `sessionTimeoutNs_` rather than `maxHeldIdleNs_`. That keeps timers out of the worker.
- This caps a dead client's acks at about 5 s + 10 s against `kAckCapacity`, which is fine, and survives transients. It is an idle-resource policy, not a convergence timer, so the time-independence rule is not violated.
- Alternatively, keep the rule but document it as a contract: "a held client must keep its Aeron runtime pumped; more than 5 s without pumping = dead". Fix the `:91-93` comment either way.

## MEDIUM-A — "Reading acks refreshes the lease" does not happen. A held reader that is making progress is reaped 10 min after its hold began

Where the claim is made:
- `ClientGateway.cpp:461-462` ("refreshed by the post-ack notifications of the acks it does read");
- `ShardNotifyTest.cpp:242`;
- the commit message.

Why it is false:
- The deferAck notification is emitted at ack **enqueue** (`Worker.h:1444-1470`, "m1: queued at ack ENQUEUE, i.e. before the ack is claimed"). It is not emitted when the client reads.
- While a session is held, its intake is paused, so no new produces are processed and no new acks are enqueued. Only already-appended acks=all acks can still fire, within milliseconds.
- Neither the `Held` nor the `Released` edge touches `lastSeenNs` (`ClientGateway.cpp:1006-1018`).

So `lastSeenNs` is frozen at about the moment the hold starts, whatever the client drains. A session held *continuously* for 10 min is reaped even though it is reading. That takes a reader slower than about `held acks / 600 s`, e.g. < ~27 acks/s with 16k owed. This is an edge case, but it is exactly the "slow but progressing" reader MAJOR-1 asked to keep.

The Released edge is safe: on the cycle the hold clears, the head Produce goes through `handleProduce`, which sets `lastSeenNs` (`:1614`) before `reapExpired` (`:505`).

Fix:
1. Make the sink count acks claimed for a session in `heldPass_` (a `progressedWhileHeld` bit).
2. Have `reportHoldChanges` re-emit `Held` as a progress tick when that bit is set. Rate-limit it, e.g. at most once per N passes or once per 1024 claimed acks.
3. On that tick, the gateway touches `lastSeenNs`.

Or at least fix the comments to say "10 min from hold start" and accept that.

## MEDIUM-B — The rule change is not reflected in the sink's contract header, and two new false comments were added

- `SessionAckSink.h:24-41` still says: "An ack that cannot be claimed (back-pressured, or the client image not yet connected) stays queued … for as long as it takes". It also omits NOT_CONNECTED-after-delivered from its list of "dropped only on STATE events".
- `:91-93`: "a live slow reader stays connected and back-pressures" is false for invoker-driven clients (MAJOR-A).
- `ClientGateway.cpp:461-462` and `ShardNotifyTest.cpp:242`: "reading acks refreshes the lease" (MEDIUM-A).

This is the same class of problem as the old MEDIUM-1: invariants that are documented but untrue get relied on.

## MEDIUM-C — A held session whose ack publication never connects keeps its owed acks against `kAckCapacity` for the full 10 min

Where: `SessionAckSink.h:189`. The `delivered == false` branch keeps waiting, and held then gets `maxHeldIdleNs_` (`ClientGateway.cpp:756`).

Two ways it happens:
- A client whose egress endpoint the broker cannot reach (NAT, firewall, wrong advertised host).
- A client that dies after being accepted but before its first ack is claimed.

Either way the client sends produces, every ack hits NOT_CONNECTED, and the worker reports Held. Its owed acks then occupy the worker-wide `ackRoom_` budget for 10 min, where it used to be 10 s.

On the gateway-routed path, the number owed before the pause lands is the pipeline depth (the KNOWN ISSUE in `ShardModeTest.cpp:1318-1327` measured bursts of tens of thousands with the derived transport). A handful of such clients can cut every session's intake on that worker, which is the `SlowEndpointUnawareClientCannotStarveTheShard` property.

Fix: a session held only because its publication never connected should get the normal `sessionTimeoutNs_`, not `maxHeldIdleNs_`. Report the hold reason with the Held signal, e.g. `Held{neverConnected}`, or treat the never-connected case as Lost under MAJOR-A's scheme. A live client with a reachable egress connects within milliseconds, so this costs it nothing.

## LOW-B — `RUNE_MAX_HELD_IDLE_MS` overflows and has no upper bound

`NodeConfig.cpp:1171-1178` accepts any positive `long long`. `BrokerNode.cpp:1574` computes `maxHeldIdleMs * 1'000'000LL`, which is signed overflow (UB) above ~9.2e12 ms. Cap the value, e.g. at 1 h like the client's liveness cap, and reject anything above. There is also no parse test.

## Checked and OK

- The Released edge does not cause a spurious reap. Within the same `doWork`, `drainWorkerReturns_` clears `heldByWorkers`, then the controlled poll processes the head Produce and touches the session (`:1614`), then `reapExpired` runs.
- `fail_` handles a session with acks queued. The failing ack and every later ack of that session are dropped (`PubFailed` branch). `reportFailures` → gateway `onSessionSignal_` Failed → `closeSession_` (decrements `heldSessions_`, announces close) → the stuck frame CONTINUEs to the unknown-session path → the image drains. Claims are retried on every pass, so NOT_CONNECTED is observed within one pass of the Aeron transition.
