# D24 review: durable follow floor, legacy-plane re-add, multi-A pinning (2026-10-08)

Scope: the uncommitted D24 change on `integ/perf-defaults` (wt26), as captured in
`2026-10-08-d24-diff.patch`. The Worker.h, PartitionReplica and storage hunks in the
working tree belong to D26 and are out of scope here.

This was a read-only review: nothing was built or run. Line numbers refer to the
working tree.

## Verdict

- **The core safety argument for (a) is correct.** A term in which this node's only
  participation was its own failed candidacy, or a denial, cannot have a leader
  whose majority contains this node. So following an older term's leader cannot
  create a majority that intersects a newer leader's majority *only* at this node.
  Every other intersection node granted the newer term and refuses the older
  term's acks.
- **The raise ordering is right on every site.** The durable raise happens before
  any message that lets another node rely on this node: the Vote, the
  LeaderLogReplication NLT, and the FollowerReady AppendPosition.
- **Two problems remain:**
  - The floor is loaded only in `init()`, which a startup race can skip. That
    reopens the MAJOR-1 counterexample.
  - The relaxation also applies in CANDIDATE_BALLOT. That creates a new stranding
    in exactly the DR-4 topology. On top of this, the "granted a failed ballot"
    stranding is still unaddressed.
- **(b) has one race that defeats its own purpose:** `release()` copies the pointer
  and then resets it.
- **(c) is fine.**

## MAJOR

### MAJOR-1: The follow floor and the ack term are loaded only in `init()`, and an NLT delivered in INIT skips `init()` (Election.cpp:288-297, 895-921)

**What happens:**

1. `NodeConsensusAgent::doWork` polls ingress, then calls `ConsensusAgent::doWork`.
2. `ConsensusAgent::doWork` drains the ingress ring before `election_.doWork()`
   (ConsensusAgent.cpp:40-63).
3. So on the first duty cycle after a restart, any queued frame reaches the
   Election while `state_ == Init`. The AeronIngress subscription is created in
   `buildMultiNodeConsensus` long before the runner starts, and a live leader sends
   an NLT every status interval, so on a restart next to a live leader this is the
   expected case, not an edge case.
4. `onCanvassPosition` and `onRequestVote` return in INIT (lines 708, 742), but
   `onNewLeadershipTerm` does not:
   - INIT is not in `inAcceptingState`, so the NLT takes the A1 "leader state"
     branch.
   - In production `leadershipTermId_` is always 0 after a restart: BrokerNode.cpp
     630/717 construct the Election with `leadershipTermId=0`, not the TermLog
     value. So `leadershipTermIdArg > leadershipTermId_` holds for every NLT.
   - The branch calls `raiseFollowFloor_(T)`, sets `leadershipTermId_ = T`, and goes
     straight to CANVASS. **`init()` never runs.**

**Consequences:**

- `followFloorTermId_` is `max(-1, T) = T` in memory. The on-disk floor F is never
  read. The file itself stays at F, because `proposeMaxFollowFloorTermId` only
  raises.
- `votedTermId_` is never restored from the floor, so the AckTerm strengthening is
  lost.
- `candidateTermId_` happens to come out right, because the proposeMax return value
  is max'd in.

**Failure scenario:** this is the review's own MAJOR-1 counterexample, reached
through a different door.

1. X grants term 4 (on-disk floor = 4) and crashes.
2. On restart, the first ingress poll carries the zombie Y's heartbeat NLT for
   term 3. The A1 branch sets the in-memory floor to 3 and moves X to CANVASS.
3. The next NLT for term 3 passes `3 < followFloorTermId_(3)`, which is false, so X
   follows Y.
4. `ackTermId()` = max(0, 3), so X acks the zombie's internal-ISR states.
5. Y commits through {Y, X} while Z has already appended a term-4 entry.

The result is the silent committed loss that MAJOR-1 described.

Before D24 this race was harmless for this purpose: the stale-ballot gate used
`candidateTermId_`, which the proposeMax return value restored. D24 moved the gate
onto a field that only `init()` loads.

**Fix (do both):**

- Load `followFloorTermId_` and `votedTermId_` from the NodeStateFile in the
  **constructor**, so no handler can observe the unloaded values.
- Add `if (state_ == ElectionState::Init) return;` to `onNewLeadershipTerm`, and
  also to `onCommitPosition` for symmetry. This matches the existing INIT guards in
  `onCanvassPosition` and `onRequestVote` (Aeron: no election message is processed
  before INIT runs). A dropped NLT costs nothing, because the leader re-sends it on
  the status interval.
- Regression test: construct the Election from a NodeStateFile with floor 4 and
  `leadershipTermId=0`. Deliver an NLT for term 3 **before** the first `doWork`,
  then keep heartbeating term 3. Assert that the node never follows and that
  `votedTermId() >= 4`.

### MAJOR-2: The relaxation also applies in CANDIDATE_BALLOT, so a candidate holding a granted quorum abandons it for a lower-term leader and strands its voters. This is a new stranding in the DR-4 topology (Election.cpp:895-899, 956-966)

`inAcceptingState` includes `CandidateBallot`. So with D24, a node that is
mid-ballot at C follows any leader at a term T where floor ≤ T < C. It does this
even after peers granted it C. Those peers raised their floors to C, and they can
now never follow T.

**3-node failure scenario (A, B, C; this is DR-4: B and C restarted, with
misrouting while re-resolving):**

1. A leads T.
2. B canvasses and stands at T+1. C, not sticky because it just restarted, grants
   it: C's floor is now T+1. C's Vote reaches B, so B holds the quorum {B, C}.
   - The unanimous check fails because A did not vote, so B waits for the ballot
     timeout before `isQuorumLeader` fires.
3. Within that window, A's NLT for T reaches B (routing is fixed by then).
   - The new gate admits it: B's floor is T, or 0 on a legacy file.
   - B follows A at T.
4. C refuses A's NLT forever, because T < floor T+1.
5. C's candidacies at T+2 and above are denied:
   - by A, which is a sticky leader with the active quorum {A, B};
   - by B, which is a sticky follower.
6. C is stranded until A dies.

**Before D24,** B refused the stale NLT, won T+1 at the timeout, and A stepped down
on the T+1 NLT (A1). The cluster converged.

So D24 swaps the old stranding (B's own failed candidacy) for a new one in the very
scenario it targets. Whether you hit it depends only on whether A's heartbeat lands
inside B's ballot window. That violates time-independent convergence.

**Fix:**

- Apply the floor relaxation only where this node has no open ballot of its own:
  CANVASS and NOMINATE. In NOMINATE, `candidateTermId_` comes from an
  already-closed candidacy.
- In CANDIDATE_BALLOT, keep `nextLeadershipTermId < candidateTermId_ → return`.
- The ballot ends in bounded time either way:
  - **won:** the T leader steps down via A1;
  - **failed:** back to CANVASS, and the next heartbeat is accepted.
- Regression test: B is in CandidateBallot at T+1 with a For vote from C. An NLT
  for T arrives before the ballot timeout. Assert that B becomes leader of T+1 at
  the timeout.

### MAJOR-3: Residual stranding: any node that GRANTED a ballot that then failed is stranded while the old leader keeps a quorum without it. This is not closed, and it is timing-dependent (Election.cpp:956-966; pre-existing class, still open)

The floor rises on a grant whether or not the candidate wins. Any node V that
granted C to a candidate that did not win refuses the T leader's NLTs for good. V's
own candidacies are then denied by the stickiness of the leader and of every live
follower.

**Reachable cases:**

- **3 nodes:** a single grant is already a quorum, so this needs the Vote to be
  lost (the misrouting case from DR-4).
- **3 nodes, after MAJOR-2 is fixed:** the candidate can still fail at the timeout
  if the vote arrives late.
- **5 nodes:** a partial partition {X, V} | {L, A, B} heals after X stands and V
  grants. X follows L again under D24, because X's own candidacy did not raise its
  floor. V is stranded.

**Impact:** V stays stranded after connectivity is fully restored, until the leader
dies. Meanwhile:

- the cluster runs one node short of its fault tolerance;
- V's partition replicas fail over away from it.

**Comparison with Raft and etcd:**

- **Raft without CheckQuorum:** V's higher-term RequestVote deposes the leader, and
  the cluster converges at a term above C.
- **etcd with CheckQuorum** (raft.go, the "leader at a lower term" branch): V
  answers the stale leader's MsgApp/heartbeat with an MsgAppResp at its higher term.
  The leader steps down, and the next election takes V back in.
- **Rune:** has neither mechanism. So V's stranding is strictly worse than both
  references. The prior review's option (b) is the missing half.

**Fix (option (b), narrowed to the floor so stickiness stays meaningful):**

1. A CANVASS node whose floor F is above an NLT's term T answers that leader with
   its floor. It can carry F in the CanvassPosition `leadershipTermId` field it
   sends, or in a dedicated message.
2. A leader, in CLOSED or a leader state, that learns a member's floor F is above
   its own term adopts F (`leaveClosedForElection_(F)`).
3. This is not suppressed by stickiness. A floor rises only through a real grant,
   lead, follow or leader announcement, so this is not the partial-partition
   ping-pong that stickiness guards against. Each round needs a fresh real grant.
4. A new election at a term above F then includes V.

**Regression test:** 5 nodes. V grants X's T+1, and X's ballot fails. L keeps
heartbeating T with an active quorum. Assert that V reaches CLOSED under some leader
with no node dying.

If you defer this, record it in the backlog. Note that D24 closes MEDIUM-3 only for
the "own failed candidacy" case.

## MEDIUM

### MEDIUM-1: Upgrade window: a pre-D24 NodeStateFile reads floor 0, so the first post-upgrade restart has no floor at all (NodeStateFile.cpp:161-163, Election.cpp:295)

On an old 64-byte file, slot 24 reads 0. Combined with the production
`leadershipTermId_ = 0` at restart, **every** NLT passes the gate on that first boot.

**Failure scenario:**

1. A node granted T+1 under the old binary. Its candidate term is T+1 and its floor
   slot is 0.
2. It crashes and is upgraded to D24.
3. It follows the zombie T leader. This is exactly the MAJOR-1 counterexample.
   Before D24 it was refused, because the stale-ballot rule used the candidate term.

**Fix:**

- Mark migration explicitly: write a magic/version word in slot 32.
- On a file without the marker, set floor := candidateTermId. That is conservative:
  it reproduces the pre-D24 refusal once, and the floor only rises from there.
- Write the marker with the same sync.

### MEDIUM-2: `PubAddBroker::release` copies the PubPtr and then resets the caller's copy, so the LAST reference can still drop on the worker (PubAddBroker.h:71-79)

**The race:**

1. `holder = new PubPtr(pub)` sets the refcount to 2.
2. `req_.offer(...)` publishes the holder.
3. The control thread can poll and delete the holder immediately, which brings the
   refcount back to 1.
4. The worker's `pub.reset()` then drops it to 0. `~ExclusivePublication` →
   `ClientConductor::releaseExclusivePublication` takes the node client's admin
   `recursive_mutex` on the **worker**.

That is the exact path MEDIUM-2 asked you to remove. The window is a few
instructions wide, but it opens on every IP-change re-add of a legacy plane. This is
not a memory-safety problem (shared_ptr control blocks are atomic); it is a
lock-discipline violation.

**Fix:** move the reference into the holder before offering, and restore it on
failure:

```cpp
PubPtr* holder = nullptr;
try { holder = new PubPtr(std::move(pub)); } catch (...) { return false; }   // pub untouched on throw
if (!req_.offer(kRelease, 0, ...)) { pub = std::move(*holder); delete holder; return false; }
return true;
```

The worker then never holds a reference after the offer.

**Test:** assert `pub.use_count() == 1` inside the holder, or instrument the
release-thread id. The current test cannot see the race (see LOW-7).

### MEDIUM-3: The tests do not pin several of the raise sites they claim to cover, and there are no NodeStateFile tests for the new slot (ElectionLogTest.cpp:2640-2750)

**`RefusesStaleLeaderAfterFollowingNewerTermRegression` (2724) does not test the
follow-site raise (Election.cpp:988):**

- The first NLT (term 4) arrives with `candidateTermId_ = 2`, so the
  `nextLeadershipTermId > candidateTermId_` **adoption** raise (line 955) fires
  first.
- The test stays green if line 988 is deleted.
- The follow-site raise matters only when the followed term is at or below
  `candidateTermId_`. That covers both the `==` case and D24's new `<` case. In the
  `<` case it is what makes a node that followed T after its own failed candidacy
  durably refuse a T-1 zombie.
- **Fix:** make the node fail a candidacy at 5, then follow 4 (relaxed path),
  restart, NLT 3. Assert the node refuses.

**Win sites:**

- `RefusesStaleLeaderAfterLeadingNewerTermRegression` reaches the leader through
  `bringToLeaderLogReplication`, which uses unanimous votes. Only line 428 is
  pinned.
- The quorum-after-timeout site (line 441) and the single-node site (line 303) are
  not exercised.

**`FollowsLeaderAfterOwnFailedCandidaciesRegression` (2640):**

- It rebuilds the Election with `leadershipTermId = term`. Production always passes
  0.
- Add a production-faithful variant with `leadershipTermId = 0`. That is also the
  configuration in which MAJOR-1 and MEDIUM-1 bite.

**NodeStateFile has no tests for `proposeMaxFollowFloorTermId`.** Missing cases:

- fresh file → floor -1;
- 64-byte legacy file (zero slot 24) → floor 0, or the migrated value after the
  MEDIUM-1 fix;
- floor-only raise (candidate already higher) still syncs and persists;
- candidate-only raise;
- reopen round-trip;
- the return value.

Also missing: the MAJOR-1 INIT-race test and the MAJOR-2 CandidateBallot test.

## LOW

- **LOW-1 (Election.cpp:303, 426-428, 439-441, 985-988).** `leaderMember_` and
  `leadershipTermId_` are assigned *before* `raiseFollowFloor_`, which can throw on
  msync/fsync failure. Today an exception is fatal, because nothing in the agent
  catches it, so this is moot. Raise first anyway, so an Election is never left
  claiming to follow or lead a term whose floor did not persist.
- **LOW-2 (Election.cpp:290-292).** For defence in depth against a torn or partial
  state file, use `candidateTermId_ = max(persisted candidate, leadershipTermId_,
  floor)`. Also apply the floor check in the `nextLeadershipTermId ==
  candidateTermId_` case. Today that case is safe only because floor ≤ candidate
  always holds in memory. A floor above the candidate would also let `nominate()`
  stand at a term the node already granted in.
- **LOW-3 (Election.cpp:1227-1237).** The doc comment for `leaveClosedForElection_`
  now sits above `raiseFollowFloor_`. Move it back.
- **LOW-4 (NodeStateFile.h:21-25).** The class-comment layout still says `[24..]
  padding`. Document slot 24 (follow floor, NULL_VALUE fresh, 0 on legacy files)
  and the write order.
- **LOW-5 (Election.cpp:913-916).** The A1 branch raises the durable floor for an
  NLT whose sender is never checked with `memberById`. This was pre-existing for the
  candidate term, but the floor now gates following. Check membership first.
- **LOW-6 (WorkerReplicationTransport.h:441-444).** The LOW-7 comment and the
  `static_assert` still say "one outstanding broker request per peer". A
  legacy-plane IP change now queues kRelease plus kAdd, so two per peer. 2 × 16 =
  32 still fits ControlRing<1024>'s 42 records, so assert `2 * kMaxPeers <= 1024 /
  24` and update the comment. Ring-full is handled correctly: the release fails, the
  stale pub is kept, and it is retried on the next confirmation.
- **LOW-7 (UnresolvedPeerRegressionTest.cpp:640-672).**
  `LegacyPlaneReAddsOnPeerIpChangeViaTheControlThreadRegression` drives
  `broker.doWork` and the owner on one thread, so it proves "through the broker",
  not "on the control thread".
  - `releasesForTest()` counts deleted holders, not last references (it misses
    MEDIUM-2).
  - The ring-full release path and the in-flight (kBrokered) IP change are not
    covered.

  The numeric-endpoint assertion (`127.0.0.2`) is good: it closes prior LOW-4 for
  this plane.
- **LOW-8 (UnresolvedPeerRegressionTest.cpp:674-700).**
  `MultiARecordHostKeepsItsAddressRegression` tests `pickAddress` and the hub's
  in/out plumbing through a test lambda. Two gaps:
  - Nothing covers the record collection in `resolveWithGetaddrinfo`.
  - It does not assert the actual symptom: no resolution event or generation bump,
    so no owner re-add, across the rotated re-checks. Add an owner subscription and
    assert that its generation is unchanged.
- **LOW-9 (PeerResolverHub.cpp:69-70).** `serveHostRequests_` (the driver
  name-resolver port) still calls `fn_` with `ip = 0`, so for a multi-A host it

  owners and the driver cache. Pass the hub's current address for that host when it
  is known. Callers that ignore the input, such as the ShardModeTest resolve
  lambdas, are unaffected by the new in/out convention.
- **LOW-10 (PubAddBroker.h:499-505 vs PeerResolution.h:181-189).**
  `numericChannel_` duplicates `PeerResolutionInbox::addChannel`. Factor out one
  helper.
  - Semantic note on `pickAddress`: while a DNS view still lists the *old* address

    Docker/k8s IP swap, that old address may belong to another member. Per-pod and
    per-container names return a single record, so this is acceptable; document it.
  - Pre-existing: `onBrokerResult_` with no matching kBrokered entry destroys the
    node-client pub on the worker. That is unreachable today.

## Answers to the brief's questions

**1. Safety argument.**
- **Holds:** it holds in 3- and 5-node clusters, through crashes on either side of
  the floor sync (the sync precedes every dependent message), and through StandDown,
  ClosedLeaderStepDown, the unanimous shortcut and single-node.
- **Complete for every term-setting site:**
  - grant;
  - the three win sites;
  - follow;
  - the A1 NLT and A1 CommitPosition paths;
  - `leaveClosedForElection_` with a higher term;
  - the `>` adoption.
- **Need no raise:**
  - `onCommitPosition` outside leader/CLOSED states (it never changes the term);
  - FollowerReplay and FollowerLogInit (no term change);
  - the TermLog append at `electionComplete` (the floor is already raised).
- **Breaks only when the floor is not loaded:** MAJOR-1, the INIT race, and
  MEDIUM-1, legacy files.

**2. Crash consistency.**
- The store order (floor, then metadata, then a compiler barrier, then the
  candidate) and the single msync+fsync are fine. Both slots sit in one 64-byte
  region, so they share one sector and one page.
- A fresh file gets -1; a legacy file reads 0 (see MEDIUM-1).
- Durability under `fileSyncLevel=0` is no worse than before.

**3. Liveness.**
- **Converges:** the own-failed-candidacy case (MEDIUM-3) and the DR-4 case where
  only the restarted node stood.
- **Does not converge:**
  - the DR-4 case where the restarted node granted and the ballot was then abandoned
    (MAJOR-2) or failed (MAJOR-3).
  - Both depend on timing and persist after the network heals, which is worse than
    Raft and etcd.

**4. Restoring `votedTermId_` from the floor.**
- **No freeze.** Every value of the floor is a term this node granted in, or in
  which a real leader announced itself.
- The node only leads or follows at terms at or above its floor, so its own live
  leader's internal-ISR epoch is never below `ackTermId()`.
- While canvassing, it refuses more than before (knowledge via `adopt()` is
  unaffected). That is conservative.

**5. (b).**
- Holder lifetime is correct through the ring, through ring-full (the copy is
  deleted and the caller keeps the pub), and through the destructor (holders are
  drained while the node client is still alive; BrokerNode.cpp:3199-3203 clears the
  brokers before `aeron_.reset()`).
- No double re-adds: a kBrokered peer has a null pub and is skipped.
- An in-flight add that completes on the stale address is fixed by the next
  confirmation.
- The worker-side last-reference race is MEDIUM-2.

**6. (c).**
- `pickAddress` is correct.
- No ResolveFn caller relied on output-only semantics in a way that breaks.
- The only inconsistent caller is the driver resolver port (LOW-9).

**7. Tests.** See MEDIUM-3, LOW-7 and LOW-8.
- The Stranded* positive test is genuinely RED before the change.
- The three negative tests pin the grant, the unanimous win and the adoption raise.
- They do not pin the follow raise or the other win sites.
