## 1. What was built

- **Coordinator side (gateway).** `ClientGateway::appendControlRecord` looks up the partition's leader in the routing image.
  - Local leader: the existing path, through the worker op ring.
  - Remote leader: the marker goes into the same `markersInFlight_` table as a local marker. The entry gets `remoteNode` and `remoteLeaderEpoch`. A `WriteTxnMarkerMsg` is sent over the cluster plane and the call returns `kControlRecordAsync`.
  - The `WriteTxnMarkerResponseMsg` is handled by the same completion as a local marker: `onControlMarkerLanded`, or `onControlMarkerRefused` on refusal.
- **Event-driven convergence.** `setRoutingImageSnapshot` checks every remote marker in flight. If the partition's leader node **or leader epoch** changed, the marker completes NotLeader at once. The TCS retry then re-resolves the leader, which may now be local. No timeout decides correctness.
- **Leader side.** `ClientGateway::appendRemoteControlRecord(const WriteTxnMarkerMsg&)` uses the same owning-worker op-ring path as a local marker.
  - The entry records `originNode` and `originToken`.
  - When the worker reports `ControlRecordAppended`, or refuses the marker, the gateway answers the origin node. The local TCS is never called.
  - If this node is not the leader (stale routing at the coordinator, no log, or an empty marker), it answers NotLeader immediately.
- **Transport.** `AeronPartitionTransport` gains:
  - `sendWriteTxnMarker` and `sendWriteTxnMarkerResponse`, which use the MPSC outbound ring;
  - function-pointer handlers set with `setTxnMarkerHandlers(fn, fn, ctx)`, which follow the `alterIsrHandler_` pattern (no virtual calls, no `std::function`);
  - dispatch for both messages in `handleFrame_`.
- **Wiring.** `BrokerNode` connects the gateway's `TxnMarkerChannel` to the transport and the transport's handlers to the gateway. Both run on the runtime thread. The handlers are cleared before the gateway is destroyed.
- **Stuck-markers gauge.** `TransactionCoordinationService::stuckMarkers()` counts markers that have been refused for more than `kStuckMarkerNs` (5 s) and are still retrying.
  - It is recomputed on each `doWork`.
  - A warning is logged when it rises from 0 and an info line when it returns to 0.
  - It resets on load and unload.

The TCS retry and dispatch logic itself is unchanged.

## 2. Deviations and gap-fills (and why)

1. **Message codecs are hand-rolled in the broker, not added to the SBE schema.** They are template ids 11 and 12, placed next to `AlterIsrMsg` in `ReplicationMessages.h`, little-endian, in the same style as `PlaneHello`.
   - `WriteTxnMarkerMsg` has a 40 B fixed block plus up to 128 B of marker. `WriteTxnMarkerResponseMsg` has a 40 B fixed block. The fields are exactly the spec's.
   - **rune-protocol was not modified.** If you want these in `schema/rune-replication.xml` as generated codecs, that edit belongs in rune-protocol. Ids 11 and 12 are free there today and should be reserved.
   - `WriteTxnMarkersRequestMsg` (TransactionMessages.h) was **not reused**. It has no token, uses topic *names*, allocates a vector on decode and handles many partitions per request, so it does not fit the spec's per-partition token protocol. It is still unwired.
2. **A change of leader epoch also fails in-flight markers, not only a change of leader node.** If the same node is re-elected or restarts, a request it may have lost is re-sent without waiting. The duplicate is harmless (spec §3) and is ordered behind the original on the same per-peer publication.
3. **Lost frames with no leadership change.** The spec says the TCS retry re-sends these, but the TCS only retries after a *refusal*. An unanswered remote marker would never be refused, so it would hang forever (for example, a frame the hold router drops for a peer it sees as down, while metadata keeps that peer as leader).
   - Gap-fill: the gateway completes a remote marker as a retriable NotLeader after `kRemoteMarkerUnansweredNs` = 1 s. This equals the spec's `kMarkerRetryMaxNs`. The sweep runs at most every 100 ms.
   - **This is a liveness safety net only.** Markers are idempotent and stay ordered per peer, so correctness never depends on it. Leadership changes still converge through the event above.
4. **The leader never answers UnknownTopic or UnknownPartition.** The TCS drops a marker on those codes. A leader whose topic registry is lagging has not proved the partition is gone, so every "not here" case answers NotLeader.
5. **The coordinator's unload purge (`purgeQueuedMarkers`) skips remote-origin entries.** They belong to another coordinator's epoch space. Without this, a coordinator unloading on node X would silently drop markers that X is appending on behalf of node Y.
6. **Remote-origin answers are never dropped.** If the outbound ring cannot take an answer, it is queued in `pendingMarkerResponses_` (FIFO) and pumped on each `doWork`. This is the response-side equivalent of the spec's "never dropped" rule.
7. **A small refactor.** The inline (no worker pool) append was extracted into `appendControlRecordInline_` so the leader-side handler can reuse it in unit rigs. The marker step of `doWork` was extracted into `pumpTxnMarkers_()`, with a `pumpTxnMarkersForTest` hook, because test gateways have no Aeron subscription to poll.
8. **TCS log change.** The "still refused, retrying every 1000 ms" warning used to fire on *every* retry once at maximum backoff. It now fires once per marker, when the backoff first reaches the maximum, which is what the spec describes as existing behaviour.
9. **"Exposed via the existing metrics/log path."** The broker has no metrics registry, so the gauge is an accessor plus the rise and clear log lines.
10. **`setRoutingImageSnapshot` is no longer `noexcept`.** It can now call into the TCS, which may allocate. It is cold and its version is gated in `NodeRuntimeAgent`.

## What changed, finding by finding

**MAJOR-1: the 1 s fallback is gone.**
- A remote marker keeps its token until a real answer arrives or the partition's leadership changes. No timeout constant decides completion.
- `AeronPartitionTransport::notePlaneReconnects_()` runs in `poll()`. It reports two events through a function-pointer handler, `setPlaneReconnectHandler`:
  - **(a) a down→up edge for a peer.** This is the existing hold-router connection-generation bump. Down peers are probed through `pub->isConnected()`, so the edge does not wait for unrelated traffic.
  - **(b) a new inbound image** (`imageCount` grew), reported as peer `-1`.
- `ClientGateway::onPlaneReconnect` marks the matching remote markers. The next marker pump re-sends every *sent* one with the **same token**. If the outbound ring is full, the re-send goes into `markerSendQueue_`.
- On the leader, a copy that is still in flight there (same origin, token and coordinator epoch), or whose answer is still queued, is skipped. A copy arriving after the answer is appended again, which is harmless (§3), and answered again.
- A late answer for a token that is still tracked completes the marker.

**MAJOR-2: coordinator-epoch fence on the leader (Kafka `ProducerStateEntry.coordinatorEpoch`).**
- `ProducerStateEntry.coordinatorEpoch` only ever rises.
- The worker's `executeAppendControlRecordWire_` is the single place every marker is appended, local or remote. It refuses a marker whose `coordinatorEpoch` is below the stored one. The refusal uses `kMarkerCoordinatorFencedError`; nothing is appended and no state is touched. The stored epoch is raised only after a successful append.
- The fence is rebuilt from the log by both rebuild paths: `ProducerStateManager::rebuildFromLog` and the worker's RC build (`RcState::feedProducerState_`). Both read `ControlMarkerLayout::coordinatorEpoch` from value bytes [70..73]; the marker carries it, as Kafka's EndTxnMarker does.
- **Error code.** The client protocol has no TRANSACTION_COORDINATOR_FENCED, and changing that protocol was out of scope. The internal code is therefore NotCoordinator (14), with a `static_assert` in `Worker.h`. It only travels on marker-reply paths and never reaches a client.
- **TCS.** A fenced refusal is never retried and never counts as landed. The retry entry is dropped, the transaction stays Prepare*, and the deposed load unloads on its own edge.

**MAJOR-3: a marker counts as landed only once the HW passes it.**
- After `appendControlBatch`, the marker's `ControlRecordAppended` parks in `pendingAcksAll_`. That is the same waiter acks=all produces use: HW > offset and ISR ≥ minIsr, re-validated every pass for ownership, role and log generation.
- It applies to both the local "landed" callback and the remote answer.
- The waiter has **no deadline**: only the HW or a role change completes it.
- Demotion while waiting returns NotLeader, which goes to the existing TCS retry.
- The owed-return slot is reserved **before** the append, as for a gateway-routed acks=all produce. With no slot, the marker is refused NotLeader and the log is left untouched.
- If the HW already passes the marker at append time (an ISR of one), the return fires immediately, so single-replica latency is unchanged.

## What changed, finding by finding

**NEW MAJOR-1: idempotence on the leader.**
- `ClientGateway::lastRemoteMarker_` is keyed by (topic, partition, producer id), with the producer id taken from the marker bytes. Each entry holds:
  - the origin node, coordinator epoch and token;
  - whether it has been answered, and with what error code and offset.
- A copy from the **same coordinator load** (same origin, epoch and token incarnation) is handled by token:
  - **Same token, still pending:** skipped.
  - **Same token, answered:** re-answered with the **original outcome** and never appended again.
  - **Older token:** never appended; it is answered NotLeader, which the coordinator ignores because it has forgotten that token.
- This O(1) index replaces the linear scans of `markersInFlight_` and `pendingMarkerResponses_` (re-review LOW-7).
- It is in memory only, per your ruling. A stale copy after a leader change is refused by the target leader epoch instead.

**Narrowing the `-1` re-send.**
- A new inbound image is now attributed to its peer by host: the host part of `Image::sourceIdentity()` is compared with each peer's endpoint host.
- Only the matching peer or peers are reported.
- If several peers share one host (the Mac tests, co-located nodes), all of them are reported. That is safe now that the leader is idempotent.
- An unknown host still reports `-1`, meaning every peer.

**NEW MEDIUM-1.** `notePlaneReconnects_` edge-detects `pub->isConnected()` for **every** peer on every poll: one load per peer, with each peer's publication reached through a stable pointer.
- A false→true edge reports the peer, and also tells the hold router so its connection generation follows.
- An idle one-way outage is therefore reported even though the router never saw it.

**NEW MEDIUM-3: target leader epoch.**
- `WriteTxnMarkerMsg.leaderEpoch` is a new int32 at +40; the block grows from 40 to 44 bytes and the marker bytes move to +44. The coordinator stamps the `remoteLeaderEpoch` it routed the marker under.
- The leader passes it to the worker as `roleEpoch` = target + 1. A value of 0 means "not checked", which is what local markers use; the +1 keeps 0 free, because leader epochs start at 0.
- The worker refuses NotLeader, a retriable error that makes the TCS re-route, when the target epoch is lower than `replica->epoch()`. The check runs after the coordinator fence and before the reservation.
- Recorded in the spec as a §2 addendum. The addendum also records:
  - leader idempotence;
  - event-driven completion;
  - HW-gated landing;
  - rolling-upgrade behaviour (re-review LOW-6);
  - the reserved template ids.

**NEW MEDIUM-2.**
- Each awaiting transaction now carries `dispatchedNs`. It is stamped at dispatch, or at the first gauge scan if dispatch happened before the TCS clock started.
- The gauge also counts the markers that were never refused (`outstanding − retries`) once they have been unresolved past the window.
- **Window:** I used the existing `kStuckMarkerNs` (5 s) for both kinds of marker, because the TCS has no "coordinator heartbeat" constant. This is observability only.

## Open concerns (fix round 2)

1. **E3 dockerized tx_* suite not run.** Yours, as agreed.
2. **Image→peer attribution uses the source host**, so it is exact only when nodes are on distinct hosts.
   - Co-located nodes all get the re-send. This is safe because the leader is now idempotent.
   - A host written differently in the endpoint and in `sourceIdentity` (for example a hostname versus an IP) falls back to re-sending to everyone.
   - The exact alternative is to learn the sender from its frames, keyed by image session id.
3. **The leader-side idempotence index (`lastRemoteMarker_`) is never pruned.** It grows to one entry per (partition, producer) ever marked remotely on this node. It is cold memory and in-memory only; pruning it on partition removal or producer expiry is follow-up work.
4. **The idempotence index is not persisted**, per your ruling. After a leader **restart** at the same leader epoch, which is rare, a trailing same-token copy is caught by neither the index nor the epoch check. It would need the copy to outlive the restart in the sender's held FIFO.
5. **The gauge window is 5 s (`kStuckMarkerNs`)**, not a "coordinator heartbeat window": no such constant exists in the TCS.
6. **During the bootstrap window the routing image comes from the static balancer**, and its leader epoch may differ from the replica's. A remote marker routed by it can then be refused NotLeader once and re-routed after the committed map arrives. The BrokerNode test, with the default config, passes.
