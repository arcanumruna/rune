## Verified correct (no finding)

### Broker rule (`ProducerStateManager.cpp:155-163`)
- No entry and seq != 0 → 28. No entry and seq 0 → accept.
- Protocol-illegal sequences are checked first and stay OOS.
- Known entry: a gap gives OOS, a lower epoch gives fenced, a higher epoch with seq != 0 gives OOS.
- The INT32_MAX → 0 wrap is unchanged.
- This matches Kafka's classic `ProducerAppendInfo.checkSequence`: no record of the producer and seq != 0 → UNKNOWN_PRODUCER_ID.

### Never appended
- `ProducePath.cpp` returns before the min-ISR gate, the append and the PSM `update`.
- The worker path (`Worker.h:5187-5196`) enqueues the return and exits.
- Tests check that LEO is unchanged on the inline, worker and real-Aeron paths.

### Proven-state gate
- Inline: `proveInlinePsm_` runs before `handleProduceBatch`. Unproven gives NotLeader or Internal, and a test covers it.
- Worker: `rcGate_` / `provePassthroughPsm_` gate as before.
- A 28 can only come out of `handleProduceBatch`, which has exactly 2 production callers. Both are gated.

### Every 28 answer site is gated
- **Inline:** `sendRespReliable_` maps the code before encoding, so the PendingResp retry queue holds already-mapped bytes.
- **Worker relay:** `handleWorkerReturn_` maps the code on `session->clientVersion`.
- **Shard mode:** `SessionAckSink::encode_` uses the per-session `clientVersion_`.
  - The array is reset on insert and erase, and moved during backward-shift deletion.
  - The `SessionAnnouncer` → `WorkerOp.clientVersion` → `executeSessionAnnounceWire_` → `ackSink_->announce(..., version)` chain is complete.
- The other ProduceResponse encoders never carry a PSM-derived code: the pending-ack NotLeader / Internal / OK paths at `ClientGateway.cpp:3857-3932`.

### Wire
- The new decoder accepts blockLength >= 14 and checks `avail >= header + blockLength`.
- A pre-D6 decoder reads fixed offsets 24..37 with `avail >= 38`, so it decodes a 46 B frame unchanged.
- The header version is not bumped, so an old `checkFrame` still accepts the frame.
- An old broker ignores `ConnectRequest.clientVersion` (pre-D6 `git grep` finds no use), so a v2 client connects fine and simply never sees 28.
- Golden vectors: `produce_response_v0.bin` is kept, plus the regenerated `produce_response.bin` and `produce_response_unknown_pid.bin`.
- On Aeron the frame grows from 70 to 78 bytes, and both pad to 96 bytes at 32 B alignment. There is no wire-size cost per ack.

### Hot path
- No allocation, no virtual call, no `std::function` and no atomics were added.
- The added cost is one compare on the error branch per ack encode, a 4 B store per WorkerOp encode, and 8 B per AckEntry.
- `check_no_atomics` is unaffected.

### Client rule U
- C1, C2, C2b and C3 run before U, and rule A ignores stale attempts.
- A 28 proves that b's current attempt was not appended. It also proves that no attempt of b, and no batch behind it, is in [logStart, LEO): the state is complete to LEO, and any such batch would have created an entry.
- So U1 re-sequencing can duplicate only an earlier attempt of b that was appended below logStart and whose OK was lost outright. That window is the one `ad6dcac` documents, and Kafka has the same one.
- Batches behind b at seq > 0 also meet 28, so none of them can be appended under the old identity. There is no gap.

## Findings

### M1 (MEDIUM): U2 fails a batch that is provably not appended, where Kafka KIP-360 retries

**Where:** `rune-client-cpp src/producer/ProducerImpl.cpp:2297-2301` (falls through to D)

**Scenario:**
1. An unclean failover, or any state loss without retention, leaves the leader with no entry for P while logStart <= lastAckedOffset (logStart is often 0).
2. P's next-in-line batch b gets 28.
3. U2 fails b with BrokerError(28) "outcome unknown" and marks the partition unresolved.

**Why this is too conservative:**
- b's offset, had any attempt been appended, would be above lastAckedOffset, which is >= logStart. That puts it inside the rebuilt range, which contradicts "no entry".
- So in the U2 case a re-send is provably duplicate-free. The case that does carry a duplicate risk is U1.
- Kafka's idempotent producer (`TransactionManager.canRetry`, last branch) always retries UNKNOWN_PRODUCER_ID with an epoch bump.
- This was the brief's explicit ruling, so it is not an implementation error. But it leaves a spurious, application-visible failure that D6 set out to remove, and "outcome unknown" is the wrong classification for it.

**Fix:**
- Preferred (Kafka parity): treat U2 like U1 and re-sequence. Optionally emit a diagnostic or metric, because acked data at or above logStart was evidently lost by the broker.
- Minimum: fail b with a definite "not appended" status, and do not mark the partition unresolved.

### M2 (MEDIUM): Transactional producer aborts on the retention case, where Kafka re-sequences and keeps the transaction

**Where:** `rune-client-cpp src/producer/TransactionalProducerImpl.cpp:1234-1237`, `:1326`

**Scenario:**
1. A long-lived transactional producer writes partition X sparsely. Sequences continue across transactions at the same epoch; they reset only on a bump (`:1001`).
2. Retention removes P's batches on X, and then a failover happens.
3. The next transaction's first batch to X (seq k > 0) gets 28.
4. 28 is mapped to OOS, which poisons the transaction. The application must abort and retry the whole transaction.

**Also:**
- The application sees error code 20 (OOS), not 28.
- The transactional producer does not track `lastAckedOffset`, so it cannot tell retention from loss.

**Kafka:** when `lastAckedOffset < logStartOffset` it calls `txnPartitionMap.startSequencesAtBeginning` and retries without aborting. Only the non-retention case is abortable. The code comment ("transactional UNKNOWN_PRODUCER_ID is abortable") is only half of KIP-360.

**Fix:**
1. Track `lastAckedOffset` in `TxnPartitionState`.
2. On 28 with `logStart > lastAckedOffset`, reset that partition's sequences to 0. This is safe within the transaction because the broker has no entry, so seq 0 is accepted.
3. Re-stamp and re-send the in-flight batches. Abort only otherwise.
4. At minimum, pass 28 through as the poison error code instead of 20.

### M3 (MEDIUM): No test covers the shard-mode chain end to end, which is the production runtime

**Where:**
- `rune-broker libs/node/include/rune/node/Worker.h:1469` (`a.logStartOffset = ret.baseOffset`)
- `Worker.h:1990` (`ackSink_->announce(..., version)`)
- tests: `SessionAckSinkTest.cpp`, `SessionAnnouncerTest.cpp`

**The gap:**
- The sink tests enqueue AckEntry and call `announce` directly.
- The announcer test checks `lastAnnouncedClientVersionForTest()`, which is set at `Worker.h:1981` before the `if (!ackSink_) return;` and before the sink sees the version.
- The worker-rebuild test goes through the non-shard relay (`handleWorkerReturnForTest`).

**Scenario:** a refactor drops either line.
- Dropping the `logStartOffset` copy means every shard-mode 28 carries lso -1. The client then always takes U2, so D6 silently does nothing in shard mode and the spurious failure is back.
- Dropping the version argument makes the default 0 (since `42afb35`), so every v2 client gets OOS in shard mode.

No test would turn red in either case.

**Fix:** add one `*Regression*` test with a Worker that has a shard ack sink (`workerSideAcks()`). It should:
1. Announce a v2 session and a v1 session through a real `WorkerOp::SessionAnnounce`.
2. Run the RC-rebuilt-after-retention produce from the existing worker test.
3. Decode the frames the sink published, and assert 28 with lso = logStart for v2 and OOS for v1.

### M4 (MEDIUM): The 46 B frame goes to every client, including the ones the version gate classifies as old

**Where:**
- `rune-protocol include/rune/protocol/client/DataMessages.h:206-220` (always BODY_FIXED = 22)
- `rune-broker SessionAckSink.h:294` (`kAckBytes` fixed at 46)
- `ClientGateway.cpp:313` and `:3518`

**The risk:**
- The error code is gated on clientVersion, but the frame size is not.
- Compatibility rests on every other decoder accepting a block longer than 14 bytes. That holds for the C++ decoders and was verified. It was not verified for rune-client-nodejs (the report flags it) or for external tools.
- A strict decoder there (`len === 38` or `blockLength === 14`) would drop every produce ack, so every produce would time out for that client. That is the whole produce path, not just the error case.

**Fix, either of:**
- Verify the nodejs decoder and add a nodejs conformance check against `produce_response.bin` (46 B) before merge.
- Or gate the size as well: encode the v0 38 B frame (BODY_FIXED_V0) for sessions with clientVersion < 2. The version is already in hand at all 3 sites; the sink would claim `ENCODED_SIZE_V0` for old sessions.

### L1 (LOW): A rebuilt PSM gives an epoch-only entry from a surviving transaction marker, so the answer is OOS, not 28

**Where:** `rune-broker libs/storage/src/ProducerStateManager.cpp:257` (`fenceEpoch` calls `getOrCreate` before the epoch compare); rebuild at `:609`.

**Scenario:**
1. Retention removes P's data batches, but a later commit or abort marker for P survives.
2. The rebuild creates an entry with lastSequence -1.
3. P's next batch at seq k > 0 is a "known entry + gap", which answers OOS, not 28.

This is latent: today the transactional client treats 28 and OOS the same. It starts to matter once M2 is implemented.

**Fix:** in rebuild, treat a marker-only entry (lastSequence == -1, no data in range) as unknown for seq != 0, or record markers without a sequence and let validate return 28 for such an entry when seq != 0.

### L2 (LOW): The client test hook drops `logStartOffset`

**Where:** `rune-client-cpp src/agent/ClientAgent.cpp:794`. `produceResponseFn_(corr, off, ec)` does not pass the log start.

Tests built on `setProduceResponseFn` cannot exercise U1 through the agent; they always see -1. This is test-only.

**Fix:** widen `ProduceResponseFn` to carry `logStartOffset`.

### L3 (LOW): The internal SBE `WorkerOp` layout changed without a schema-version bump

**Where:** `rune-protocol schema/rune-internal-ring.xml:209`. `clientVersion` is inserted before `tailKind`, so the block grows from 239 to 243 and `tailKind` moves from offset 238 to 242. `SBE_SCHEMA_VERSION` stays 0.

This is safe while the ring stays in-process with both ends compiled together. Any offline decoder (FR or trace tooling, captured ring dumps) built at a different revision will misread `tailKind` and the tail.

**Fix:** append new fields after the existing ones, or bump `schema version` / `sinceVersion` when the layout changes.

### L4 (LOW): The gate is implemented twice

**Where:** `SessionAckSink.h:451-454` re-implements `produceErrorForClient` inline. `rune::storage` is presumably not a dependency of node headers.

A future code that needs gating (for example a later D-series error) could be added to one site and not the other.

**Fix:** move `produceErrorForClient` into rune-protocol (`Protocol.h`, next to `clientUnderstandsUnknownProducerId`) and use it at all 3 sites.

### L5 (LOW): Under `2029cfd`, `SessionAckSink::announce` defaulted to kClientVersion (2)

Any `announce` call without a version would have sent 28 to old clients. The production caller always passes the version. Already fixed by `42afb35` (default 0). Listed for traceability only.

### L6 (LOW, accepted): U1 duplicate window, plus a minor hot-path footprint

**U1 duplicate window:** it applies when an earlier attempt of b was appended below the new logStart and its OK was lost outright. It is Kafka-equivalent and documented in `ad6dcac`; no action.

**Hot path:**
- The new `clientVersion_` array (16 KiB per sink) adds a cache line per ack flush, beside `keys_` and `states_`.
- AckEntry grows by 8 B.

Negligible. If ack-flush benchmarks regress, fold the version into `PubReady`.

## Test quality

- RED-first evidence was produced by sabotaging each fix, per the report.
- New tests use `*Regression*` naming. The pure wire-constant tests (`UnknownProducerIdWire.*`, `ConformanceGolden.ProduceResponseUnknownProducerId`) are feature tests, which is acceptable.
- The broker tests cover:
  - the PSM after real `Log` retention
  - ProducePath
  - inline failover, plus the unproven gate
  - the worker RC rebuild plus the relay
  - real-Aeron Connect gating
- The client tests cover U1, U2, C1, C3 ordering, rule A, and an e2e against the InvokerGateway model with exactly-once and epoch-1 checks.
- The existing `EosOosRegression.FollowersOfARejectedHeadAreResequencedNotFailed` was relaxed to `oos + unknownPid >= 3`. That is semantically right.
- Gaps: M3 (the shard chain) and L2 (the hook). The e2e runs against the broker model, not the real broker binary (noted in the report).
