## Implementation notes (deviations from the plan's code)
- The receive path detaches its per-transport cmsg buffers from the shared receiver/sender `msgvec` after every recvmmsg. Aeron reuses one msgvec across all transports in a poll, and stock Aeron only resets it once per duty cycle.
- Test-data fix: the plan's `mixedSizes` produced a 179,527 B message at MTU 8192, which is above term/8 = 131,072, so the offer could never be accepted. Sizes are now clamped to term/8.
- `DataLossRecoversWithGroOn` also asserts that Aeron's "Retransmits sent" counter is above 0, which proves the loss interceptor actually dropped data.
- Extra tests:
  - `StockRigCountsNothing`.
  - EmbeddedDriver msgs-per-send is 16 with GSO, 2 with GSO off, and 4 when set explicitly.
  - Client: UDP echo at MTU 1408 proves `gso_datagrams > gso_sends` and `gro_datagrams > 0`; stock path; explicit msgs-per-send cap; injected EIO falls back to sendmmsg without loss.
- The test rig driver idles with "backoff", not "yield" (never-busy-spin rule). Tests never sleep: they poll with a deadline and `sched_yield`.

## Concerns
1. **The shared rune-protocol checkout lacks the GSO commits.** `/Users/vradu/Projects/rune-protocol` is at 2b1de4c, a docs-only commit on top of f3fa865. Both wt29 and wt8 compile `${RUNE_PROTOCOL_INCLUDE}/../src/net/rune_gso_bindings.c`, so a configure against the default `../rune-protocol` fails until feat/gso-1 (7595bf0, 25cdbbb) is merged into it. 2. **`ShardModeRegression.SlowEndpointUnawareClientCannotStarveTheShard` is a pre-existing flake (about 50% on Linux).**
   - It reproduces on the Oct 2 pre-GSO binary (`/root/wt26`): 3 of 6 runs fail with about 28.8k ack-room pauses.
   - Interleaved A/B on the GSO tree: no bindings failed 3/6, GSO 0/6.
   - Cause: the documented T13 KNOWN ISSUE (the pause depends on pipeline depth).
   - I fixed the test's "legacy" client so it really is the stock transport. With GSO on, that client had silently gained GSO and 16 msgs/send, which deepened the pipeline. The T13 issue itself is not fixed; it is out of GSO scope and owned by T13.
3. **The VM's Aeron driver lib is the FR-hooked build** (findings §8). Both arms are equally affected, so the comparison is relative and matches the conditions of §4.3/§4.4. The stock-lib restore before "final" absolute numbers is still pending (it is a shared package, so I did not swap it).
4. **The DR e2e matrix (plan Task 5 step 4) was not run.**
5. Behaviour differences from stock Aeron:
   - ENOBUFS on a GSO send is treated as a transient short send (Aeron re-sends); stock sendmmsg treats it as an error.
   - When GRO coalesces non-8-byte-multiple control frames (status messages are 36 B), the split hands Aeron unaligned buffer offsets. This is fine on x86_64/arm64 loads, but worth knowing.
6. Env parsing is inconsistent between client and broker. `RUNE_CLIENT_AERON_UDP_GSO` goes through the client's numeric `readSize`, so only `0`/`1` work; `true`/`false` produce a warning and are ignored. The broker accepts `0`/`1`/`false`/`true`.
7. No Opus review of these changes was done, because the brief said no subagents.
8. **VM housekeeping**
