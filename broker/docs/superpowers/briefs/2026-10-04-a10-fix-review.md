## CRITICAL

### C1 — `sessionById_` sends liveness to the wrong session in multi-node mode: broker session ids are per-node counters, so they collide
- `rune-client-cpp-wt13/include/rune/client/agent/ClientAgent.h:767-772` returns the **first** session whose
  `sessionId()` matches.
- `src/agent/ClientAgent.cpp:800` (ProduceResponse) and `:769` (Pong) use it.
- Broker: `rune-broker-wt45/libs/gateway/include/rune/gateway/SessionTable.h:85-87`. `nextSessionId()` is
  `++nextId_` starting at 0 on **each node**. Nothing namespaces it by node id (grep confirms that
  `nextId_` is the only source).
- The client gets one session per leader node (`sessionForEndpoint`). All sessions share **one** egress
  subscription (`ClientAgent.cpp:708-712`, which is why ConnectResponse is demuxed by correlationId).
  The client therefore cannot tell which node an ack came from by sessionId alone.

**Failure scenario (the A10 bench itself):**
1. One producer connects to all 3 nodes. Each node's first Connect gets id 1, so the client holds three
   sessions, all with id 1.
2. Every ProduceResponse and every keepalive Pong from nodes 2 and 3 resolves to `sessions_[0]`.
3. Sessions 2 and 3 are never refreshed. They go stale every `responseTimeoutNs` (10 s) and resume exactly
   as before the fix. The client half of A10 is not fixed. Only the broker-side mitigation hides the storm.

Worse, the misattribution keeps a **dead** session alive. If node 1 dies, its session (id 1) is still
credited by node 2's acks (id 1), so liveness never detects the loss. Only the image-unavailable path
(if any) catches it.

The new test `PongRefreshesItsOwnSession` uses ids 41 and 42, which avoids the collision. There is no
test with equal ids on two sessions.

**Fix (either):**
- (a) Make session ids cluster-unique on the broker. For example, seed `nextId_` with
  `(int64_t)nodeId << 48` (keep the id > 0), so ids stay unique across node restarts too (use the
  epoch/incarnation bits).
- (b) Demux on the client by the Aeron **image** that delivered the frame. Each broker publication is a
  distinct Aeron session: record `header.sessionId()` of the image when the ConnectResponse arrives and
  map it to the `Session`. The poll callback currently passes only `(buf, len)`, so the transport must
  expose the header.

(a) is simpler and also removes the same ambiguity anywhere else the client keys on sessionId. Add a
regression test with two sessions sharing an id, where only the second receives acks and must stay
Connected.

## MEDIUM

### M1 — `withSparseTerms` on record-egress makes a consumer **data-plane** publication sparse, contrary to the commit's claim
- `rune-broker-wt45/libs/gateway/src/ClientGateway.cpp:2685`. `pendingRecordEgress_` is the per-(session,
  worker) publication that carries **Records** to consumers (`:2655-2680`). It uses the driver-default term
  (`aeronTermBufferBytes`, no `withTermLength`), so it is not a "small control publication".
- NodeConfig.h:644-652 documents the cost of sparse terms on tmpfs: page faults on first write (measured
  ~15% of a loaded shard thread, 73–79k → 100–105k rec/s), and a full tmpfs turns into a **mid-run SIGBUS**
  on the writer instead of a loud create failure.

**Scenario:** a consumer subscribes at runtime. The worker's push loop takes about 12k first-lap page
faults (3 × 16 MiB / 4 KiB) on its hot path. With /dev/shm near full, the worker SIGBUSes during a push
instead of failing the add.

**Fix:** keep record-egress non-sparse and rely on the SessionAckSink-style bounded re-add for its
`PubFind::Error`, or give it a small term plus sparse only if a bench proves it is free.
Per house rules, either way needs an interleaved A/B consumer bench before landing.

The same SIGBUS trade applies, more mildly, to the ack publications (1 MiB term, 3 MiB per session at
`NodeConfig.h:546`). These faults are on the worker's ack-claim path, which runs at 20k–100k acks/s, so it
is not a "control rate". Document it in the perf findings spec.

### M2 — Re-adds are unpaced and unclassified, so 8 attempts can burn out within the same transient window
- `SessionAckSink.h:836-847`. The re-add runs on the very next pass after the error is observed. With the
  invoker conductor, a full add→error round trip is a few passes (sub-millisecond on a busy worker).
  `kMaxPubAddAttempts = 8` can therefore be exhausted while the same condition persists. With periodic
  fsync, io_uring completions arrive continuously, so the EINTR condition is correlated with load, not
  independent per attempt.
- The retry also does not separate transient from permanent. Aeron's `RegistrationException` carries the
  driver `errorCode` (INVALID_CHANNEL, etc.) and the message (`(4) Interrupted system call`).
  `AeronSessionPubPolicy::find` (`:957-963`) collapses every case to `PubFind::Error`.
- A bad channel now costs 8 driver registrations and 8 driver error logs per session instead of 1.
  Today it is pre-filtered by the gateway's own Connect add on the same channel, so the impact is low.

**Fix:**
- Map the exception's error code in the policy: return `PubFind::Error` (fatal) for INVALID_CHANNEL and
  similar codes, and `PubFind::Retry` for GENERIC/IO errors.
- Space retries by a **pass count** (for example, attempt k after 2^k passes, capped). This stays
  time-independent (no clock) but crosses more than one burst of completions.

With sparse terms on the ack publication, the EINTR source is gone, so this is defence in depth. That is
why it is MEDIUM.

### M3 — Channel-slot lifetime is longer, which makes pool exhaustion more likely, and the exhausted path silently gets no retry; no test covers slot accounting
- `SessionAckSink.h:812-817`. The slot now stays with the session through Resolving (until Ready, Failed,
  or after up to 8 retries). Before, it was returned the moment `add()` was issued.
- In a connect/resume burst of more than 256 announcements per pass window, more sessions fall into
  `announce()` → `addNow_` (`:229-231`, `:798-802`) with `chan = kNoChan`. Those sessions get **zero**
  retries (`:836`), so a transient error still kills them with SessionExpired. That is exactly the A10
  storm shape: a resume burst under load.
- I traced the accounting and it is correct:
  - Announced → Resolving moves the slot without freeing it.
  - Ready, final Error, close/erase, and re-announce each free it exactly once:
    `freeChanSlot_` at `:824` and `:849`, and `leaveState_` at `:637`.
  - The erase_ backward shift moves states and does not free.
  - `fail_` is only reached from Ready (`:318`).
  - The drain list is correct: an errored reg is replaced in place without being queued (`:840-843`), and
    a superseded live reg is queued by `leaveState_` (`:641`).
  - unresolved_ bookkeeping is correct: a retried session is kept (`:845`), and an Announced/Resolving
    re-announce is not double-listed (`:221`, `:232`).
- However, `freeChanSlot_`'s `freeChanCount_ < kMaxChannelSlots` guard (`:796`) would hide a double free,
  and **no test** asserts slot conservation. `grep` finds no pool test in SessionAckSinkTest.cpp.

**Fix:**
- Add `freeChannelSlotsForTest()` and a regression test that runs announce → error/retry → close /
  re-announce mid-retry / Ready / Failed and asserts the free count returns to 256 and the drain list
  holds only live regs.
- Add a test for the pool-exhausted path.
- Consider keeping a heap/std::string copy of the channel for the `kNoChan` path (cold, rare), or document
  the asymmetry.

### M4 — Runtime-created **images** (and other runtime adds) remain non-sparse on the fused worker
- Images inherit `is_sparse` from the matching **subscription** link (Aeron
  `aeron_driver_conductor.c:105-125`), not from the publication's URI. A client's ingress publication to
  the broker creates a broker-side image at connect/resume time. In fused placement, the conductor runs on
  the worker thread, so the same tmpfs `fallocate` EINTR applies there.
- The driver re-attempts on the next SETUP, so this probably self-heals with a delay rather than a storm.
  It is the same root cause, though, and is not covered or verified.
- Likewise, `WorkerReplicationTransport.h:161` and `WorkerEgress.h:76` add without sparse and without
  retry. They run at construction today; check whether any runs at runtime on failover.

**Fix:** confirm on the VM with the FR capture whether `Interrupted system call` still appears in the
driver error log after this fix. If it does, use sparse on the ingress subscription or retry the
`fallocate` in a driver wrapper. Otherwise, note it in the commit/spec.

## LOW

- **L1** `AeronChannel.h:28-34`. `find("sparse=")` is a raw substring match, so a param value containing
  `sparse=` would suppress the append. A URI ending in `?` becomes `...?|sparse=true`. Neither occurs with
  client-generated channels. Parse `?`/`|` keys if you want it exact. `sparse=true` itself is valid
  syntax for udp and ipc exclusive publications (driver `aeron_driver_uri.c:307,344`). Appending it with
  `|`, or with `?` for a bare `aeron:ipc`, is correct, and an explicit `sparse=` from the client wins.
  Per-publication sparse does not conflict between exclusive publications on the same channel (each has
  its own log).
- **L2** `ClientAgent.cpp:769-770`. A Pong whose sessionId matches no session falls back to crediting the
  **seed**. After a resume, a Pong for the old id credits the seed falsely. Drop it instead: the Pong is an
  answer to a keepalive that no live session sent.
- **L3** `SessionMachine.h:398-404`. Own-stall false positives:
  - In Invoker mode, an owner that skips `doWork()` for more than `responseTimeoutNs` (10 s) also exceeds
    `aeronClientLivenessTimeoutNs` (10 s, `Client.h:182-183`), so the Aeron client is already dead. A
    resume is harmless in comparison.
  - `lastTickNs_` is updated in every state, so a long Backoff, Connecting or never-ticked new session
    does not trigger it.
  - It can discard a session the broker would still accept (broker lease longer than the client timeout).
    That costs one reconnect plus resend, which is acceptable.
  - Say in the comment that tests driving `tick()` with clock jumps over `responseTimeoutNs` while
    Connected will now see Resuming.
- **L4** `SessionMachine.h:705-708`. Ping with correlationId 0 does not collide with application pings:
  - `Client::nextCorrId_` starts at 1 (`Client.h:1032`).
  - `findCtl_` also requires `op == OpKind::Ping` (`Client.cpp:2214-2216`).
  - The broker `handlePing` (`ClientGateway.cpp:1660-1688`) touches the lease exactly like
    `handleKeepalive` (`:1650-1655`), and the broker has no other Keepalive consumer (grep), so the lease
    is preserved.
  - Caveat: the Pong is sent best-effort on the gateway egress (`:1687`, return value ignored). Under egress
    back-pressure an idle session can miss Pongs. That is fine as long as `keepaliveIntervalNs` ≪
    `responseTimeoutNs`; assert that ratio in SessionConfig validation.
- **L5** `ClientAgent.cpp:800`. Hot path is OK: no allocation, virtual calls, std::function, atomics or
  locks. `sessionById_` does one `unique_ptr` deref per session (≤3) per ack. An optional last-hit cache
  would make it O(1). The broker changes are all cold path (publication setup); the `std::string` building
  in `withSparseTerms` is fine there.
- **L6** `SessionAckSink.h:557`. `pubAddRetries()` is not exported to worker stats or FR. Wire it into
  stats so a recurrence is visible in bench output without a debugger.
- **L7** Tests:
  - Missing: a client test with colliding session ids (C1); a test that a ProduceResponse for an unknown
    sid credits nobody; a broker test for close/re-announce **during** a retry (M3).
  - `ClientAgentTest.cpp:281-287`: the mock Gateway now classifies keepalives by `correlationId == 0`.
    That is fine, but it encodes the convention in the test double. A shared constant
    (`kKeepaliveCorrelationId = 0`) in the codec would keep client and broker in agreement.

## Checked and fine (no finding)

- The SessionAckSink state machine (see M3 for the full trace): no leak or double free of channel slots
  across Announced/Resolving/Ready/Failed/close/re-announce/addNow_. An errored reg is never drained, and
  a superseded live reg always is. The retry is bounded at 8 adds per announce episode and cannot loop
  (the `attempts` counter resets only on re-announce, which is a runtime event).
- Broker ProduceResponse always carries sessionId: `SessionAckSink.h:862` and every gateway construction
  site (`ClientGateway.cpp:327,3771,4110,4132,4158,4185`).
- sessionId 0 is guarded (`ClientAgent.h:768`). Sessions mid-resume have `onActivity` gated to Connected
  (`SessionMachine.h:372-376`), so acks for the old id are harmless.
