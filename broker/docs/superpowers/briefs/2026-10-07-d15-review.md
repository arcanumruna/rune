# D15 review: memory-backed epoch edges (2026-10-07)

- **Scope:** `git diff 375a539..2cccff5` on `fix/d15-memory-epoch-edges` (wt63, HEAD 2cccff5).
- **Verdict:** APPROVE WITH CHANGES.
- **Counts:** critical 0, major 2, medium 5, low 5.
- **Tests run:** `ctest -j4 -R "D15|LeaderEpochFence|MetadataStateMachineRegression|EpochRestart"`: 23/23 green (build-fast was up to date).

## Major

### M1. The legacy feature level turns off the 9c80eab fence for every cluster whose metadata log predates D15

- **Where:**
  - `ReplicationMessages.h:437` (`kBase = 0` is documented as "pre-D15: no bump requests")
  - `PartitionReplica.h:1609` (`fenceProtocol_()`)
  - `PartitionReplica.cpp:313` and `:346`
- **The premise is wrong.** 9c80eab, 63280ce and 498ec7c are all ancestors of main 375a539. A main binary already has the full fence protocol: replicas refuse and send bump requests, and controllers act on bumps and leaderless reports. Yet main nodes advertise 0 in `isr[6]`, and a log they wrote has no `FeatureLevelRecord`, so it reads as level 0. The gate therefore turns the fence off between two binaries that both support it.
- **Failure scenario (rolling upgrade from main, or any cluster created on main):**
  1. Node L is a memory-backed, sole-ISR leader at epoch e. The cluster is upgraded node by node, and L is restarted on the D15 binary.
  2. L comes back empty. The level is still 0, because the other members have not re-registered with a D15 binary.
  3. The committed map still names L leader at epoch e, or the balancer re-elects it.
  4. `fenceProtocol_()` is false, so L leads epoch e again with an empty log. This is a second history under an epoch it already led.
  5. Followers' KIP-101 truncation cannot see the divergence, so committed records are lost. This is exactly the bug 9c80eab fixed.
- **A rolling upgrade is the trigger, not a rare case:** every step restarts a node, and memory-backed replicas come back empty.
- **It can last forever:** a member that never registers again (permanently dead, or still on an old binary) holds the level at 0. That leaves the fence off for the life of the cluster. The report's "acceptable, as in Kafka" does not hold here. Kafka's `metadata.version` never disables a safety mechanism that already shipped; it gates only new wire semantics.
- **Fix options:**
  - **(a)** Keep the fence protocol unconditional, as main has it. Use the level only for semantics an older peer cannot handle. Nothing in D15 qualifies: the trailer and type 6 are both skipped by older binaries, and main controllers handle bumps.
  - **(b)** Make `kBase` mean "main / post-9c80eab" and gate only binaries older than 498ec7c. Those are not deployed (tags cp8/cp9 only).
  - **Either way, add a RED test:** a log with no `FeatureLevelRecord`, plus a sole-ISR memory leader restarted empty, must not lead its fenced epoch.

### M2. Survivor election per co-partition unit gives up committed data for colocation

- **Where:** `MetadataService.h:1037-1072` (`decideLeaderless_`).
- **Before:** with `survivorLeaderElection` on, each partition elected its own clean leader whenever it had one. Unclean election happened only when no clean candidate existed.
- **Now:** if the unit has no single leader that is clean for every member, survivor election picks one replica by summed LEO for all members. Any member for which that replica is not clean is then elected unclean, with `isr = {leader}`.
- **Failure scenario:**
  1. Memory node 1 led unit {A-0, B-0} and restarted empty.
  2. A-0 has ISR {1,2} and B-0 has ISR {1,3}, because the ISRs shrank separately.
  3. Node 2 is the only clean choice for A-0 and node 3 the only one for B-0. No common clean leader exists.
  4. Survivor election picks, say, 2. B-0 is elected uncleanly at node 2, which is not in B-0's ISR and is behind, so B-0 loses committed records. Separate per-partition decisions would have lost nothing.
- **The report's claim is false.** It says the election "is unclean only where it has to be"; here it is unclean only so the unit stays colocated.
- **Fix:** when every member has its own clean candidate, choose between:
  - per-member clean leaders, temporarily split, with the co-partition move-back fixing colocation later; or
  - holding the unit.

  Use survivor (unclean) election only for members that have no clean candidate at all.
- **Test gap:** add this case to `CoPartitionUnitLeaderlessDecidedAsOneUnitRegression`. Today it covers only one empty node with shared ISRs.

## Medium

- **m1. Below the fence level, a replica leads on an offline log dir.**
  - Where: `PartitionReplica.cpp:333-346` and `:1962`.
  - A failed fence write sets `logDirOffline_`. Below `kEpochFence` the replica then leads anyway, via `++unfencedLegacyLeads_`, or via the `epochStateWriteCompleted` re-entry into `becomeLeader`.
  - A pre-fence binary never wrote a fence, so this is not "as before". The replica takes leadership on a dir whose fsync just failed. The first append either fails (disk: fail-stop) or the leader acks writes that are not durable.
  - Fix: below the level, refuse on `logDirOffline_` as well (follower only). Only the refusal at a fenced epoch should be downgraded. This mostly goes away with M1(a).
- **m2. The feature level rides in `WorkerOp::acks`, which defaults to 0 (`kBase`).**
  - Where: `WorkerOp.h:153`; read at `Worker.h:3079` and `:3116`.
  - Any role-op producer that does not stamp the level silently turns the fence off. `WorkerPool::grantReplicaForTestMigration` and `releaseReplicaForTestMigration` (`WorkerPool.h:382` and `:400`) already don't stamp it.
  - Fix: use a dedicated field defaulting to `kLatest`, or a sentinel of -1 meaning "leave unchanged".
- **m3. A co-partition unit ignores siblings that are leaderless for another reason.**
  - Where: `MetadataService.h:977`.
  - Only partitions with an `emptyMemoryLeader_` entry count as unit members. A sibling that is NO_LEADER for another reason (a LogDirOffline mark, or the balancer's empty ISR intersection) is neither a member nor a `siblingLeader` candidate, because its `leaderNode` is below 0.
  - The balancer elects that sibling on its own while the EML members are decided separately, so the unit can still split.
- **m4. Record type 6 is claimed outside rune-protocol.**
  - Where: `MetadataExtensions.h:31`.
  - `MetadataRecordType` is owned by the sibling rune-protocol header (1..5). The next type added there will collide with 6, and old logs would then decode a `FeatureLevelRecord` as that type.
  - Fix: reserve 6 (`FeatureLevel`) and the 0xD1 trailer tag in rune-protocol's enum and docs now.
- **m5. The memory-backed fence write is synchronous I/O on the owning worker (confirmed; pre-existing, and the report says so).**
  - Where: `PartitionReplica.cpp:2941+`, `persistLedEpoch_`.
  - It runs open, write, fsync, rename and dir fsync, plus a `std::string` allocation, inline on the worker. This happens once per new leadership epoch for memory replicas (`es_` is disabled without a disk log), and the D15 legacy branch takes the same path.
  - It is cold, not steady state, but it is still worker-thread I/O during failovers: every partition on that worker stalls for milliseconds. Under the hot-path rule it must not be called "fine".
  - Keep it on the backlog with a µs budget, and move it to the io backend by decoupling `es_` from `diskLog_->dir()`.

## Low

- **l1. More than 256 marked partitions at a controller claim can race the balancer.**
  - `restoreLeaderlessMarks_` can queue more than `kMaxRecordsPerBatch` (256) re-arms. The first rebalance (`recheckOnCatchUp_`) filters only `inflight_`, not `pendingDynamicRecords_`. It can therefore emit a second record for a queued key at the same `leaderEpoch`.
  - This is safe: `install_` rejects a same-epoch record with a different leader, deterministically. The cost is a wasted record and a wasted tick.
  - Fix: filter keys still in the pending queue as well.
- **l2. Per-member reporting gap (not a bug).** A unit larger than the remaining budget (`recs.size() + memberCount > maxRecords`) is deferred to a later event-driven tick. That is fine at 4096, but nothing forces a re-tick if no further event arrives.
- **l3. Host-order trailer fields.** The trailer `memcpy`s `node` and `incarnation` in host order (`MetadataExtensions.h:70`). This is acceptable because Rune is all little-endian; using `detail::putS32`/`putS64` would match the rest of the codec.
- **l4. Step A inherits the user-partition level.** `roleFeatureLevel_` is shared by Step A (internal partitions) and Step B. After a Step B pass, Step A stamps the MSM level rather than the documented `kLatest`. It is harmless, because internal replicas have no `isrChannel_`, but the comment at `ReplicationMetadataBridge.h:560` is wrong.
- **l5. Upgraded logs keep unmarked leaderless records.** NO_LEADER records written by main controllers carry no trailer. A D15 successor cannot restore their marks, so those partitions behave as on main.

## Asked-for confirmations

- **Two leaders in one epoch from the re-arm or unit decision.** No.
  - Re-arms and decisions always commit at `leaderEpoch + 1`, and the controller is single-writer.
  - The MSM rejects a same-epoch record with a different leader.
  - The only same-epoch second history is M1, which is across process incarnations.
- **Non-ISR leader / clean path.** The clean path requires ISR membership and `leo >= maxLeo` among available replicas. Unclean only under opt-in survivor election, but see M2.
- **Determinism.** No issues found.
  - Marks and the feature level are installed only from committed records.
  - Pending records are reverted and committed in position order.
  - The level is monotonic.
  - Controller decisions are committed as records, KRaft-style, and are not recomputed on replay.
  - The bridge's stamp timing can only raise a replica's level, which is the safe direction. The level is committed only after every member advertised it.
- **Wire compatibility.**
  - `UpdatePartitionAssignmentRecord::decode` bounds-checks and ignores trailing bytes, so the trailer is skipped.
  - On main, `MetadataStateMachine::apply` has a default of "unknown type, skip", so type 6 is skipped. It is the only consumer of `peekRecordType`.
  - `AlterIsrMsg` always encodes all 16 `isr` slots, and old senders zero-initialise them, so slot 6 reads 0.
  - New binaries read old logs as level 0 with no marks. This is fine apart from M1.
- **Snapshot/restore.** Confirmed: there is no production caller of `MetadataStateMachine::snapshot` or `restore`; the only hits are its own definitions. Not major. When snapshots land, add the level and marks to them, ideally as a RED test now that fails once a caller exists.
- **Liveness of raising the level.** Registration is re-sent on every controller change (`ControlledShutdown::step_(Running)`), so a successor learns every live member's level. A permanently dead member holds the level back forever. That would be acceptable only if level 0 kept main's safety (M1).
- **Bumps silently dropped.** None beyond the intended legacy behaviour.
- **Atomics, allocation, virtual calls.**
  - No new atomics.
  - The worker hot path adds only one `int16_t` store per role op.
  - No virtual calls are added.
  - `decideLeaderless_` and `unitKeys_` allocate and scan on the control thread, on a cold path.
