## Broker crashes

Four broker SIGSEGVs, all with the same signature. Container exit code 139. The cores are named `core.rune-wrk-0.pid1.sig11.*`, so the crash is on worker thread `rune-wrk-0`.

| when (UTC) | container | test |
|---|---|---|
| 10-04 22:08:34 | rune-dr-fault-rune-1-1 | first test of DR-13 (`test_dr13_scale[50]`), which still passed |
| 10-04 23:05:22 | rune-dr-rune-2-1 | DR-2 session cluster, case 14 |
| 10-04 23:05:23 | rune-dr-rune-3-1 | DR-2 session cluster, case 14 |
| 10-05 08:12:45 | rune-dr-rune-1-1 | DR-2 isolation rerun 3, soak `clients=5, keys=16, recs=1000, partitions:3` |

Backtrace (the same in all four; one is an uncaught exception, the other three are plain segfaults):

```
#0 aeron::ExclusivePublication::tryClaim(int, BufferClaim&)        (or ::offer(...))
#1 rune::node::Worker::pushOwnedSubscriptions_(long)
#2 rune::node::Worker::doWorkShard_(long)
#3 rune::node::Worker::doWork(long)
#4 rune::node::BasicShardAgent<MonotonicNanoClock>::doWork(long)
```

The variant on rune-3 at 23:05 was an uncaught exception that ended in `std::terminate` and `abort`:

```
terminate called after throwing an instance of 'aeron::util::OutOfBoundsException'
  what():  index out of bounds[0x7f568c02ab10]: index=0 + 8, capacity=0
#5 aeron::concurrent::AtomicBuffer::boundsCheck ... #6 ExclusivePublication::offer<...> #7 Worker::pushOwnedSubscriptions_
```

Its sibling, rune-2, logged this about 1 s before it segfaulted:

```
[2026-10-04 23:05:20.484] [error] Worker 0: push sub=1 (topicId=1 partition=0) failed at offset=130: Records frame 150 B exceeds the egress maxMessageLength 0 B — MessageTooLarge, subscription parked (cursor not advanced)
```

In both lines the egress publication reports `maxMessageLength 0` and `capacity=0`. The worker is pushing to a subscriber egress publication that has already been closed or released. The crash comes right after a consensus re-election, when a subscriber goes away or reconnects:

```
rune-3: [23:05:20.850] leadership change — no leader (election in progress)
rune-3: [23:05:21.407] ClientGateway: inline producer state invalidated + read_committed state rebuilt ...
```

The 4th core shows it is not tied to the 39-failure cascade: the same crash recurred in an isolated rerun.

Separate non-crash exits. Every `docker pause`/`unpause` of a broker (DR-10, DR-11) killed that broker on unpause with exit 255. This happened 10 times:

```
ERROR: client timeout from driver : void aeron::ClientConductor::onClientTimeout(int64_t) : aeron-client/src/main/cpp/ClientConductor.cpp : 983
ERROR: timeout between service calls over 10000 ms : int aeron::ClientConductor::onHeartbeatCheckTimeouts() ...   (1 occurrence)
```

The broker's embedded Aeron client is timed out by its driver and the process exits. It does not rejoin as a follower. See DR-10 below.

## Notes and harness issues

- **Orphaned client container.** When a `docker run` client hits the harness's `subprocess` timeout, the container is not killed. It keeps running, and it contaminated the next test (DR-15 cold-restart phantoms). `harness/dockerutil.run` should `docker rm -f` the container on timeout. My rerun loop removed leftover `dr-client-*` containers by name between runs.
- **Mutable image tag.** The harness auto-builds the netem sidecar as `rune-netem:dev`. That tag breaks the no-dev/latest tag rule.
- **Topology.** The cluster comes up in shard mode by default: `effective config: mode=shard placement=fused workers=1`.
