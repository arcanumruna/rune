## Correctness of readInto vs readView

**Sparse-index skip bound — sound.**  Index entries are `(batch baseOffset, batch start pos)`
(`LogSegment.cpp:349-351`, `394-397`, `451`, recovery `857`, `LogCleaner.cpp buildIndex` — all the same
`shouldIndex(bytesSince==0 || bytesSince>=interval)` rule, all interval 4096 since every segment is built
with `kDefaultIndexIntervalBytes`, `Log.cpp:45`).  `OffsetIndex::slotFor` returns the largest entry with
offset <= target.  If the target batch starts at t and the chosen entry at p_k, then every batch in
[p_k, t) was appended with bytesSince < interval (otherwise it would carry entry k+1 with base <= target,
contradicting the lookup), so **t - p_k < interval**.  One interval of slack is sufficient for a present
offset; the second interval is headroom.  Exceptions all degrade to `firstTooLarge` -> readView (correct,
just mapped): compaction gap (first deliverable batch Y sits at the *next* entry; skip < interval + size of
the batch preceding Y), an index with missing/truncated entries (lookup -> pos 0), or a different interval on
disk.  None produces wrong data.

**Torn tail / logSize_.**  Only the owner worker appends (sync `pwrite`/`pwritev`, `logSize_` advanced
after the write; io_uring is used only for recovery-point checkpoints), truncates (`truncateInPlace`,
`recover` — owner) and installs compaction swaps (fd keeps its old inode, same as readView's
`BorrowedFd` map).  `pread` into [pos0, min(logSize_, ...)) therefore never races a writer and never reads
another file.  `total <= 0` -> stop, and a batch running past the window at the true segment end
(`got == remaining`) -> plain empty, matching readView.

**pread loop.**  EINTR retried, short reads continued, 0 -> stop.  Fine.  (See LOW-2 for error handling.)

**maxBytes <= 0.**  `need = 2*interval + overhead`; second loop `cap == 0` -> exactly one batch.  Matches
readView (test covers `maxBytes = 0`).

**firstTooLarge.**  No false negatives found: every exit where `got < remaining` and the scan ran off the
window sets it.  False positives exist (gap case above, pread error, bufCap-bound window) but are all
harmless (readView fallback).  The fallback cannot loop: it is one readView call per PushRead; an empty
result is answered Empty and the gateway re-issues.  No starvation: a fresh pass gets `cap = min(512K, fit,
128K)` and readView always includes the first batch whole.

**Semantics drift (document it).**  When `bufCap < maxBytes + skip`, readInto returns a *prefix* of
readView's batches (window-cut batch -> break, not tooLarge).  Harmless for the worker (scratch is
budget + 64 KiB, `need <= 128K + 8253`, so it never binds there), but the header says "readView's batch
semantics" — see LOW-3.

Offset gaps (compacted segments) are handled identically to readView in both loops (scan by
`lastOffset >= startOffset`; `nextOffset` from the last taken batch).

## Worker

- Scratch lifetime: `v`/`pushRuns_` point into `pushScratch_` only inside `readPushChunk_`; the Deferred
  returns happen before `tryClaim` and `deferPushRead_` stores only `PushReadArgs` (re-read next pass), and
  `encodeWorkerReturnGather` copies into the claimed slot before return.  No aliasing across calls.  OK.
- Budget / defer / TooLarge logic unchanged.  OK.
- Allocation: `std::vector(n)` value-initialises (zero-fills) at Worker construction, so the 192 KiB is
  first-touched cold, not on the pass.  OK.  (Nit: it is first-touched on the constructing thread, not the
  pinned worker — NUMA locality only.)
- Hot-path cost: one `pread` syscall + a kernel copy of up to ~136 KiB per PushRead (two copies total:
  kernel->scratch, scratch->ring), replacing zero-syscall-but-faulting mmap reads.  This is the pre-F5 cost
  minus the allocation; it must be confirmed by the box A/B (pending) per the measured-before/after rule.

## Findings

### MAJOR-1 — the in-worker subscription push still reads through the read map on the same worker thread
`Worker.h:2526` (`pushOwnedSubscriptions_` -> `s.logPtr->readView(...)`).  This path is live whenever
per-worker egress is active, which `BrokerNode.cpp:3625` turns on unconditionally in shard (thread-per-core)
mode and `BrokerNode.cpp:1643` when WorkerEgress wires.  It has exactly the #65 failure mode (first-touch
faults -> `mmap_lock` read behind provisioner/cleaner mmap/munmap -> ~1 ms off-CPU worker passes), on the
same thread and the same push budget.  The gate that bisected #65 runs the gateway-PushRead path, so it
cannot see this.  The view there is consumed within the loop iteration, so it can use the same
`readInto(..., pushScratch_)` (sequential use of one scratch is safe).  Not strictly a regression of this
diff, but it is the same bug on the same thread; fix in this change or ticket it as the next item with a
Reads+Retention shard-mode gate run.

### MEDIUM-1 — the readView fallback is not "rare"; on large batches the fix is a no-op and does wasted mapped reads
`Worker.h:2879-2890`, `LogSegment.cpp:626-649`.  The window is `need = cap + 2*interval + overhead`, not
`bufCap`.  So `firstTooLarge` fires whenever the first batch exceeds roughly `cap + 4 KiB`:
- **mid-pass**: after ~120 KiB pushed, `cap = pushBudgetLeft_` ~8 KiB -> any batch > ~12-16 KiB (normal
  producer batching/linger) falls back to `readView` (faults, mmap_lock), and then the batch is >
  `pushBudgetLeft_` with `!freshPass` -> `Deferred` anyway.  The mapped read is pure waste.
- **fresh pass**: batches > ~136 KiB always fall back, even when they would fit the 192 KiB scratch.
Suggested shape (no syscall/alloc added on the common path):
1. `if (tooLarge && !freshPass) return PushChunk::Deferred;` (the next fresh pass re-serves it; a gap-case
   false positive also just defers one pass).
2. In readInto, when the cut batch is the *first deliverable* one and `pos + total <= bufCap`, extend the
   window with a second pread (cold, one extra syscall) instead of reporting tooLarge; size the scratch to
   `max(kPushPassBudgetBytes, fit) + 2*interval + overhead` (fit is known at construction from the ring)
   — then a batch that still doesn't fit is `> fit`, i.e. already `PushChunk::TooLarge` from its header,
   and the worker's readView fallback can be deleted entirely.
3. Add a counter (`pushReadMapFallbacks_`) so the bench/FR can prove the fallback rate is ~0.

### MEDIUM-2 — equivalence test never reaches the window-cut / skip-overflow / gap paths
`LogSegmentTest.cpp:900-931`.  `makeBatch(off, ts, 1..5)` builds ~70-110 B batches; 200 of them are ~18 KiB,
so for maxBytes 4096/64K/1M the whole segment fits the window every time.  Not exercised: a first batch
cut by the window with more segment beyond (non-tiny), batches larger than the index interval, compaction
offset gaps (start offsets inside gaps, incl. the gap-after-a-big-batch false positive), a segment larger
than `bufCap` (where readInto returns a prefix — the test's `ASSERT_EQ(len)` would *fail* there, which is
fine but should be pinned as the documented contract), and Log-level multi-segment selection
(`Log::readInto` at a segment boundary).  Add: a ~1-2 MiB segment with mixed 100 B / 6 KiB / 40 KiB batches
and offset gaps, bufCap both larger and smaller than maxBytes + 8 KiB, assert `into` is a batch-prefix of
`view` (equal when the window is not bufCap-bound) and `tooLarge` exactly when the first batch exceeds the
window.  The worker test (`HotPathBRegressionTest.cpp:1520`) should also cover the fallback branch (a batch
> window with `fit` large enough) and, if MEDIUM-1.1 lands, the non-fresh large-batch defer without a map
read.

### MEDIUM-3 (follow-up, not required here) — replication serve / follower push are worker-thread readView users too
`PartitionReplica.cpp:911` (fetch serve), `:1085` (owed serve), `:3347` (leader push) run on the owning
worker in shard mode and fault through the same map on acks=all leaders.  Not a drop-in swap: the owed
memo keys on `view.data` (`builtView`) — a scratch pointer is constant and would need the memo to key on
(offset, len, installGen) instead — and `maxFetchBytes` can be MiBs (scratch sizing / per-replica buffer).
Worth its own ticket gated by a 3-node acks=all Reads+Retention run.  `ClientGateway.cpp:3513` is the
inline no-WorkerPool legacy path: LOW, ignore.

### LOW-1 — read-map provisioning is now dead work for push-only logs
`Log.cpp:272-276` (grow request at half full from `maybeRoll`) and `LogSegment::prepareStaging`'s
whole-segment `openReadMap` (F5) still run, but the grow answer is only polled from `Log::readView`
(`Log.cpp:1042-1044`).  On a log read only via readInto, the provisioner still does whole-segment mmaps
(each one an `mmap_lock` write hold — the very contention source of #65) and a grown map can sit in
`mapRing_` with `growOutstanding_` latched until some readView/destructor.  Not a leak (`~Log` drains), but
consider polling `pollReadMaps_` from readInto too, or skipping the read map provisioning when the log has
no map readers.  Measure before changing.

### LOW-2 — pread hard error falls back to the mapped view
`LogSegment.cpp:634` -> `got < remaining` -> `firstTooLarge` -> `readView`.  A real EIO on pread becomes a
mapped access to the same bad page, i.e. SIGBUS instead of an answerable error.  Same as HEAD's behaviour
(always mapped), so not a regression; cheap to make an error return empty without setting firstTooLarge.

### LOW-3 — stale / imprecise comments
- `Worker.h:2827-2830` and `:2858-2863` still say "gathered from the segment's read mmap (Log::readView) ...
  No allocation, no syscall (the read map exists), one copy" — now one pread + two copies.
- `Worker.h:2882-2884` "rare: a batch near the ring's max message" — wrong, see MEDIUM-1.
- `LogSegment.h:193-199` should state that with `bufCap < maxBytes + 2*interval + overhead` the result is a
  batch-prefix of readView's, and that a compaction gap may report firstTooLarge spuriously.
- `LogSegment.cpp:620` comment "<= one index interval + one batch earlier" is the gap-case bound; the
  present-offset bound is "< one interval" — say both.

### LOW-4 — extra read for a lagging bound
The pread always copies `min(remaining, cap + 8 KiB)` even when the HW/LSO bound is a few hundred bytes
past `nextOffset` (acks=all leader with LEO ahead of HW).  readView only touched the pages it walked.  Small
in the tail-reading case; note it for the A/B if acks=all numbers move.

### Observation (pre-existing, unverified, out of diff)
`Log::readInto`/`readView` only consult the segment with base <= startOffset; a start offset inside a
compacted *tail* gap of a sealed segment returns empty without moving to the next segment, and
`readPushChunk_` answers `Empty` without advancing `newNextOffset`.  If nothing upstream skips the cursor to
the next segment base, such a consumer would spin empty.  Worth a quick check/test; identical at HEAD.

# Re-review — fix round 1 (diff vs f5680c8, backlog hunks ignored)

Reviewer: Opus (read-only, narrow scope).  Files: `LogSegment.cpp` readInto (new fill loop),

## Verdict: CLEAN

### MAJOR-1 — RESOLVED
`pushOwnedSubscriptions_` now reads via `readNoFault_` (pread into `pushScratch_`).  Scratch aliasing traced:
- The owned-sub loop takes ONE view per subscription and consumes it fully inside that iteration —
  `sendRecordsFrame` copies the batch into the publication term (offer/tryClaim) or into `egressScratch_`
  (a separate buffer) synchronously; back-pressure stores only `s.nextOffset` (re-read next pass);
  `sendPushTooLarge_` does not touch the view.  No read is issued inside the inner loop, so the next
  subscription's read overwrites the scratch only after the previous view is dead.
- `readPushChunk_` collects `pushRuns_` into the scratch and gathers them into the claimed ret_ slot before
  returning; every Deferred/Empty return precedes `tryClaim` and `deferPushRead_` stores only args.
- The two paths are sequential on the worker thread and neither calls the other.  No aliasing.
Sizing: both callers request <= `kPushPassBudgetBytes` (128 KiB); window <= 128K + 2*4K + overhead, scratch
320 KiB.  The new test asserts zero `readViewCalls` and zero fallbacks on the owned-sub path (RED/GREEN as
reported).

### MEDIUM-1 — RESOLVED
New fill() loop checked:
- `limit = min(remaining, bufCap)`; every `fill(x)` has `got < x <= limit <= remaining` (header path:
  `min(limit, pos+kOverhead)` with `got < limit` and `pos+kOverhead > got`; batch path: `end <= limit`), so it
  never reads past `logSize_` or the buffer, and each successful `continue` strictly grows `got` — no
  infinite loop.  A failed fill (error / unexpected EOF) returns empty with `firstTooLarge` false
  (header path: `got >= limit` is impossible after a short fill), so LOW-2 is now mostly fixed too.
- Absent offset (`got >= remaining` between batches) -> plain empty.  Torn tail: `total <= 0` -> empty;
  a batch running past `logSize_` (`end > remaining`) -> empty, not tooLarge.  `firstTooLarge` only when
  `end > bufCap` and `end <= remaining` (batch complete in the file), or the header itself can't fit.
- Never returns a cut batch: the first loop only breaks on a batch with `end <= got`; the second loop
  stops at the first cut batch.  `maxBytes <= 0` -> exactly one batch; `cap` measured from `firstPos` —
  unchanged.
- Semantics: when the read-on extended `got` only to the end of a cut first batch (or the skip exceeded
  2 intervals), the answer is a batch-PREFIX of readView's (first batch always whole).  Correct and harmless
  for both callers (mid-pass such a batch is Deferred by the existing budget rule; cost is one pread of that
  batch, no fault).
- `readNoFault_` falls back only on `firstTooLarge`, counted.  Not taken: MEDIUM-1.1 (Deferred before reading
  on a non-fresh pass) — acceptable now that the read is a pread rather than a mapped fault.

### MEDIUM-2 — RESOLVED (core)
`ReadIntoLargeBatchesMultiSegmentAndBufferLimitRegression` covers batches > the index interval (window-cut
first batch, read-on, no false tooLarge), multi-segment `Log::readInto` selection across >= 3 segments, and
the bufCap-bound prefix contract (prefix of readView, whole batches only).  The equivalence math holds
(every >4 KiB batch is indexed, so skip = 0 and `firstPos + maxBytes < want`).

### MEDIUM-3 / LOWs — deferral to D26 reasonable
Replication readView users need the owed-memo rekey + MiB scratch design and their own 3-node acks=all gate;
LOWs are comments/provisioner waste/edge cases.  D26 lists them all.

### New / remaining (LOW only, add to D26)
- LOW-5: `readNoFault_` falls back to the mapped view for any first batch reaching past the 320 KiB scratch
  (`end > bufCap` measured from the index entry), while `fit` (return ring max msg) can be far larger — such
  batches fault through the map on every PushRead.  Counted (`pushReadMapFallbacks_`); watch the counter in
  the bench, size the scratch from `fit` if it is ever non-zero.
- LOW-6: no test drives the worker fallback branch (`pushReadMapFallbacks_ > 0`) or a compaction-gap
  start offset through readInto (both degrade safely: fallback / prefix).

Rules: no allocation (scratch at construction), no atomics/mutex/virtuals added, both new tests
`*Regression*`.  Box A/B (p99.9 ~154 us vs 166/220 us, solo-read worker ~100 us) supports the change; the
v2 (read-on) tree itself should get the same one-shot A/B confirmation before merge per the measured
before/after rule.
