All 3 original MAJORs and all 5 original MEDIUMs are resolved as the rulings asked, with tests that were shown RED by mutation.

One new MAJOR comes from the re-send design itself:
- The **first** answer completes the marker.
- A re-sent copy of the same token can still be in transit behind that answer.
- The leader appends such a copy again, because its duplicate check only covers copies that are *still in flight* there.
- If the copy arrives after the producer's next transaction has started writing to that partition, it closes that transaction with the old decision. The coordinator-epoch fence cannot catch this, because the copy carries the same epoch.

The fix is small: make the leader idempotent per (origin, token, epoch) for the **last applied** marker of that producer and partition. Details are below.

## NEW MAJOR

### NEW MAJOR-1: a re-sent copy that trails the first answer is appended again and closes the producer's NEXT transaction (same coordinator epoch, so the fence cannot catch it)

**Where:**
- `ClientGateway.cpp:3740-3764`: `resendRemoteMarkers_` re-sends every *sent, unanswered* remote marker on any reconnect event. A `-1` event (any new inbound image, from any peer) sets `resendAllRemoteMarkers_` and re-sends to **every** leader, including healthy ones whose answers are simply still in flight.
- `ClientGateway.cpp:3766-3790`: the first answer erases the entry and completes the marker. The comment states "an answer to any copy completes the marker".
- `ClientGateway.cpp:3815-3822`: the leader skips a copy only while the original is still in `markersInFlight_` or `pendingMarkerResponses_`. Once the answer has left, the next copy is appended again. The comment says this is "harmless (§3)".
- `Worker.h:3202`: the fence is strict `<`, so an equal epoch passes. `Worker.h:3233`: `rc->onMarker(pid, base, commit)` closes whatever transaction is **open** for that producer.

**Scenario (no leadership change needed):**
1. Coordinator C sends COMMIT(T1), token k, as copy A1 to leader L. L appends it, the HW passes, and L sends answer R1.
2. Before R1 reaches C, C sees any plane event. Examples: a third node restarts, so a new image appears on C's subscription (-1); or the C↔L hold router has an up edge. C re-sends copy A2 with token k to L.
3. R1 reaches C. The marker completes, T1 completes, and EndTxn is acknowledged.
4. The producer begins T2 (same producer id and producer epoch; Rune does not bump the epoch per transaction) and produces to the same partition on L. This goes over the **client** path, which is not ordered against the cluster plane.
5. A2 is still behind in C's `HeldFifo` to L, or in L's cluster-plane image while L's controlled poll ABORTs on a full worker ring. Both are the back-pressure states the first review already called realistic under produce saturation. A2 reaches `appendRemoteControlRecord` only after T2's first batch was appended.
6. L's in-flight check misses (k was answered). The fence passes (same coordinator epoch). A2 is appended as COMMIT, and `onMarker` closes **T2** as committed.
7. If T2 later aborts, its ABORT finds no open transaction, so aborted data stays visible to read_committed consumers: an atomicity violation. Starting from an ABORT(T1) copy instead, T2's committed data is hidden.

**Why this is new.** Before the fix, the coordinator re-dispatched with a **new** token, after a refusal, so no copy of an answered token could trail its answer. Now every reconnect event re-sends copies whose first answer may already be on the way back. The `-1` trigger makes the window cluster-wide: any image churn on the coordinator re-sends every marker in flight to every leader.

**Fix (small, cold path):**
- Make the leader idempotent for the **last applied** marker. Per (topic, partition, producer id), remember the (originNode, originToken, coordinatorEpoch) of the last marker appended on behalf of a remote origin. Either add it to the worker's `ProducerStateEntry` next to `coordinatorEpoch`, or keep a gateway-side map that is replaced when that producer's next marker on that partition lands.
- A copy that matches it is **re-answered from memory and never appended**. This holds until that producer's next marker on that partition replaces the entry, which is exactly the window in which a trailing copy can hurt.
- Narrow the `-1` trigger. Map the new image to its peer (Aeron `Image::sourceIdentity()` / session → peer) and re-send only to that peer. Healthy leaders then do not get copies.
- Add a regression test: answer R1 is delivered, then T2's data is appended, then copy A2 arrives. Expect no new control batch, T2 still open, and a second answer for k.

## NEW MEDIUM

### NEW MEDIUM-1: a one-way C→L outage on an idle direction is never re-sent (only peers already marked down are probed)

**Where:** `AeronPartitionTransport.cpp:404-407`. `pub->isConnected()` is probed only for peers the hold router **already** marked down, and a peer is marked down only by a failed offer.

**This answers the "lost frame on a live link" concern.**
- **Within one image, Aeron does not lose frames.** A unicast publication with one tethered subscriber is flow-controlled to the receiver window, so there is no term overrun, and gaps are repaired by NAK retransmit. A marker on a live image is never "lost while the link stays up". **That case is acceptable without a timer.**
- **Loss happens only when an image is torn down and re-created**, because the new image joins at the current position. Three causes:
  - a receiver image-liveness timeout (network partition or a stalled sender driver);
  - a publication closed or re-created (process restart);
  - a subscription closed.
- **Which of these the fix covers:**
  - A node restart and a symmetric partition both re-create the image on the **coordinator's** subscription too, so C gets `-1`. Covered.
  - A one-way C→L loss re-creates the image on **L**. L's `-1` re-sends only L's own markers, so it does not help C. C sees the link only through its publication. If C makes no offer to L while `isConnected()` is false (it is idle toward L), the hold router never records a down edge, so there is no up edge and no re-send. With replication traffic flowing this is unlikely, but it is a liveness hole that has no timer by ruling.

**Fix:** edge-detect `pub->isConnected()` for **every** peer each poll (it is one load per peer), not only for peers already down. A false→true transition then reports the peer exactly like a `connGen` bump. Image teardown at the receiver (default 10 s liveness) always outlasts the sender's connection timeout (default 5 s), so every image loss becomes visible to the sender this way. Add a test with a one-way outage: the receiver subscription is closed and re-added while the sender is idle.

### NEW MEDIUM-2: markers parked on the HW are invisible to the stuck-markers gauge

**Where:**
- `Worker.h:3266-3284`: the park has `deadlineNs = max`.
- `TransactionCoordinationService.cpp` (`updateStuckMarkers_`): the gauge counts only **refused** retries.

**This answers the "unbounded wait" concern.**
- **The wait itself is consistent with acks=all semantics and with ruling 1.** A marker parks only if ISR ≥ minIsr held at append (`appendControlBatch(acksAll=true)` gates on min-ISR). After that, only the HW or a role / log-generation change completes it. While the ISR stays below minIsr with the leader unchanged, the partition takes no acks=all produce either, so the transaction cannot make progress anyway. The park holds one owed slot per (producer, partition), bounded by the number of active producers.
- **What is wrong is observability.** On the coordinator such a marker is a first attempt that is in flight, so it never reaches `a.retries`. The gauge reads 0 while the transaction stays Prepare* and the producer gets ConcurrentTransactions indefinitely. The only signal is the ISR metrics of an unrelated partition.

**Fix:**
- Stamp the dispatch time for **every** dispatched marker (not only refused ones).
- Count it in the gauge once it has been unresolved for longer than `kStuckMarkerNs`, whatever the reason.
- Alternatively, have the worker expose a "markers parked on the HW" counter.

### NEW MEDIUM-3: the same-epoch stale copy across two leadership changes is still open, and is cheap to close

**Where:** `ReplicationMessages.h:644-651`: `WriteTxnMarkerMsg` carries no target leader epoch. `ClientGateway.cpp:3806-3813` removed the only leader check on the leader side (MEDIUM-5), so the worker role gate is the only one left.

**This answers the "same-epoch stale copy" concern.**

**Scenario:**
1. C sends COMMIT(T1) to L at leader epoch e. The copy waits in C's `HeldFifo` to L, or in L's image, under back-pressure.
2. Leadership moves L→L2. C fails the marker NotLeader; the TCS re-routes it to L2, it lands there, and T1 completes. T2 writes to L2.
3. Leadership moves back to L at e+2.
4. The old copy is now decoded on L, which leads again. It passes the role gate and the fence (same coordinator epoch), and it closes T2.

**Is this realistic?** It needs a copy held across two leadership changes. That is uncommon, but this broker's DynamicBalancer moves leadership actively (see the multi-node produce notes). Under saturation, a `HeldFifo` hold of a few seconds plus a quick preferred-leader return is plausible. NEW MAJOR-1's re-sends add more copies that can be held this way.

**It is not recorded in the spec yet** (report concern 4).

**Fix (no KIP-890 needed):**
- Stamp `WriteTxnMarker` with the `remoteLeaderEpoch` the coordinator routed it under (it is already in `MarkerInFlight`). The block grows; ids 11/12 are reserved, and the codec is in-tree.
- Have the leader refuse NotLeader when `w.leaderEpoch < replica epoch`. The coordinator has long since dropped that token, so the answer is ignored.
- If the coordinator's image lags, a valid marker is refused once and re-routed, which is the same cost as a normal leader change.
- For the local path: a local marker is dispatched to the worker op ring the moment it is routed, so no copy is held across leader epochs. The local path is not affected.

## NEW LOW

1. **The wiring test does not prove success** (`D9CrossNodeMarkerTest.cpp:1240-1255`).
   - `inFlight == 0` is also true for a NotLeader **refusal** answer, and the test calls `appendControlRecord` with coordinator epoch 1, bypassing the TCS, so no landed callback is observed.
   - Fix: assert a landed outcome, for example through a gateway "landed remote markers" test counter, or by driving the real TCS. Optionally also check the counter's value (0).
2. **`AcksAllParkedBatchBeforeAbortIsCovered` lost its "the reply overtakes the parked ack" ordering.** Both now leave the same park-ordered queue, produce first. The ordering is still reachable when the marker's HW is already past at append (ISR {self}) while an earlier acks=all produce is parked. Add a variant with minIsr 1 / ISR {self} to keep the RC "late result re-opens a resolved txn" guard exercised.
3. **The queue pump runs before the leader-change check** (`ClientGateway.cpp:3865` vs `3868-3871`). A queued remote marker whose leader just moved is sent once to the old leader, then failed NotLeader. This is harmless today (the old leader's role gate refuses it), but it feeds NEW MEDIUM-3. Run the leader-change check first.
4. **The fenced code reuses NotCoordinator (14)** (`ControlMarker.h`, `kMarkerCoordinatorFencedError`). This answers the "error-code reuse" concern.
   - **No retry-forever risk.** The only producer of 14 on the marker paths is the worker fence (`Worker.h:3202-3209`). The TCS treats it as a terminal drop (`TCS.cpp:806-815`). Marker codes never reach a client: EndTxn uses `txnErrorToProtocol(completeTransaction)`.
   - **The opposite failure is bounded too.** A deposed load leaves the transaction Prepare* until its own unload, and the newer coordinator re-drives it.
   - **Cosmetic issue:** the gateway logs it as `"FAILED to append (error=14)"` at error level (seen in every test run) before the TCS's FENCED line. Log the fenced case as fenced, at warn level.
   - **Suggestion:** use an internal-only value outside the client enum, so a future client-side meaning of 14 on any shared path cannot collide.
5. **An owed-cap refusal is reported as NotLeader** (`Worker.h:3213-3218`). Under produce saturation the cap is refilled continuously. The marker loses each time and the TCS backs off (≤ 1 s), so EndTxn can starve. The gauge does show it; the code is misleading in logs and on the remote answer. Consider a distinct retriable code, or giving markers a reserved owed slot.
6. **No schema version bump and no machine check of the reservation** (rune-protocol `b80c5ea`, comment only).
   - With the timer removed, a not-yet-upgraded leader that silently drops template 11 now leaves the marker waiting until that node restarts (its new image fires `-1` at the coordinator). A rolling upgrade heals itself, but transactions stall until then.
   - Add a `static_assert` in `ReplicationMessages.h` against the highest generated template id once the SBE replication codec lands, and note the upgrade behaviour in the spec.
7. **The leader-side duplicate check is a linear scan** of `markersInFlight_` and `pendingMarkerResponses_` for every incoming remote marker (`ClientGateway.cpp:3815-3822`). It is cold, but O(n) per marker under heavy EOS load. Folding it into the NEW MAJOR-1 index (keyed by origin and token) makes it O(1).
