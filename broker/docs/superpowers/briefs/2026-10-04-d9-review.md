## Verdict: APPROVE WITH CHANGES

| Severity | Count |
|---|---|
| CRITICAL | 0 |
| MAJOR | 3 |
| MEDIUM | 5 |
| LOW | 7 |

The main path is correct and well built:
- A coordinator forwards a marker to a remote leader.
- The leader appends the marker on its owning worker and answers.
- The answer drives the TCS callbacks used for a local marker.
- A leader-node or leader-epoch change fails in-flight remote markers immediately, driven by the event.

The hot path is clean:
- No atomics, mutexes, virtual calls or `std::function`.
- The produce path is untouched.
- `doWork` now always calls `pumpTxnMarkers_()`, which costs three `empty()` checks.

Three MAJOR findings block "production-ready":
1. The 1 s fallback **completes** a marker instead of re-sending it.
2. The leader has no coordinator-epoch fence.
3. The leader answers on append, not on ISR commit. This is inherited from the local path, but D9 makes it the normal path.

All three have small, well-defined fixes.

## MAJOR

### MAJOR-1: the 1 s "unanswered" net completes the marker as refused instead of re-sending it

**Where:**
- `libs/gateway/src/ClientGateway.cpp:3728-3746` (`sweepUnansweredRemoteMarkers_` calls `refuseMarker_`, which erases the entry and calls `onControlMarkerRefused`).
- `ClientGateway.cpp:3748-3758` (a late answer for the erased token is dropped as "unknown").
- `ClientGateway.h:710` (`kRemoteMarkerUnansweredNs` = 1 s).
- `ClientGateway.cpp:3688` (`sentNs` is stamped when the frame enters the outbound ring, not when it is offered or acknowledged).

**Rule 1 (time-independence).** The timer does not decide *safety*. Re-sends from one coordinator go over the same per-peer publication and the leader's FIFO `markerSendQueue_`, so they stay ordered.

The timer does decide *liveness and completion*. After 1 s it throws away a marker that is merely slow. The marker may already have landed. The valid answer arriving at 1.0+ s is then ignored, because its token no longer exists.

**Failure scenario:**
1. The answer round trip is consistently ≥ 1 s. Causes include: a coordinator→leader `HeldFifo` behind a full replication backlog; the leader's worker op ring full under produce saturation, with the marker waiting in the leader's `markerSendQueue_`; or a stalled leader control loop.
2. Attempt *k* is swept at 1 s and the TCS re-queues it with backoff (≤ 1 s).
3. Attempt *k+1* is swept the same way, and every late answer is discarded.
4. Result: the transaction stays Prepare* for as long as the latency lasts. The producer gets ConcurrentTransactions. Every cycle appends **one more duplicate COMMIT/ABORT batch** to the partition log, so the log grows without bound.

This is the "tuned constant decides the outcome" pattern that rule 1 forbids.

**Second gap.** For a frame that really is lost, the timer is the *only* recovery. The hold router drops frames for a peer it sees as down (`OutboundHoldRouter.h`, PEER DOWN). A short link flap, or a leader restart faster than metadata failure detection (no epoch bump), therefore recovers only through the timer.

**Fix: make it a pure re-send, driven by events.**
- On a lost frame, **keep** the entry and re-send the **same token**. Never complete or refuse it. An answer to any copy then completes the marker, and copies stay FIFO on the peer.
- Drive the re-send from the plane's link events:
  - the hold router's down→up edge, which bumps `connGen` (`OutboundHoldRouter::markUp_`, already counted as `upEdges`);
  - and/or the coordinator's subscription image from that peer becoming available again.
- On the leader, a down-dropped answer is covered by the same re-send (the leader re-answers a duplicate token idempotently), or by holding answers until the up edge.
- If a periodic safety net remains, it must only re-send with the same token. Leadership changes stay the only events that complete a marker NotLeader.
- Add a regression test: the answer arrives after the net fired → the marker completes, with exactly one extra duplicate at most.

### MAJOR-2: no coordinator-epoch fence on the leader, so a stale marker from a deposed coordinator can close the next transaction

**Where:**
- `ClientGateway.cpp:3772-3812`: `appendRemoteControlRecord` accepts any `coordinatorEpoch`.
- `libs/node/include/rune/node/Worker.h:3196`: `psm_.fenceEpoch` raises the *producer* epoch only.
- `Worker.h:3208`: `rc->onMarker` resolves whatever transaction is open for the pid.
- `ReadCommittedView.h:228`: `onControlMarker` closes the open transaction of that pid regardless of which transaction the marker was for.
- Producer epochs are not bumped per transaction (`TransactionCoordinator.cpp:180`, InitProducerId only).

**Why D9 introduces this.** Before D9, only the node that leads a partition wrote markers to it, through one FIFO op ring. D9 adds **several unordered sources** for the same partition: coordinator X (old) and coordinator Y (new) each have their own publication to leader L. Aeron orders frames per image, but not across images.

**Failure scenario:**
1. Coordinator X sends COMMIT(T1) to L. The frame waits in X's `HeldFifo` (L is live but back-pressured), or in X's image on L behind a FetchRequest that L's poll keeps ABORTing because a worker ring is full.
2. Coordinator ownership moves to Y, for example a txn-state leadership rebalance. X unloads; `purgeQueuedMarkers` cannot reach frames already in the transport.
3. Y loads PrepareCommit(T1), re-drives COMMIT(T1) to L, and it lands. T1 completes.
4. The producer begins T2 (same pid and epoch) and produces to the partition on L.
5. X's stale COMMIT(T1) is now delivered and appended after T2's data. `onControlMarker` closes **T2**. T2's records become visible to read_committed consumers as committed. If T2 later aborts, its ABORT marker finds no open transaction (a no-op), so **aborted data stays committed**. This breaks atomicity.

**Kafka parity (rule 4).** Kafka fences this in `ProducerStateManager`: `appendEndTxnMarker` rejects a marker whose `coordinatorEpoch` is lower than the last one recorded for that pid, with `TRANSACTION_COORDINATOR_FENCED`.

**Fix:**
- Record the last marker `coordinatorEpoch` per pid in the worker's `psm_` (it is persisted in the control batch, so the PSM rebuild recovers it).
- Refuse a marker with a lower epoch. Answer with a non-retriable code that the coordinator treats as "drop / fenced".
- Add a regression test with two coordinator nodes and a stale-epoch marker delivered after the next transaction's data.

**Residual risk, same family.** Even with the fence, a same-epoch stale copy from one coordinator to an old leader can matter if leadership returns to that node. This needs the copy to be held across two leadership changes, so it is very unlikely; Kafka closes it fully only with KIP-890's per-transaction epoch bump. Note it in the spec.

### MAJOR-3: the marker "lands" at leader append, not at ISR commit (inherited, but D9 makes it the main path)

**Where:**
- `Worker.h:3200`: `appendControlBatch(markerSpan, acksAll=true)`. Here `acksAll` is only the min-ISR gate, not a wait for the high watermark.
- `Worker.h:3240`: `enqueueReturn_` right after the append.
- `ClientGateway.cpp:3586-3590`: the remote origin is answered at once.
- `ClientGateway.cpp:3769`: the coordinator calls `onControlMarkerLanded`.

**Failure scenario:**
1. L appends COMMIT(T1) and answers. The coordinator completes T1 and acks EndTxn.
2. L crashes before a follower fetched the marker. The new leader L' never got the marker (L's unreplicated tail is truncated on rejoin).
3. On L', T1's data is an open transaction with no marker. The LSO stays pinned, so read_committed consumers stall on that partition. This is a hanging transaction.
4. When the producer's next transaction writes a marker there, `onControlMarker` resolves the *open* transaction, so T1's data takes **T2's** decision. If T2 aborts, committed T1 data disappears.

**Kafka parity (rule 4).** Kafka writes markers with `requiredAcks = -1` and answers WriteTxnMarkers only after the ISR has the marker.

**Status.** The same gap exists for local markers today (pre-D9). In a multi-node cluster, though, most partitions are led remotely, so D9 makes this the *common* path. The spec's own invariant ("a marker counts toward completion once COMMITTED", `TransactionCoordinationService.cpp`, the `appendFnOverride_` note) is not met.

**Fix:**
- Defer `ControlRecordAppended` (local, and the remote answer) until HW ≥ marker offset + 1, as acks=all produces already do (`deferAck`).
- Or keep the immediate answer and have the coordinator count the marker only on a later "committed" notification.
- Add a regression test: the leader dies after the append and before the follower fetch → the coordinator must not complete; the marker is re-driven to the new leader.

## MEDIUM

### MEDIUM-1: response matching ignores `coordinatorEpoch` and tokens restart at 1 per process, so a stale answer can wedge a transaction forever

**Where:**
- `ClientGateway.cpp:3750-3752` matches on token, topic, partition and pid only.
- `ClientGateway.h:1640`: `nextMarkerToken_ = 1` on every boot.
- `TransactionCoordinationService.cpp:774/785`: `currentEpoch_` drops callbacks with the old epoch.

**Scenario:**
1. The coordinator node restarts while L still holds an unanswered marker from the previous incarnation. The marker sits in L's `markerSendQueue_` or in `pendingMarkerResponses_` behind a full ring.
2. After the restart, the new load re-drives the same Prepare* transaction (same pid and partitions) with tokens 1..N again.
3. L's late answer carries the old token and the old `coordinatorEpoch`. It matches the new entry, so `onRemoteControlRecordResponse` **erases** that entry. The TCS then ignores the callback because the epoch is stale.
4. Nothing completes or retries that marker again. There is no entry left for the sweep, and the TCS retry is `inFlight = true` and is never re-queued. The transaction stays Prepare* for good.

**Fix:**
- Also require `r.coordinatorEpoch == m.coordinatorEpoch` before erasing.
- Seed `nextMarkerToken_` with a boot nonce in the high bits.
- Add a regression test.

### MEDIUM-2: wire template ids 11/12 are hand-rolled outside the schema

**Where:** `libs/replication/include/rune/replication/ReplicationMessages.h:78-79, 638, 705`. `rune-protocol/schema/rune-replication.xml` defines ids 1–10 only (schema 112, version 3).

**Problem:**
- The schema is no longer the single source of truth.
- Nothing reserves ids 11/12. The next schema message added in rune-protocol (for example the SBE replication conversion in progress) will very likely take id 11 and silently collide on the same stream, because `handleFrame_` dispatches on the template id alone (`AeronPartitionTransport.cpp:585-608`).
- The schema version was not bumped. A rolling-upgrade peer silently drops the unknown template, which turns into MAJOR-1's timer loop until every node is upgraded.

**Fix:** add `WriteTxnMarker` / `WriteTxnMarkerResponse` to `rune-replication.xml` (`sinceVersion` = 4) in rune-protocol, and switch to the generated codecs. At minimum, reserve the ids there now and add a `static_assert` cross-check against the generated header.

### MEDIUM-3: the stuck-markers gauge is not exposed on any metrics path

**Where:** `TransactionCoordinationService.h:195-200`; `TransactionCoordinationService.cpp:825-836`.

**Problem.**
- The gauge is an in-process accessor plus two log lines.
- The spec says "exposed via the existing metrics/log path", and the broker *has* an operator-visible counter path: Aeron counters in CnC, read by `rune_role` (`BrokerNode.cpp:380-390`).
- An operator therefore cannot read or alert on the gauge without grepping logs.

**Gauge semantics are otherwise correct:**
- It counts retries refused for more than 5 s that have not landed, including ones re-dispatched and in flight.
- It is cleared when the marker lands or is dropped (`dropRetry_`).
- It is reset on load and unload.

**Fix:** publish the gauge as an Aeron counter, the same way as the role and term counters.

### MEDIUM-4: the BrokerNode wiring is never exercised by a test, and the E3 tx_* suite was not run

**Where:** `libs/node/src/BrokerNode.cpp:2038-2050` and `2900-2901`.

**Problem.**
- The 3-node rig wires the transport and the gateway by hand (`D9CrossNodeMarkerTest.cpp:500-517`), so a broken or missing BrokerNode wiring would pass every D9 test.
- Two things are unproven: the wiring only happens inside the `txnCoordService_` try block when `replTransport_` exists, and the per-worker replication-plane mode still polls the control-plane transport.
- Project rule "never hand over untested code" requires the real path with the default config.

**Fix:** add one BrokerNode-level 3-node test, or run the E3 tx_atomicity / tx_eos / tx_read_committed suite on k3s-node-01, before merge.

### MEDIUM-5: the leader-side check compares the leader's own routing image, which can lag its replica role, and convergence then polls on backoff

**Where:** `ClientGateway.cpp:3788-3790`.

**Problem.**
- The replica's role gate in `appendControlBatch` is already authoritative.
- This second check, against L's own routing image, refuses with NotLeader when L's image is older than the coordinator's. That happens right after an election, when the coordinator's image moved first.
- Recovery is then only the TCS backoff loop (100 ms… up to 1 s), not an event.
- It is correct but slow, and it adds a third "who leads?" source to reason about.

**Fix:** drop the image check and rely on the worker's role gate. If it is kept, make L's image update re-answer instead of polling.

## LOW

1. **`updateStuckMarkers_` walks every awaiting transaction on every control-loop pass** whenever any EndTxn is in flight. The guard is `!awaiting_.empty()`, which is the normal state under EOS load. Guard on "any retry entry" (a count) or rate-limit the walk. (`TransactionCoordinationService.cpp:259, 825-836`)
2. **`firstRefusedNs` comes from `lastNowNs_`.** A refusal before the first `doWork` records 0 and counts as stuck immediately. (`TransactionCoordinationService.cpp:820-821`)
3. **The decoded `commit` / `producerId` fields are not cross-checked against the marker bytes.** The worker uses the bytes; the gateway's inline path and the answers use the fields. A malformed or mismatched frame is accepted. Also, a marker the replica rejects as invalid (`kAppendInvalidBatch` → `Internal`) is retried forever by the coordinator, the same as on the local path. (`ClientGateway.cpp:3772-3812`, `ReplicationMessages.h:672-690`)
4. **A marker above 128 B silently takes the local path, which can never land remotely.** Today it cannot happen, because `ControlMarker::ENCODED_SIZE` is fixed. Make it a `static_assert(ControlMarker::ENCODED_SIZE <= WriteTxnMarkerMsg::kMaxMarkerBytes)`. (`ClientGateway.cpp:4940`)
5. **Self-addressed sends are delivered re-entrantly** (`AeronPartitionTransport.cpp:379, 388`). They are unreachable today, but a self-send from inside `pumpMarkerQueue_` would change `markerSendQueue_` while it is being iterated. Refuse or assert on `to == self` instead.
6. **The coordinator's produce gate answers NotLeader instead of a redirect** while a remote marker for that partition is queued (`ClientGateway.cpp:2254`, report §6.6). It is transient but avoidable: skip the gate for entries with `remoteNode >= 0`, because the coordinator does not lead that partition.
7. **`setRoutingImageSnapshot` is no longer `noexcept`** and now calls into the TCS synchronously, from inside the NodeRuntimeAgent routing publish (`ClientGateway.h:359-365`). An allocation failure now escapes into the duty cycle. Consider queueing the failed tokens and completing them in `pumpTxnMarkers_`.

## Answers to the specific checks

**Token lifecycle**
- Coordinator entries: created in `appendControlRecord`, sent or queued FIFO, then erased by the answer, by a leader or epoch change, by the sweep, or by `purgeQueuedMarkers` if still queued.
- Leader-side entries carry `originNode` / `originToken`, are skipped by the purge (correct) and by the sweep and leader-change logic (correct), and are answered exactly once on append or refusal.
- Gaps: MEDIUM-1 (epoch not matched, token reuse across restarts) and MAJOR-1 (the sweep erases instead of re-sending).

**Epoch fencing of answers**
- The TCS ignores callbacks with a stale epoch.
- The gateway erases the entry before that check (MEDIUM-1).
- The leader does not fence stale coordinator epochs at all (MAJOR-2).

**Coordinator failover mid-marker**
- Queued markers are purged and sent ones complete harmlessly against the old epoch.
- Frames already in the transport are not purgeable, which leads to MAJOR-2.

**Leader failover after the append, before the answer**
- The duplicate is harmless:
  - `LsoTracker::onControlMarker` returns -1 when no transaction is open, so `RcState::applyMarker_` does nothing (`RcState.h:343-345`).
  - `psm_.fenceEpoch` only raises the epoch.
  - `TxnCleanState::onMarker` treats it as an empty-transaction marker that can be removed.
- This holds only while the producer has not opened the next transaction on that partition, which the deferred EndTxn guarantees for copies from the **same** coordinator on the same peer FIFO.
- Leader failover **after the answer** is MAJOR-3.

**Full outbound ring**
- Markers stay in `markerSendQueue_` (FIFO).
- Answers stay in `pendingMarkerResponses_` (FIFO).
- Nothing is dropped. Tested.

**Unknown topic**
- On the coordinator: no local log → -1 → TCS retry; it is dropped once the coordinator's metadata shows the partition gone (`partitionExists_`).
- On the leader: always NotLeader, never UnknownTopic. This is correct for a registry that is merely behind.

**Self is leader by stale routing**
- On the coordinator: the local path → the worker role gate answers NotLeader → TCS backoff → the next attempt re-resolves the leader. It converges, but by backoff, not by an event.

**Remote node restart**
- If the epoch bumps, the event fires correctly.
- With no metadata change, frames to the down peer are dropped and only the 1 s timer recovers (MAJOR-1).

**Ordering on the leader**
- The forwarded marker uses the same owning-worker op ring as a local marker, so it lands after every produce that was acknowledged before EndTxn.
- Per-peer FIFO is guaranteed: one `ExclusivePublication` per peer (`AeronPartitionTransport.cpp:82`), the hold router FIFO per peer, and in-order delivery within one Aeron image.
- That FIFO covers re-sends from **one** coordinator only. Copies from different coordinators are unordered (MAJOR-2).

**Message layout**
- Little-endian fixed blocks, sized 40+≤128 and 40.
- Decode checks: the total length, the template id, `blockLength >= BLOCK_LENGTH`, `markerLen <= 128`, and `markerLen` within the frame using subtraction (no overflow).
- Zero-copy span. Good.
- Ids do not collide today; see MEDIUM-2 for the future collision and the source-of-truth issue.

**Tests**
- They use a real cross-node transport: 3 nodes, a real `AeronPartitionTransport` per node on one `EmbeddedDriver`, real replication, and a real TCS on node 3.
- No sleeps: there is a single `std::this_thread::yield()`, and every wait is a condition loop with a cap.
- Names follow `*Regression*`.
- The node clock is driven explicitly, so the 1 s sweep never fires inside the integration windows. Good for determinism, but the timer-versus-late-answer interaction (MAJOR-1) is untested.
- Missing:
  - MAJOR-1: a late answer after the net fired;
  - MAJOR-2: a stale coordinator epoch;
  - MAJOR-3: leader death after the answer and before replication;
  - MEDIUM-1: a stale answer after a coordinator restart;
  - MEDIUM-4: the BrokerNode wiring.
