## Measured first (A, 20k, one worker: perf trace -s 4 s, perf record 4 s)
- **Records per batch at 20k = 1.03** (446k batches for 460k records, every run).
  - The invoker client already sends one frame per partition per pass ("end-of-pass batching").
  - Records arrive 50 us apart, round-robin over 8 partitions, so a pass almost never holds 2 records of one
    partition.
  - Idea (1) is already implemented and has nothing left to coalesce at this rate.
- **~3.6 messages per send syscall.** A node sends ~29.5k push / fast-ack / ack messages/s in 8.1k send syscalls.
  - There is one publication per peer per worker, and Aeron packs everything offered before the sender duty into one
    datagram.
  - Per pass a worker has about one batch per partition, so there is no second batch to fold into a push.
  - Idea (2) is what the transport already does.
- **Syscalls per worker per second:**
  - recvmmsg 66.5k, 78.6% of them empty;
  - epoll_wait 11.5k;
  - pwrite 12.2k;
  - sends 8.1k;
  - sched_yield 143, nanosleep 5.
- **Worker profile:**
  - syscall entry 10% + recvmmsg 9.7%: the empty polls (idea 3), which A7's epoll-first removes;
  - **rune_fr_c_now 2.6% + rune_fr_c_span 0.5%** with the recorder off.
- **Client profile:** **rune_fr_c_now 4.5% + rune_fr_c_span 1.2%**.
- **The workers never park at 20k.** There is ~1 wake event every ~70 us per worker, and the backoff needs 10 empty
  passes before its first yield and 30 before its first park.
  - So 20k worker CPU is set by the idle shape and the event rate, not by work per batch.
  - Less work per event gives shorter passes, not idle time.
  - The box is saturated in every arm (system idle 0-2%).

## Change
- **rune-fr 5fe5464.** The patched Aeron C hooks call `rune_fr_c_now()` at every duty-cycle span.
  - It ran rdtscp even when the recorder was disabled.
  - Now it returns 0 when disabled; a span started at 0 already records nothing.
  - RED-first test: `HopPrimitivesRegression.CApiNowIsZeroWhileDisabledRegression`.
  - Proof of path: B's disassembly checks `g_enabled` before rdtscp in both binaries.
- **Tried and dropped: repeat the A1 driver duty only while a backlog may be left.**
  - A byte threshold missed receive backlogs of small datagrams. The first B probe at 20k collapsed: p50 26 ms, ~2
    records per batch.
  - A receive-full counter fixed that side, but the Linux tests showed window-limited sends also slip under any byte
    signal.
  - The result was not safe without send- and receive-side "full" counters through the bindings.
  - Its 20k payoff is capped by the idle shape anyway, so it was reverted.

## Concerns
- **The goal is not met.** 20k worker CPU is unchanged.  What would move it:
  - (a) A9's eventfd doorbell on cross-thread rings, so the idle can park after an empty pass without the 30-pass
    spin/yield phase;
  - (b) A7's epoll-first, for the ~20% of each worker spent in empty recvmmsg;
  - (c) fewer events per record, which here means coalescing across passes, i.e. a linger: latency.
- **20k p99 was higher in both B rounds** (29-37 vs 16-26 ms).  It is inside the 13-51 ms spread already recorded for
  this config, and the change only removes an instruction.  Still, n=2 does not prove it neutral; an n ≥ 15 ABAB
  would.
- **The product change is in shared sibling checkouts.**
  - rune-fr 5fe5464 is on its current branch, diag/fr-shard-waterfall, which every broker and client worktree builds
    as ../rune-fr.
  - rune-protocol has an add+revert pair, 214440c / 8bd5d23, on feat/self-contained-worker-shards; net zero.
- **Planka MCP failed to connect** this session, so no ticket moves.
- **The A arm in the probes and A/B ran with FR compiled in** (ENABLE_FLIGHT_RECORDER defaults ON), the same as every
  earlier reference number.  The fix brings that default build to roughly "FR off" cost on the hot path.
- **The tp.sh RESULT line is cut at 400 characters**, so `records_per_batch` prints truncated.  Use sent/batches
  instead, as done here.
